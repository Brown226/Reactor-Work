# Reactor 全面吸收 PKPM Agent 能力方案

> 目标：不是替换，是以 Reactor 为主体，吸收 PKPM Agent 的全部能力并拓宽
> 依据：Reactor 77 个 service 模块现状 + PKPM Agent 完整逆向资产

---

## 二、吸收策略：三层递进

```
第一层：能力吸收（Capability）—— 把缺的补上
第二层：能力融合（Fusion）—— 让两套能力互相增强
第三层：能力拓宽（Expansion）—— 做出双方都没有的
```

### 关键原则：**Reactor 是主体，不重写**

| 做法 | 评价 |
|---|---|
| ❌ 把 PKPM Agent 架构搬过来替换 Reactor | 错，浪费 Reactor 77 个成熟模块 |
| ❌ 只接 PKPM 的 API，不吸收设计 | 错，丢掉最有价值的确定性体系 |
| ✅ **在 Reactor 现有骨架上，长出工程能力** | 对 |

## 三、第一层：能力吸收（12-16 周）

### Phase A：工程连接层（W1-4）

**目标**：Reactor 能驱动工程软件

```
packages/services/src/
├── engineering/                      ← 新建目录
│   ├── mcp-link/
│   │   ├── base.ts                   BaseMCPLink 抽象
│   │   ├── registry.ts               注册表（14 函数）
│   │   ├── discovery.ts              四路安装发现
│   │   └── links/
│   │       ├── bimbase.ts            ★ P0
│   │       ├── sap2000.ts
│   │       ├── autocad.ts
│   │       ├── rhino.ts
│   │       └── office.ts
│   └── py-executor/                  Python 执行器桥
│       ├── manager.ts                子进程池
│       ├── worker.ts                 会话常驻
│       └── inject.ts                 ★ mcp_ptc 函数注入
```

**吸收点**：

| 从 PKPM Agent 吸收 | 落到 Reactor |
|---|---|
| `BaseMCPLink` 四方法设计 | `engineering/mcp-link/base.ts` |
| 四路注册表发现 | `discovery.ts` |
| 端口探测三函数 | `common_tools` 移植 |
| **`mcp_ptc` 函数注入** | **`inject.ts`（自研，2 周）** |
| 连接简报 | 接入 Reactor 的 prompt 注入 |

**融合点**：
- Reactor 已有 `mcp-sync`，**不重复造**，而是让它调用新的 `mcp-link`
- `mcp-sync` 管配置持久化，`mcp-link` 管运行时连接

### Phase B：工程技能库（W5-6）

**目标**：Reactor 的 skills 系统装载 22 份工程技能

Reactor 已有 `skills`（很成熟：scope/enabled/promptContext/copyToCommon/deleteSkill）。

**只需做两件事**：

```
1. 把 22 份 SKILL.md 放进技能目录
2. 把 258 项 references 按需加载接上
```

**融合点**：Reactor 的 `skill-sync` 支持服务端下发，**意味着可以集中管理企业技能库**——这是 PKPM Agent 没有的能力。

### Phase C：Python 执行器（W7-9）

**目标**：Agent 能写 Python 脚本驱动软件

```
Reactor (Node)  →  IPC  →  Python worker  →  COM/MCP  →  软件
```

**吸收点**：

| 从 PKPM Agent 吸收 | 说明 |
|---|---|
| 会话常驻 worker（按 key） | Tekla 的 .NET 运行时不能反复加载 |
| Job Object 回收 | Windows 进程树清理 |
| 超时中断（异步 + 阻塞两套） | 计算可能跑几分钟 |
| 输出捕获（只有 print 返回） | 省 token |

**融合点**：Reactor 的 `terminal` 模块已有进程管理，**复用它的进程树逻辑**。

### Phase D：确定性体系（W10-12）★ 最不能省

**目标**：让 AI 输出可验证

```
packages/services/src/engineering/determinism/
├── spec.ts               分析规格定义（照抄 analysis-spec.schema.json）
├── preflight.ts          预检（移植 823 行 Python 逻辑）
├── evidence.ts           证据门禁（移植 736 行）
├── gates/                门禁实现
│   ├── forceBalance.ts   力/力矩平衡
│   ├── energy.ts         能量
│   ├── contact.ts        接触
│   ├── singularity.ts    奇异应力
│   └── meshConvergence.ts 网格收敛
└── contract.ts           执行契约校验
```

**吸收点**：三种判定操作符

```typescript
type Operator = 'between' | 'approximately' | 'review';
// review 永远返回 false —— 有些判断 AI 不许自己下结论
```

**这是 Reactor 现在完全没有的能力，也是产品能不能卖的关键。**

### Phase E：上下文压缩（W13-14）

**目标**：长会话不爆

**吸收点**（从 79 个签名还原）：

```
1. 找安全切点 _find_safe_cutoff_point（不能切断 tool_call 配对）
2. 原子组 _atomic_groups（assistant + 它的 tool 消息）
3. 分级摘要 _age_to_budget（老内容更狠）
4. tpc 动态校准（tokens-per-char）
5. 压缩后仍可 browse 原文
```

**融合点**：Reactor 有 `memory` 模块，压缩后的历史可以进 memory。

### Phase F：知识库引擎（W15-16）

**目标**：工程知识可检索、可追溯

**两条路**：

| 选项 | 说明 |
|---|---|
| A. 吸收 PKPM 的 wiki_store 设计 | 学它的 `read_citation`（引用可达行） |
| B. **用 EvoFlow**（已授权） | 直接对接，只补引用回溯 |

**建议 B**，但要吸收两个设计点：
1. **引用可回溯到行**（规范条文必须可溯源）
2. **语义索引异步降级**（未建好时关键词搜索不受影响）

## 四、第二层：能力融合（吸收后的化学反应）

这部分是**吸收方案的核心价值**——不是简单相加。

### 融合点 1：Reactor 的远程能力 × 工程软件

Reactor 有 `remote-projects` + `reactor-server` + `remote-sync`。

**PKPM Agent 只能在本机跑。** 融合后：

```
设计院的服务器上装 PKPM + Reactor Server
  ↓
工程师在任何地方用 Reactor 客户端
  ↓
远程驱动服务器上的 PKPM 建模、计算
```

**这是 PKPM Agent 结构上做不到的**（它是单机 Electron App）。

### 融合点 2：Reactor 的多端 × 工程场景

| Reactor 已有 | 融合工程后的场景 |
|---|---|
| 飞书/Telegram bot（`bots`） | **群里 @机器人 查计算结果** |
| 浏览器操控（`browserView`） | 打开规范网站查条文 |
| 语音（`voice-input`） | **工地上语音问"这层柱子够不够"** |
| 会话共享（`conversation-share`） | 把计算结果发给同事 |
| 子代理（`subagents`） | **一个查规范、一个跑计算、一个出报告** |

### 融合点 3：Reactor 的插件系统 × 工程技能

Reactor 有 `plugin-ui-bridge`（插件可渲染原生 UI）。

**融合后**：工程插件可以有自己的参数面板

```
用户点插件 → 弹出参数表单（层号、截面、荷载）
           → Agent 填好 → 执行
```

这就是 PKPM Agent 的 `plugin-creator` 能力，但**长在 Reactor 更强的插件系统上**。

### 融合点 4：确定性体系 × 所有工具

**PKPM Agent 的确定性体系只作用于工程软件。**

**融合后可以推广到所有操作**：

```
Reactor 现有的文件编辑、终端命令、Git 操作
  → 也走预检 + 证据门禁
  → "改完这 20 个文件，测试过了吗？"
```

**这是能力的泛化，Reactor 独有。**

## 五、第三层：能力拓宽（超越双方）

### 拓宽 1：从「工程软件」到「工程 + 编程」

```
PKPM Agent：只能做工程
Reactor：   只能做编程
融合后：     做完计算 → 直接改代码 / 写脚本 / 提 PR
```

**场景**：调通一个 SAP2000 脚本 → 直接存进你们的 Git 仓库 → 其他人复用

### 拓宽 2：从「单机」到「团队」

```
PKPM Agent：单机、单用户
Reactor：   有 server、有同步、有多端
融合后：     企业级工程知识资产平台
            ├─ 技能库集中下发（server-skills）
            ├─ 构件库共享
            ├─ 审查规则统一
            └─ 计算结果归档
```

### 拓宽 3：从「建筑结构」到「全工程」

Reactor 吸收 22 个技能后，覆盖面远超 PKPM Agent 的定位：

| 领域 | 技能 |
|---|---|
| 建筑结构 | PKPM / ETABS / SAP2000 / STAAD / SAUSG |
| **工厂设计** | PlantS（你们的 E3D 替代战场） |
| **工业仿真** | Abaqus / PKPMCAE |
| 三维建模 | Rhino / SketchUp / Tekla |
| 制图 | AutoCAD / 浩辰 / 中望 |
| 绿色低碳 | GBP（12 类子技能） |
| 办公 | Word / Excel / PPT / PDF |
| 图纸审查 | PKPM-Checker |

### 拓宽 4：从「工具」到「平台」

PKPM Agent 是封闭产品，Reactor 可以做成**开放平台**：

```
第三方可以：
  ├─ 写工程技能（skill-creator 规范）
  ├─ 写插件（plugin-creator 规范）
  ├─ 接自己的软件（BaseMCPLink 扩展）
  └─ 贡献 API 库
```

## 八、必须先决策的三件事

### 决策 1：Python 执行器放哪

| 方案 | 优点 | 缺点 |
|---|---|---|
| 独立 Python 服务 | 干净隔离 | 多一个进程要管 |
| Reuse zcode-agent | 复用进程管理 | 混在 Node 进程里不好管 |
| **子进程池（推荐）** | 平衡 | 要自己实现池 |

### 决策 2：知识库用谁

- **A**：移植 PKPM 的 wiki_store（23 个 pyd，$成本高$）
- **B**：**用 EvoFlow + 补引用回溯**（推荐）

### 决策 3：确定性体系做多深

| 级别 | 内容 | 工作量 |
|---|---|---|
| 基础 | 只有预检 | 2 周 |
| **标准（推荐）** | 预检 + 证据门禁 | 4 周 |
| 完整 | + 网格收敛 + 奇异应力 | 6 周 |

## 九、风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| **BIMBase SDK 不可写** | 整个方案不成立 | **W1 必须先验证** |
| 工程软件版本漂移 | 接口失效 | 适配器隔离 + 版本探测 |
| Python 环境依赖地狱 | 部署困难 | 参考 PKPM 的可移植 venv 方案 |
| 团队不熟悉工程领域 | 做出来不实用 | 找结构工程师参与验收 |
| 摊子铺太大 | 都做不完 | 按 Phase 交付，每个都能独立用 |

## 十、一句话总结

**PKPM Agent 给你们的是「工程能力的零件箱」，Reactor 是「已经造好的车」。**

吸收的正确姿势不是把零件箱当车开，而是：

> **把零件装到车上，让车能开进工地。**

而 Reactor 比 PKPM Agent 多出来的（远程、多端、插件、编程）就是**装完零件后的额外马力**。
