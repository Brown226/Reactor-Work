# 补充：工程确定性体系（此前方案遗漏的核心）

> 复核发现：《PKPM移植设计方案》只讲了架构，遗漏了**这套产品真正的差异化设计**。
> 这部分是从 Abaqus-Link + PKPMCAE-Link 的明文代码还原出来的。

---

## 一、为什么这块最重要

PKPM Agent 的宣传词是「控制大模型幻觉、保障工程确定性」。
**具体怎么控制？** 代码里写得很清楚，分三道闸：

```
输入闸：preflight_analysis_spec.py   (823行)  ← 提交计算前
过程闸：execution_contract.md        (50KB)   ← 执行过程中
输出闸：evaluate_result_evidence.py  (736行)  ← 结果判定时
```

这三道闸是**纯 Python 确定性代码，不经过 LLM**。

---

## 二、输入闸：分析规格预检

### 设计要点

`analysis_spec` 必须**显式记录**：

```
分析类型 / 单位 / 材料 / 几何 / 分析步 /
边界条件 / 连接 / 载荷 / 网格 / 输出 / 验收标准
```

### 铁律（技能原文）

> 结构校验失败时**报告缺项并停止**，**不能自行补**材料、单位、边界条件、接触、`nlgeom` 或验收阈值。

**这条极其关键**：LLM 最擅长的就是"帮你补全"，但在工程场景这是灾难。

### 校验时机

| 时机 | 做什么 |
|---|---|
| 分析配置完成、首次提交 Job 前 | 跑一次 `validate_analysis_spec.py` |
| 规格变化后 | 只在**后续提交或结果判定前**重跑 |
| 每个几何/材料/网格里程碑 | **不重复校验**（省 token） |

### 三种结果的处理

| 结果 | 处理 |
|---|---|
| `FAIL` / `UNSUPPORTED` | 停止 |
| `WARN` | **必须连同证据交给用户判断** |
| `PASS` | 继续 |

## 三、输出闸：结果证据门禁（最精妙的设计）

### 核心思想

> 门禁未通过时**只能报告未验证或失败**，**不能仅凭 `COMPLETED` 宣称结果正确**。

这一句直接击中了 AI 工程应用的最大问题：**求解器说"算完了"≠"结果对"**。

### 三种判定操作符（从代码里提取）

```python
def _compare(value, operator, limit) -> tuple[bool, str]:
    if operator == "review":
        # ★ 必须是人工判断，永远不会自动通过
        return False, "operator 'review' requires human judgment and cannot pass automatically"

    if operator == "between":
        # limit = [lower, upper]
        return limit[0] <= value <= limit[1], ""

    if operator == "approximately":
        # limit = {target, tolerance}
        return abs(value - target) <= tolerance, ""
```

**注意 `review` 这个操作符的设计**：它**永远返回 False**。
意思是：有些判定 AI 永远不许自己下结论，必须人来。

### 门禁类型（从 references 里提取）

| 门禁 | 检查什么 |
|---|---|
| 力/力矩平衡 | 反力是否等于外荷载 |
| 能量 | 应变能是否合理 |
| 接触 | 接触状态是否收敛 |
| 终态 | 分析是否正常结束 |
| **奇异应力** | 是否出现不合理的应力集中 |
| **网格收敛** | 加密后结果是否稳定 |

**后两个是纯工程经验**，一般 AI 产品想不到要做。

### 工作流

```
1. 读取 references/result-evidence-gates.md
2. 确定要提取哪些量
3. 确定性提取（不用 LLM）
4. 写入 result_evidence
5. 运行 evaluate_result_evidence.py
6. 门禁通过 → 报告结果
   门禁不通过 → 报告"未验证"
```

## 四、过程闸：执行契约

`PKPMCAE-Link/references/execution_contract.md`（50KB）规定的核心约束：

### ① 规格缺失先澄清，不猜

> 关键规格缺失时**先澄清**；默认值、估算和等效假设**必须注明**。

### ② 区分"手册记载"与"未验证能力"

> API 参数、枚举、单位和执行顺序以本技能中对应路线的用法**与实际软件版本**为依据，
> **不编造接口**。区分手册记载与未验证能力。

### ③ 软件脚本与 Agent 代码分离

> 软件内嵌 Python **禁止 print、中文标识符和第三方库**

这条很实际：Abaqus/CAE 内嵌的 Python 2.7 环境很脆弱。

### ④ 完成即停，不自动扩展

> 完成规定的产物存在性核对后**交付并停止**。
> 未经用户明确要求，**不自动**分析结果、优化模型、做收敛研究或重跑。

**这是防止 AI "自作多情"的关键规则。**

### ⑤ 用户指令优先于模板

> 用户明确指令**优先于**模板约定；**不为满足模板或工具校验改变用户要求**。

### ⑥ 失败不自动重试

> 执行失败时**不自动重试**。先读取 `error.recovery` 中的真实对象类型、
> 可用成员、调用签名、相近参数名和 repository 键——这些是**当前运行时证据**。

只有仍缺精确契约时，才针对原操作**定向查询一次**；
**禁止通过改写关键词连续试探**。

## 五、对 Reactor 移植的具体建议

### 必须实现的三个组件

```typescript
// 1. 规格预检器
interface AnalysisSpec { /* 见 analysis-spec.schema.json */ }
function preflight(spec: AnalysisSpec): {
  status: 'PASS' | 'WARN' | 'FAIL' | 'UNSUPPORTED';
  missing: string[];
  warnings: { field: string; reason: string }[];
}

// 2. 证据门禁
interface EvidenceCriteria {
  operator: 'between' | 'approximately' | 'review';
  limit: number | [number, number] | { target: number; tolerance: number };
}
function evaluateEvidence(
  spec: AnalysisSpec,
  evidence: Record<string, number>
): { passed: boolean; reasons: string[] };

// 3. 执行契约中间件
// 在 tool_call 前检查：
//   - 规格是否完整
//   - 是否在允许的操作范围内
//   - 是否需要用户确认
```

### 三条必须写进系统提示词的铁律

```
1. 规格缺失先澄清，不能自行补全材料/单位/边界/阈值
2. 求解器说 COMPLETED ≠ 结果正确，必须过证据门禁
3. 完成即停，不自动优化、不自动重跑、不自动扩展分析
```

## 六、这块比架构更值钱

| 对比项 | 架构 | 确定性体系 |
|---|---|---|
| 可复制性 | 高（开源方案多） | **低**（需要工程领域知识） |

| 竞品差距 | 小 | **大** |

## 七、修订后的实施优先级

原方案把「中间件链」排在 Week 9-11，把确定性体系漏了。

**建议调整为：**

```
W1-2    MCP 连接层
W3-5    Python 执行器
W6      函数检索
W7-8    技能系统
W9-10   ★ 确定性体系（预检 + 证据门禁）   ← 新增，提前
W11-12  中间件链（含权限）
W13     知识库对接
```

**理由**：确定性体系是产品能不能卖的前提，不能放到最后。
