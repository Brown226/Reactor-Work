# 批量审查

## 步骤

1. **先列清单并确认范围**。把要审的文件列出来（含路径）给用户确认；范围不明的先问，不要自己扩大或缩小。
2. **逐个处理，一份文件一轮**：
   - `parse_document`（或 `ocr_scan` / `parse_dwg`，按文件类型选）抽成 markdown；
     抽取失败（工具报错）时**不要**用 `Read` 兜底读 docx/xlsx/pptx（那是乱码，
     会把错误报告写得像真的一样）——按 review-standard-check 的失败分支处理，并记入 `scope`。
   - 长正文先用 `Write` 落成 `.extracted.txt`，审查时传 `textFile`（偏移仍是全文基准）；
   - 对文本跑对应的审查（`review-proofread` / `review-consistency` / `review-standard-check` 等）；
   - 每份文件**单独**保留它的结论，不要在处理中途就把结论"揉"成一个池子——合并后无法回溯是哪份文件的问题。
3. **扇出方式按"文件数或文本量"选**（两者任一超线就走工作流）：
   - 文件数 ≤3 **且**单份正文都很短（合计约 2 万字符以内）：顺序处理，不要为它起工作流。
   - 文件数 >3，**或**任一份正文超过约 2 万字符（设计说明/PSAR 级别），**或**合计文本量很大：
     用 `CreateWorkflow` 按文件扇出子代理，每个子代理只负责一份文件的抽取 + 审查，
     返回结构化的 `{file, issues[]}`；主流程只负责汇总与出报告。
     理由：单份文件的审查会读进去大量正文，串行做容易把上下文吃满，且一份失败会拖住整批；
     成本的真实驱动因素是**文本量**，不是文件数。
4. **合并报告**：调用 `ExportReviewReport`，一次生成一份总报告：
   - `title` 写批次名（如「XX 项目设计说明批量审查」）；
   - `scope` 必须写清楚**审了几份、什么类型、没审什么**（如「12 份 docx 正文；未含 dwg 图纸」；
     某份抽取失败也要写进去）；
   - `conclusion` 必填：全部审完且只有部分文件有问题 → `passed`；有文件没审成 → `partial`；
     全部没审成 → `not_checked`；
   - `issues` 里每条用 `location` 带上文件名（如「HX1CI0842.docx §5.2」），否则报告里分不清是哪份文件；
   - 涉及标准引用自检时，把 `KnowledgeCheck` 的 `stamp` 放进 `basis.standardsStamp`、
     `coverage.uncoveredFamilies` 放进 `basis.uncoveredFamilies`——报告要能自证对着哪一版库判的；
   - 用户要明细表就再导一份 `.xlsx`。

## 纪律

- **不要漏报"没审成的"**：某份文件抽取失败（扫描件、格式不支持）时，必须写进 `scope` 与结论里，
  不能让它在报告里静默消失——那会让读者以为"这批都干净"。
- **问题条数超过 5000 会被工具拒绝**：这时按章节或子目录拆成多份报告分别导出，
  不要把 info 级条目塞进问题表凑数。
- 报告结尾保留工具自带的那句"供复核参考"；批量报告更要如此，它不是终稿。
- 不要把不同文件之间**真实存在**的矛盾当成单文件问题：跨文件不一致属于"以文审文"，要单独说明
  基准与偏差方向。
