# 标准引用自检

## 为什么必须先调工具

「某标准还在不在实施」是**事实问题**，不能靠模型记忆回答——模型对标准状态的记忆既过时又不可验证。
本技能一律以 `KnowledgeCheck`（`action=standards`）的返回为准。

## 步骤

1. 抽取文档正文的**纯文本**。这一步有三个互不相同的失败形态，必须分清：

   | 形态 | 判据 | 处理 |
   | --- | --- | --- |
   | 抽取成功 | `parse_document` 返回 markdown | 继续自检 |
   | 无文本层 | 图纸 / 扫描件，工具明确返回"无文本层"/`needsOcr` | 说明无法自检，建议改用 `ocr_scan` 后重试 |
   | **抽取工具失败** | 工具报错（如「未找到 anydoc 原生资产」「资产加载失败」） | **终止自检**，报告用户"文档解析组件不可用"，不要换工具硬读 |

   - 抽取工具用 `parse_document`（docx/doc/xlsx/xls/pptx/ppt/odt/rtf/csv/epub/pdf）；扫描件 PDF 用 `ocr_scan`；
     图纸用 `parse_dwg`。`Read` **不能**用来读 docx/xlsx/pptx——按 utf8 读出来是乱码，
     而对乱码做自检会产出一份"看起来正常"的错误报告，这比报错危险得多。
   - 抽取失败的典型原因：解析插件资产不完整（多见于刚安装/升级后）。此时**不要**降级、不要用
     `Read` 兜底，直接告诉用户重试或重启应用后再来。
2. 调用 `KnowledgeCheck`：
   - 短正文：`action: "standards"`，`text` 传正文，`sourcePath` 传来源文件路径。
   - 长正文（超过约 40 万字符，如 PSAR/设计说明）：先用 `Write` 把提取出的纯文本落成文件
     （如 `<被审文件名>.extracted.txt`），再传 `textFile: "<该文件绝对路径>"`。
     **不要手工切片多次传**——`startOffset`/`endOffset` 是相对传入文本的，切片会让偏移变成
     "合法但错的"，前端高亮会跳到错误位置。
3. **看 `stale`**：若 `stale: true`，说明端侧缓存缺失——**不要下任何结论**，提示用户先在桌面端登录
   企业服务端完成知识库同步，再重跑。注意 `stale: false` 但 `notice` 提到快照较旧时：结论仍可用，
   但要向用户说明"这是 N 天前的库快照"。
4. 按 `issues` 逐条汇报。类别与话术（照抄口径，不要自行加严或放宽）：

| `code` | 结论 | 严重度 | 怎么说 |
| --- | --- | --- | --- |
| `abolished` | 引用了已废止标准 | `error` | 给出库中现行版本（`suggestion`）作为改引建议 |
| `no_year` | 引用未注年代号 | `warning` | 引用规范要求注年代号；给出库中现行版本；缺 `/T` 的要指出 |
| `no_version` | 未写版本标注 | `warning` | 同一年代号库中分多个版本（如 `（2018年版）`），应写明 |
| `not_in_library` | 编号/年代号库中不存在 | `error` | 列出库中该编号的全部条目，提示疑似笔误或前缀错（`GB` vs `GB/T`） |
| `family_not_collected` | 库未覆盖该标准体系 | `info` | 该体系（如 `DL`/`NB`/`EJ`/`CECS`）在库里几乎没有条目，**无法核对**；需人工确认，**不得**说成编号有错或标准不存在 |
| `missing` | 同体系收录充分但查不到 | `warning` | 更可能是编号或年代号笔误——**必须写"需人工确认"** |
| `upcoming` | 即将实施 | `info` | 实施日期未到，需确认设计引用是否合适 |
| `ok` | 通过 | 无 | 只在汇总里计数，不要逐条列出 |

5. 每条问题带 `startOffset`/`endOffset`/`line`，**原样透传**——前端要用它做「点击问题 → 原文高亮」。
6. 汇总给出：共 N 条引用、通过多少、各类问题多少；`coverage.uncoveredFamilies` 非空时，
   必须显式说明"这些体系本次无法机检核对"。

## 不要做

- 不要在 `stale: true` 时用模型记忆补一份"大概"的结论。
- 不要把 `family_not_collected` 说成"该标准不存在"或"编号写错了"——那是库缺口，不是文档缺陷。
  也不要把 `missing` 轻描淡写说成"库待补充"——同体系收录充分时它更可能是笔误。
- 不要漏掉未识别到的引用类型（如 `DL`/`NB`/`CECS` 等行业标准），它们常因库未收录而报
  `family_not_collected`，这正是要暴给用户的库缺口。
- **绝不对乱码做自检**：发现正文件口是 `Embedded object:`、成片替换字符（`U+FFFD`）或
  明显非目标语言的碎片，说明抽取没成功，按上表"抽取工具失败"处理。

## 输出要求（所有审查类型一致）

先用对话消息给出整体判断（结论、问题条数、按严重度分组的一句话摘要），再由**结构化结果**承载明细。

每条问题必须包含：

| 字段 | 要求 |
| --- | --- |
| `severity` | `error`（必须修改）/ `warning`（建议修改）/ `info`（提示） |
| `ruleCode` | 本条依据的规则标识（如 `TYPO-001`、`STD-ABOLISHED`），不适用时写类型名 |
| `originalText` | **原文片段**——一字不改地抄回，用于定位与复核；缺失这一项的问题条视为无效 |
| `suggestion` | 建议改成什么；无法给出时写明"需人工确认" |
| `description` | 一句话说明为什么是问题（引规则/标准/条款） |
| `location` | 行号或章节号；有字符偏移时一并给出（`startOffset`/`endOffset`） |
| `anchor` | 供「点击问题 → 原文高亮」使用的定位（文件名 + 上述偏移；无偏移时给 `quote`） |

严重度口径（**不要全报 error**）：

- `error`：事实错误、引用已废止标准、违反强制性条文、数据矛盾——不改会出事。
- `warning`：规范/习惯问题、表述不严谨、可能引起歧义的措辞。
- `info`：可读性建议、可选优化。

**禁止**：把"未发现问题"写成结论却省略检查范围；把猜测写成结论；报出问题却不给原文片段。
