# 基础校对

## 何时用

用户要给一份文件做**文字层面**的检查，不涉及技术内容对错。设计说明、设备材料表、函件、报告都适用。

## 步骤

1. **先拿白名单**：调用 `KnowledgeCheck`（`action=terminology`）——把候选词传进去，**命中的必须丢弃**。
   白名单装的是核安全/设备/工艺/建筑/电气专业词，误报专业词是这类审查最大的噪音来源。
   若结果里的 `notice` 提示「白名单对本文档几乎无覆盖」，说明它没装本文档所属领域
   （如消防/给排水）的专业词：**不要把 `remaining` 当成错别字上报**，先向用户说明这个边界。
2. **确定性错别字**：逐条比 `references/typo-dictionary.md`（见该文件用法，同一错词最多报 3 处）。
3. **标点与排版**：比 `references/punctuation-rules.md`（全半角、顿号/逗号、括号、单位符号、中英混排空格）。
4. **量词与单位**：`台/套/个/根/米`与单位符号的误用（如 `KW`→`kW`、`Mpa`→`MPa`、`立方米`与`m³`混用）。
5. **编号与称谓一致性**：同一实体在全文中的叫法是否统一（如「循环水泵」与「循环水升压泵」混用要报 `warning`）。
6. 汇总：总数、按类别、按严重度。

## 不要做

- 不要改技术结论、不要判安全与否——那是别的审查类型的范围，越界会给用户错误的安全感。
- 不要把格式偏好（如"这里应该换行"）报成 `error`。

## 输出要求（所有审查类型一致）

先用对话消息给出整体判断（结论、问题条数、按严重度分组的一句话摘要），明细**必须调用
`ReportReviewIssues` 工具**落成结构化结果 —— 不要自己在回复里手写 JSON：

```
ReportReviewIssues({
  text: "<提取出的正文>"            // 长文档改用 textFile: "<抽取文本的绝对路径>"
  sourcePath: "<被审文件路径>",
  issues: [{
    severity: "error" | "warning" | "info",
    ruleCode: "标点-001",          // 规则标识：<中文类别>-<三位序号>。类别取 错别字/标点/语法/术语/量词/单位/编号/格式；不要用英文缩写——面板把这个标识直接显示给用户看
    originalText: "……",            // 原文片段，一字不改地抄回
    description: "为什么是问题",     // 引规则/标准/条款
    suggestion: "改成什么",          // 无法给出时写“需人工确认”
    location: "§5.2 表 5-1",        // 可选：给人看的章节/表格位置
    occurrence: 2                   // 可选：同一片段在正文出现多次时指定取第几次
  }]
})
```

**偏移由工具算，你不要自己填**：`startOffset`/`endOffset`/行号由工具在正文里查找 `originalText`
得出，用来支撑卡片上的「点击问题 → 原文高亮」。模型自己算的偏移是这条链路上最不可靠的一环——
会给出一串「看起来合法但错」的数字，而跳错位置比不跳更误导复核者。

几条硬要求：

- `originalText` **一字不改**地抄回（含标点与空格）。抄写时被输入法改了全角/半角或加了省略号，
  工具会退到归一化匹配并在结果里标注「位置按最近似处给出」；再找不到就返回 `located: false`，
  这类问题条**必须在回复里写明「无法定位」**，不要编造行号。
- 同一片段在正文里出现多次时，用 `occurrence` 指定第几次；不指定则取第一处，工具的 `notice`
  会告诉你有几条是这样处理的 —— 这类定位要在回复里说明「按首次出现定位」。
- 工具返回 `unlocated > 0` 或 `notice` 提到归一化匹配时，回复里必须如实转述，不要隐去。

严重度口径（**不要全报 error**）：

- `error`：事实错误、引用已废止标准、违反强制性条文、数据矛盾——不改会出事。
- `warning`：规范/习惯问题、表述不严谨、可能引起歧义的措辞。
- `info`：可读性建议、可选优化。

**禁止**：把"未发现问题"写成结论却省略检查范围；把猜测写成结论；报出问题却不给原文片段；
不调工具而在正文里手写一段 JSON 冒充结构化结果。
