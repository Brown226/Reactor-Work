# 批量审查

## 步骤

1. **先列清单并确认范围**。把要审的文件列出来（含路径）给用户确认；范围不明的先问，不要自己扩大或缩小。
2. **逐个处理，一份文件一轮**：
   - `parse_document`（或 `ocr_scan` / `parse_dwg`，按文件类型选）抽成 markdown；
   - 对文本跑对应的审查（`review-proofread` / `review-consistency` / `review-standard-check` 等）；
   - 每份文件**单独**保留它的结论，不要在处理中途就把结论"揉"成一个池子——合并后无法回溯是哪份文件的问题。
3. **扇出方式按数量选**（这是本技能唯一的性能判断）：
   - ≤3 个文件：顺序处理即可，不要为它起工作流。
   - \>3 个文件：用 `CreateWorkflow` 按文件扇出子代理，每个子代理只负责一份文件的抽取 + 审查，
     返回结构化的 `{file, issues[]}`；主流程只负责汇总与出报告。理由：单份文件的审查会读进去
     大量正文，串行做容易把上下文吃满，且一份失败会拖住整批。
4. **合并报告**：调用 `ExportReviewReport`，一次生成一份总报告：
   - `title` 写批次名（如「XX 项目设计说明批量审查」）；
   - `scope` 必须写清楚**审了几份、什么类型、没审什么**（如「12 份 docx 正文；未含 dwg 图纸」）；
   - `issues` 里每条用 `location` 带上文件名（如「HX1CI0842.docx §5.2」），否则报告里分不清是哪份文件；
   - 用户要明细表就再导一份 `.xlsx`。

## 纪律

- **不要漏报"没审成的"**：某份文件抽取失败（扫描件、格式不支持）时，必须写进 `scope` 与结论里，
  不能让它在报告里静默消失——那会让读者以为"这批都干净"。
- 报告结尾保留工具自带的那句"供复核参考"；批量报告更要如此，它不是终稿。
- 不要把不同文件之间**真实存在**的矛盾当成单文件问题：跨文件不一致属于"以文审文"，要单独说明
  基准与偏差方向。
