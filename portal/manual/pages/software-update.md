# 软件包分发与自动更新

Reactor 面向内网交付，**不提供公网下载页**。交付物有三类：桌面端安装包、命令行 / Web 发行包，以及桌面端的**自动更新**。本页说明它们分别怎么产生、在内网怎么获取、自动更新走什么链路，以及客户端看到的更新说明与版本日志从哪来。

构建命令的完整参数见[安装与部署](install.md)；服务端更新模块的职责与部署见[服务端总览与接线](server-overview.md)。

## 1. 三类交付物

| 交付物 | 构建命令 | 产物 | 说明 |
| --- | --- | --- | --- |
| 桌面端安装包 | `pnpm bundle:desktop` | `Reactor-<版本>-<平台>-<架构>.<安装格式>` | Windows 为 NSIS 安装程序，macOS 为 `dmg` / `zip`，Linux 为 `AppImage` / `deb` / `rpm` 等 |
| 命令行 / Web 发行包 | `pnpm build:zcode` | `dist/zcode/` 下的运行包与安装脚本 | 含 TUI、Web 与 Agent，产物结构见[安装与部署](install.md) |
| 单文件命令行 | `pnpm build:sea` | 单文件可执行程序 | 免 Node 依赖的命令行形态，构建后上传到内网共享目录分发 |

产物的版本号默认取仓库根 `package.json` 的 `version`；桌面端安装包会把该版本写入应用元数据。

## 2. 内网获取方式

三类交付物的获取路径不同：

- **桌面端安装包**：登记在服务端的「软件更新」模块，由管理台上传与发布（见第 5 节）。**还没装的人**在内网浏览器打开服务端的**下载页**即可看到各平台最新版本并直接下载；**已装的人**走自动更新拉取（见第 3 节）。两者读的是同一份发布记录，管理员上线一次，两边同时生效。
- **命令行 / Web 发行包**：把 `pnpm build:zcode` 的整个输出目录上传到**内网可访问的托管地址**，安装脚本从该地址的 `latest.json` 读取版本与摘要，再下载对应运行包并校验。托管地址由 `ZCODE_DIST_BASE_URL` 指定（也可用 `--base-url` 传入），**必须指向内网**。
- **单文件命令行**：构建后上传到内网共享目录，用户直接取用。

> **提示**：本说明书不记录任何具体的内网地址——托管地址与共享路径由部署方按实际环境配置。

### 2.1 用户怎么拿到桌面端安装包

**还没装客户端的人**在内网浏览器打开：

```text
http://<服务端地址>/download
```

这是服务端**带的一个公开下载页**（无需登录，页面本身不依赖任何外部资源）：列出各平台 / 通道的最新已发布版本、文件名、大小与发布说明，点「下载」即从服务端取安装包。它读的就是管理员在管理台上线的那份登记，**管理员上线一次，下载页与已装客户端的自动更新同时看到该版本**。

产品门户（官网）首页的「下载 Reactor」按钮也指向同一下载页：门户配置里把 `/download` 转发到服务端，因此从官网点一下就能直接下载，无需先记住服务端地址。该转发由部署方按环境配置（见门户目录的 `nginx.conf`）。

页面只列出**已上线且带产物**的版本；下线的版本会立即从列表消失。新增平台的支持、镜像加速等不在该页范围内，由部署方按需处理。

面向的三种人对照如下：

| 情况 | 怎么拿到 / 更新 |
| --- | --- |
| 还没装（新用户） | 打开 `/download` 下载对应平台安装包 |
| 已装，想更新 | 客户端自动检查（菜单「帮助 → 检查更新」），走第 3 节的更新清单 |
| 要命令行 / Web 发行包 | 不经此页，从内网托管地址获取（见上一节） |

## 3. 桌面端自动更新

桌面端用 `electron-updater` 做自动更新，但**更新源不是通用静态源，而是服务端下发的一份更新清单**。它由客户端侧一个自建的更新清单 Provider 承载，取代了默认的静态文件源。

### 3.1 更新清单

客户端向服务端请求更新清单：

```text
GET /api/v1/releases/electron/manifest?platform=<平台>&channel=<通道>&device_mid=<设备标识>
```

| 参数 | 说明 |
| --- | --- |
| `platform` | Electron 口径的平台串，如 `windows-x64`、`darwin-arm64`、`linux-x64` |
| `channel` | 发布通道，`1` 为稳定通道、`3` 为预览通道 |
| `device_mid` | 设备标识，用于灰度分桶（见第 3.3 节） |

清单返回该平台 / 通道下**最新已发布**的版本、发布说明与产物列表；没有已发布版本时**如实返回不存在**，不会伪造一个"当前版本"来掩盖管理台没配好的事实。

客户端拉取清单的**端点地址由构建时注入的产品端点地址决定**（可用环境变量覆盖）。内网部署时应把它指向内网服务端，使**更新检查与产物下载都不出内网**。

### 3.2 产物下载

清单里的产物 URL 指向服务端的文件接口：

```text
GET /api/v1/releases/electron/files/<文件标识>
```

该接口支持**单段 Range 断点续传**，并回带 sha512 校验和（base64）。客户端据此校验产物完整性后再安装；地址只接受服务端登记过的文件标识，路径穿越无从下手。

### 3.3 通道与灰度

| 项 | 说明 |
| --- | --- |
| 通道 | **稳定**与**预览**两条；用户可在设置里选择是否接收预览更新 |
| 灰度 | 每次发布可设投放百分比；客户端带设备标识参与分桶，**同一设备对同一发布的分桶结果稳定**，不会在"有 / 无"之间跳 |
| 无设备标识的客户端 | 旧版或命令行客户端不带设备标识，**不参与灰度，直接给全量**，避免它们永远收不到更新 |

### 3.4 检查与安装

| 项 | 说明 |
| --- | --- |
| 手动检查 | 菜单栏 **帮助 → 检查更新** |
| 后台检查 | 按固定间隔自动检查一次 |
| 安装方式 | 下载完成后按配置静默安装，或提示用户重启后安装 |

## 4. 更新说明与版本日志的来源

这是更新链路里容易被忽略的一环：**客户端更新提示里的发布说明，来自服务端。**

| 层 | 内容 | 谁维护 |
| --- | --- | --- |
| 服务端发布记录 | 版本号、发布名、中文 / 英文发布说明、投放百分比、发布时间与发布人 | 管理台发版时填写，存在服务端发布表 |
| 客户端更新提示 | 从更新清单同步发布说明，按界面语言在中文 / 英文之间回退 | 随更新清单自动下发 |
| 官网更新日志 | v1.0.0 基线条目静态维护；**基线之后由服务端同步** | 管理台发版时填写的发布说明 |

也就是说：**客户端更新提示与官网更新日志，读的是同一份服务端发布说明**。发版时在管理台一次填好，两处同时生效。

官网更新日志页从服务端的公开接口拉取已发布版本：

```text
GET /api/v1/releases/changelog?limit=<条数>
```

按**版本号去重**（同一版本发到多个平台只显示一条）、按上线时间倒序，只回已上线且写了更新说明的条目，不外传 `stored_name` / `sha512` 等内部寻址字段。页面用渐进增强方式加载：**取不到（门户未配反代、服务端离线、库内暂无记录）时静默保留 v1.0.0 静态基线**，不影响页面可用性。

## 5. 发版流程（管理台）

服务端的软件更新模块把"发版"拆成两步，避免几百 MB 的产物经过内存：

1. **建草稿**：在管理台「软件更新」填写平台、通道、版本号、发布名与中英文说明。
2. **上传产物**：以原始字节流上传安装包，**边写盘边计算 sha512**；上传中断不会留下看似可用的产物。产物类型必须在允许列表内（`exe` / `msi` / `zip` / `dmg` / `pkg` / `AppImage` / `deb` / `rpm` / `pacman` 等），否则上传时即拒绝——避免传到线上才发现客户端识别不了。
3. **上线 / 灰度**：产物就绪后才能上线，可设投放百分比；之后可随时调整或下线。

产物存放在服务端的更新文件目录（容器部署时挂独立数据卷），**不进数据库**；数据库只存登记信息。管理面的增删改都会记入管理审计。

## 6. 自动更新的边界

| 项 | 说明 |
| --- | --- |
| 更新源 | **只认**服务端下发的更新清单，产品内不提供第二个更新地址入口 |
| 失败语义 | 检查失败只提示，不影响应用使用；产物校验不通过会重新下载 |
| 产物与记录一致性 | 数据库有记录、磁盘无文件时，下载接口如实报"产物缺失"，提示检查数据卷 |

## 7. 强制升级门（当前关闭）

产品里有一套**「低于最低可用版本必须先升级」**的启动门：启动时读取服务端下发的**最低可用版本**，若当前版本低于它，**阻止进入主界面**并要求先升级。

> **如实说明**：该门**当前以开关关闭，尚未生效**。原因是它的最低版本配置原读自产品端点的客户端配置通道，而该通道下发的仍是**旧产品线**的版本号；Reactor 的版本号从 `1.0.0` 重新起算，按版本比较会把新版本**误判为过旧**、启动即被挡住。内网服务端的策略通道目前**尚未下发**该字段，没有可替代的权威来源。
>
> 重新启用的条件是：服务端开始下发最低可用版本，且把配置来源切到内网服务端策略通道。在此之前，**不要指望强制升级门拦人**。
