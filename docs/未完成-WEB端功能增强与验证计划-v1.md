# Web 端功能增强与验证计划

> 状态：待实施。本文汇总 Win7/Web 推广路线的既有结论、已完成的验证、待补缺口与验收口径，
> 作为后续所有 Web 端改动的总纲。平台指标看板另见 `未完成-管理端双平台运营看板-方案-v1.md`。

## 1. 背景与定位

公司内仍有大量 Win7 电脑，其可用浏览器最高为 Chromium 109（Chrome/Edge 109 是最后一个支持
Win7 的版本）。因此 Web 端不是桌面端的附属，而是一条**独立的正式入口**：

| 入口 | 人群 | 形态 |
| --- | --- | --- |
| 桌面客户端 | Win10 1809+ / Win11 | Electron 41，全功能，agent 跑在本机 |
| **Web 客户端** | Win7（Chrome 109）与无客户端环境 | 浏览器访问，agent 跑在服务器 |

关键认知（避免重复踩坑）：

- web 与桌面**共用同一套前端**（`@zcode/ui` 的 `Root`），差异只在入口装配与平台适配层。
  因此**共享层改动会同时影响两端**，兼容处理只允许落在 web 构建配置与 web 入口。
- web 不是"桌面端的远程画面"：`packages/web` → `packages/server` → 服务器进程 fork agent，
  **工作区是服务器磁盘**，用户跑的命令、改的文件都在服务器上。
- `reactor-web` 镜像是**自包含的运行时**（前端 + 服务端 + agent 全在里面），但**不是完整系统**：
  依赖 identity（登录）与 gateway（模型），缺任一条都表现为"用不了"。

## 3. 能力边界（功能级，不含场景）

### 3.1 等效（行为一致）

对话与流式、中断/重试、任务与会话管理、权限确认、工作流；agent 全部工具（读写文件、搜索、
执行命令、编辑代码）；工作区与文件树、文件搜索、文件预览（代码/Markdown/PDF/Office/图片）、
Diff 与审查、Git、终端；技能与插件市场、MCP 读取启用；主题/语言/字号、企业登录与账号切换、
会话分享、浏览器通知。

### 3.2 等效但机制不同（用户结果一致）

| 功能 | 桌面端 | Web 端 |
| --- | --- | --- |
| 附件 | 零上传直读本机路径 | 分片上传（单次 ≤ 8 个） |
| 工作区 | 本机任意目录 | 服务器目录 |
| 终端 | 本机 shell | 服务器 shell |
| 更新 | 自动更新 | 刷新即最新 |
| 凭据 | OS 钥匙串 | 服务端派生密钥 |

### 3.3 不可实现（浏览器/架构决定）

本机任意目录作为工作区、系统文件管理器显示、外部编辑器打开、内嵌浏览器、网页元素标注与截图、
浏览器自动化（当前）、CUA、Chrome 数据导入、OS 钥匙串、自动更新与回滚、托盘与任务栏徽标、
关闭到托盘、全局快捷键、原生标题栏、独立窗口、开机自启、文件关联与右键菜单、导出日志到本地、
窗口截图、离线使用、本地图片壁纸、USB/串口、本机文件零上传。

> 其中「努力可做」的子集：导出日志（Blob 下载）、本地壁纸（file input + IndexedDB）、
> 徽标/独立窗口/文件关联（PWA 化）、屏幕截图（`getDisplayMedia`）、串口（Web Serial）、
> 任务栏徽标（`setAppBadge`）、浏览器自动化（容器内 headless Chromium）。
> **这些 API 绝大多数要求 HTTPS**，未上证书前一律不可用。

## 4. 待补缺口（按优先级）

| 优先 | 缺口 | 现状 | 目标 |
| --- | --- | --- | --- |
| P0 | DWG 解析在 Linux 不可用 | `dwg-tools-plugin` 只有 `assets/win32-x64` 的 .NET sidecar，代码 RID 映射含 `linux-x64` | 构建机 `dotnet publish -r linux-x64`，产物进资产树与镜像 |
| P0 | 每用户工作区与配额 | 单工作区 `/data/workspace`，用户互相可见 | 总 20GB / 每用户 1GB；`/data/users/<uid>/` + 应用层配额 |
| P0 | HTTPS 与同源反代 | `http://host:3030`，跨源登录依赖 CORS | nginx 同源反代，解锁安全上下文类 API |
| P1 | 大文件上传落用户空间 | 附件进 artifact store，不占用户工作区 | 直传工作区 + 配额校验（图纸级几十 MB） |
| P1 | 办公四件套生成验证 | 容器内未验证库与中文字体 | 实测 docx/xlsx/pptx/pdf 生成与中文渲染 |
| P2 | 不可用功能置灰 | 入口可点但静默失败 | 置灰 + 悬停「该功能仅支持客户端使用」 |
| P2 | 服务端访问控制 | 未配 `ZCODE_SERVER_AUTH_TOKEN` 时 `/ws` 全开 | 默认强制令牌，或接入登录身份 |

## 5. 验证方法（每个 Web 改动都要过）

**构建期**：`pnpm --filter @zcode/web build` 后检查产物 CSS 无裸 `oklch`、JS 无 Chrome 110+ API
（当前仅 `toSorted`，已垫片）。

**真机回归**：用 Playwright 拉取的 `chromium-1040`（Chromium 109.0.5414.46）跑：
1. 打开页面，`pageerror` / `console.error` 必须为空；
2. 不出现错误边界「这块界面出了点问题」；
3. 与当前 Chrome 同页对比，差异仅限字形抗锯齿与广色域（阈值参考 1.5%）。

**桌面端不可回归**：任何改动若触及 `packages/ui` / `packages/shared`，必须同时验证桌面端渲染未变。

## 6. 验收清单

- [ ] Chromium 109 与当前 Chrome 均无报错、无错误边界
- [ ] 桌面端构建产物渲染与改动前一致
- [ ] `pnpm typecheck` / `pnpm lint` / `pnpm architecture:check --changed` 通过
- [ ] 置灰项在 web 端不可点击且悬停有说明，桌面端行为不变
- [ ] 登录链路（含 CORS/反代）在目标部署形态下实测通过
