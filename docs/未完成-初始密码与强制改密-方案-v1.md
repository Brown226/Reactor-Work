## 1. 背景与问题

大王提出的原始诉求（2026-10-14）：

1. 域账号一时接不通，也要保证现有系统可用（**两重保障**）；
2. 当前库里用户的密码统一改为 `用户名@123`；
3. 管理台用户管理支持重置密码，规则同样是 `用户名@123`；
4. 客户端「设置 → 账号」支持用户自己改密码；
5. 客户端检测到首次登录后**强制**修改初始密码；
6. 新密码强度：大写 + 小写 + 数字 + 特殊符号。

## 2. 关键事实核查（动手前实测）

| 项 | 实测结果 |
| --- | --- |
| `users` 表 source 分布 | `ad/active` **807**、`local/active` 3、`local/disabled` 1 |
| 有 `password_hash` 的用户数 | **4**（仅 local） |
| `auth.ts` 登录分支 | `source=local` → bcrypt 校验；`source=ad` → **走 LDAP bind，不读 PG 密码** |
| `sync.ts:54` 同步规则 | `existing.source === "local"` → **直接跳过**（注释「平台本地号，uid 撞名，跳过」） |

**由此得出的决定性结论**：那 807 个 `source=ad` 的用户，密码在 LDAP 里，平台**读不到也改不了**。
直接给他们写 `用户名@123` 的哈希是**无效功能**——登录时代码根本不看那个字段。

## 3. 方案选择

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| A（选定） | 807 个 ad 用户转为 `local`，密码设 `用户名@123`，置 `must_change_password` | 六条需求全生效 |
| B | 只改 local 的 3 人 | 807 员工仍走 LDAP 123456，改密功能对 90% 的人是摆设 |
| C | 等接真实 AD 后再改 | AD 密码归域管，平台无权改，永远做不到 |

**A 的关健收益**：`sync.ts` 对 `local` 用户是「跳过」而非「停用」，所以将来接入真实 AD 后：

- 这 807 人**不会被判为「AD 缺失」而停用**（不会出现全员登录不了）；
- 他们的姓名/部门也不再被 AD 覆盖（代价，见 §7）。

**代价（已向大王明示）**：转为 local 后，这些人的姓名/部门不随 AD 自动更新。

## 4. 数据模型

`users` 表新增一列（`identity/db.ts`）：

```sql
must_change_password BOOLEAN NOT NULL DEFAULT false
```

- `ensureSchema` 里同时保留一条幂等 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`：
  `CREATE TABLE IF NOT EXISTS` **不会给已存在的表加列**，而生产库早于该字段存在。
- 语义：`true` = 该账号必须修改初始密码才能继续使用（初始密码 / 管理员重置均置位）。

## 5. 服务端

### 5.1 密码强度（`identity/passwords.ts`）

```ts
validatePasswordStrength(pwd): string | null   // null=通过；否则返回人类可读原因
```

规则：≥8 位，且同时含大写、小写、数字、特殊符号。
**四条都要**——只要求"其中几种"的弱规则在内网字典攻击下形同虚设。

### 5.2 三个接口（`identity/routes.ts`）

| 方法 | 路径 | 用途 | 要点 |
| --- | --- | --- | --- |
| POST | `/auth/change-password` | 自助改密 | 必须校验**原密码**；`source=ad` 明确拒绝并指路；过强度关后才清 `must_change_password` |
| POST | `/users/:id/reset-password` | 管理员重置 | 规则**固定** `<uid>@123`，服务端自行计算，**不接受前端传口令** |
| PATCH | `/users/:id`（既有） | 改资料 | 带 `password` 时同样过强度关并置 `mustChangePassword` |

**为什么重置单独一个路由而不复用 PATCH 的 `password`**：PATCH 允许传任意口令，
而"重置"的语义是「回到可预期的初始值 + 强制下次改密」。单独路由让规则只存在于服务端一处，
前端没有覆盖能力，也不会出现"重置成了另一个弱口令"。

### 5.3 登录下发

`toPublicUser` 增加 `mustChangePassword`，登录/刷新/`/me` 三条路径自动带上。
契约同步：`server/packages/shared/src/identity.ts`、`server/packages/admin/src/types.ts`。

## 6. 客户端（桌面端）

### 6.1 契约与 service

- `ReactorServerUserInfo` 加 `mustChangePassword: boolean`；
- `toUserInfo` 与 `readUser` **都做 `?? false` 兜底**——本机可能存着升级前写入的旧 user JSON，
  没有该字段；不兜底会让 UI 收到 `undefined`（条件判断里与 false 等价，但类型上骗过契约）；
- `IReactorServerService.changePassword(old, new)`：成功后**立即落盘 user**。
  不同步的话，强制改密弹窗会继续挡着界面，用户只能靠重新登录才消失。

### 6.2 阻断式改密弹窗（`ForcePasswordChangeDialog.tsx`）

挂在 `Root.tsx`（不是设置页内）——用户可能从头到尾不进设置页，门禁必须覆盖整个应用。

**为什么自绘而不用通用 Dialog**：必须同时禁掉 ESC、点遮罩、关闭按钮三条退出路径，
而通用 Dialog 的 `onOpenChange` 语义是"用户可取消"，与需求正好相反。

**为什么必须阻断式**：初始密码是 `用户名@123` 这种可预测值（同事知道账号就能算出密码），
留着它等于账号半公开。提示条/横幅会被用户习惯性点掉，实测拦不住人。

### 6.3 设置页自助改密（`AccountProfilePanel.tsx` 内 `ChangePasswordCard`）

与弹窗共用 `passwordStrength.ts`（五条规则 + `isStrongPassword` + `firstFailedPasswordRule`），
避免三处规则漂移。客户端先拦一道只为少一次无效请求，**服务端仍是权威判据**。

## 7. 与 AD 接入的关系

| 场景 | 行为 |
| --- | --- |
| AD 未接 / 接不通 | 807 人用 `用户名@123` 登录（本地 bcrypt），**系统完全可用** |
| AD 接好后跑组织同步 | 这 807 人因 `source=local` 被**跳过**——不停用、不覆盖 |
| AD 里的新员工 | 同步进来为 `source=ad`，走 LDAP bind，密码归域管 |
| `REACTOR_AUTH_MODE=local` 时 | local 账号不可用（`auth.ts:151`）——**不要切到这个模式** |
| `REACTOR_AUTH_MODE=mixed`（当前） | local 与 ad 并存，即两重保障 |

## 8. 运维脚本

`server/packages/server/scripts/convert-ad-users-to-local.mjs`

- **默认 dry-run**，必须显式 `--apply` 才写库（动 807 个账号的生产操作）；
- 只转 `source=ad AND status=active`；disabled 的保持原状；
- 保留 `ad_dn` 不清空（将来接 AD 仍可按 DN 追溯）；
- 幂等可重跑；结尾自校「local 用户是否都有密码哈希」，缺哈希即报错退出。

**执行顺序有硬依赖**（顺序错了会把用户卡死）：

```
① 重建 identity 镜像（新接口上线）
② 执行账号转换（--apply）
③ 打桌面安装包（改密弹窗 + 设置页表单）
```

若先做 ② 不做 ①：用户被要求改密但服务端没有改密入口 → **卡死**。
