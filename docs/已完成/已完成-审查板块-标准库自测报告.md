# 标准库 · 标准引用自检实测报告

> 2026-09-22。用 `docs/审查板块原始数据/标准库测试文档/` 里的**真实设计文件**跑了一遍
> 「标准引用自检」，验证三件事：消费面取数是否通、机械匹配判定是否可用、**库里的数据够不够判**。
> 结论：链路通、判定可用；**库存在一处成体系的误删（已修）**，行业标准整体缺失（源数据即缺），
> 图纸类文件拿不到文本层。

## 1. 被测对象与输入

| 项 | 内容 |
| --- | --- |
| 库 | 管理端标准清单，实测时 13,445 条（起始 13,368，见 §5 补充导入 77 条） |
| 取数路径 | `GET /v1/standards/index`（Bearer，消费面只读索引，即 M3c 端侧要用的那条） |
| 判定逻辑 | 确定性机械匹配（无 LLM）：归一化 → 编号拆 `(标识符, 数字, 年代号, 版本标注)` → 四级索引命中 |
| 被测文档 | 同目录 6 个真实文件（4 个 CNPE 设计文件 + 1 个图纸 + 1 份使用说明） |

取数实测：`HTTP 200 / 199–238ms / 13,445 条 / Last-Modified` 正常下发，`items` 与 `maxUpdatedAt` 齐备。

## 2. 文档可解析性（**这是第一个结论**）

| 文件 | 类型 | 能否抽到引用 | 说明 |
| --- | --- | --- | --- |
| `HX1CI084200…(15251CI-JPS502).docx` | 消防给排水设计说明 | ✅ 14 条 | python-docx（含 6 张表） |
| `HX1CI010300…(15251CI-JPS103).xlsx` | 废水系统设备材料表 | ✅ 12 条 | openpyxl |
| `2.pdf` | 循环水处理系统工艺设计说明（**图纸**） | ❌ **0 条** | 全页只有标题栏约 581 字符可抽；图面文字为矢量/曲线，`pdftotext` 拿不到 |
| `FZ9HX011101…(15169HX-JPS01-001).dwg` | 图纸 | ❌ 未解析 | DWG 需 CAD 解析或 OCR，本期无能力 |
| `河北分公司大数据人工智能…pptx` | 汇报演示 | — | 非设计文件，未纳入（pptx 文本可解析） |
| `设计文件规范引用自查工具使用说明.pdf` | 规则来源 | — | 抽出被测工具的功能与校验口径，见 §3 |

**要点：图纸类文件（PDF 图纸 / DWG）必须给出显式提示。** 本次 `2.pdf` 抽不到任何引用，
如果工具对它「静默无结论」，会被读成「这份图纸没问题」——比报不出问题更危险。
这是 M3c 的必做项：**无法自检的文件要明说无法自检**。

## 3. 判定口径（四类，来自工具使用说明 + 实际需要）

| 判定 | 含义 | 本轮命中 |
| --- | --- | --- |
| 通过 | 库中该编号该年代号为现行/即将实施 | 17 |
| **已废止引用** | 该编号该年代号已废止 —— 最常见、也最有价值的缺陷 | 1 |
| **未注年代号** | 只写编号不写年代号（引用规范要求注年代号） | 2 |
| **未收录** | 库中没有该编号（库待补，或非标准编号 / 笔误） | 6 |

归一化是这套东西的全部难点，实测必须处理：全角字符、`— – ～ ∕` 破折号变体、编号内空格
（库里有 `GB/T 12459-2017`、`GB/T8163-1999`、`GB12238-89` 三种写法并存）、两位年号（`-89` → 1989）
以及**版本标注**。

> **版本标注必须参与匹配。** 实测教训：文档写 `GB50016-2014（2018年版）`，若把尾注吃掉，
> 会被判成「引用了 GB 50016-2014（已废止）」——而它引的其实是现行的 2018 年版。
> 这是**误报**，比漏报更容易让用户失去信任。

## 5. 发现并已修复：分类白名单误删（**本次最重要的发现**）

### 现象

自检把 `GB 50222-2017 建筑内部装修设计防火规范`（**现行，且被 JPS502 设计说明真实引用**）
和 `GB 55037-2022 建筑防火通用规范`（**全文强制国标**）判成「未收录」。

### 定位

逐行对比原始 36,985 与现库：**「未收录」不是源数据缺失，是本库自己删掉了**。
`方案-v1.md` §4.4.1 的第 ② 轮（按核电设计院相关性白名单，−15,262 条）是按
**14 个专业分类白名单**筛的，分类器把一批**建筑/消防类现行国标分到了白名单外的桶**
（建筑、装修、市政等），于是被整批丢弃。

按「名称强命中给排水/消防领域词 且 不含无关领域词」反推，**误删 93 条**（其中现行 53 条），
包括 `GB 50016-2014(2018年版)`（建筑设计防火规范）、`GB 50116-2013`（火灾自动报警系统设计规范）、
`GB 3445-2018`（室内消火栓）、`GB 4452-2011`（室外消火栓）、`GB 12955/14102/16809`（防火门/卷帘/窗）
等 —— 对给排水与消防专业是**主力标准**。

### 处理

按同一口径生成补充批次，**剔除用户已明确排除的 `GJB` 军事类 16 条**，
补入 **77 条**（现行 38 / 即将实施 2 / 废止 37），经管理面 `/admin/standards/import` 导入：
`{"received":77,"inserted":77,"skipped":0}`，库 **13,368 → 13,445**
（现行 7,068 / 废止 6,248 / 即将实施 129，分类 `暖通/给排水/消防` 398 → 475）。

> 补入的废止旧版本（37 条）同样必要：自检的核心价值之一是判「你引用的这条已废止」，
> 库里没有旧版就只能报「未收录」，判定价值反而下降。

### 复测

- `GB 50222-2017`、`GB 55037-2022` → **转为通过**（误报消除）。
- 并**额外暴露出一条原先不可见的问题**：库中同时有了 `GB 50016-2014`（已废止）与
  `GB 50016-2014(2018年版)`（现行），文档引用的版本标注终于能被区分（见 §3 版本标注）。

## 7. 能力缺口（不是数据问题，需排期）

1. **图纸类文件**：PDF 图纸与 DWG 拿不到文本层 → 需 OCR / CAD 解析。**在做到之前必须显式提示"无法自检"**（见 §2）。
2. **三类需要人确认的判定**：未注年代号、`GB` 与 `GB/T` 前缀混用、疑似笔误 —— 工具只能给候选，
   不能自动判错（§4.1 #4 就是例子）。
3. **`.tmp/` 里的匹配脚本未固化**：本轮自检用的抽取/匹配脚本是临时脚本，**脚本本身没进仓库**，
   M3c 需要把它落成受测的确定性工具（端侧 `SELF_CHECK`），并补单测覆盖
   （版本标注、两位年号、全角标点、破折号变体这几条必须有回归用例）。
4. **导入载荷的生成链未固化**：`xlsx → 导入 JSON` 是一次性脚本，仓库里没有。
   当前可复现路径记录在 §8。

## 8. 复现方式（本轮实际执行的命令）

```bash
# ① 取索引（消费面，Bearer）—— 也可用 admin/Admin@123 在 :8791 换 token
node .tmp/fetch-index.mjs          # → HTTP 200 / 13,445 条 / Last-Modified

# ② 抽文本
pdftotext -enc UTF-8 -layout "2.pdf" out.txt                      # 正文型 PDF
python -c "import docx; ..."                                      # python-docx（docx 段落 + 表格）
python -c "import openpyxl; ..."                                  # openpyxl（xlsx 全 sheet）

# ③ 抽取 + 匹配（确定性，无 LLM）
node .tmp/selfcheck.mjs <docx.txt> <xlsx.txt> <pdf.txt>
#    → 逐条输出：判定 / 命中的库记录 / 原文上下文与行号
```

**导入载荷转换口径**（与 `方案-v1.md` §4.4.1 的 8 列一一对应，状态码做规范化）：

```python
status = {"现行": "current", "废止": "abolished", "即将实施": "upcoming"}[row[0]]
# 列序：状态 / 标准编号 / 标准名称 / 发布日期 / 实施日期 / 废止日期 / 替换信息 / 归类
# 日期输出 YYYY-MM-DD 或 null；standardNo 与 standardName 去首尾空白
```

补充批次（77 条）载荷：`.tmp/standards-restore-fire.json`；
**本轮为修正 §5 误删而做，与全量导入载荷是两件事，不要用后者覆盖前者。**

## 9. 结论

1. **链路可用**：取数 200ms 级、判定可复现、问题能定位到文件与行号，且**零 LLM 依赖**。
2. **数据是当前瓶颈**，不是算法：一类误删已修（93 条中的 77 条），
   **行业标准缺失才是"能不能真用"的关键**（§4.2 的 5 条全属此类）。
3. **诚实边界**：图纸类无法自检、三类判定需人工确认 —— 这两点必须在 UI 上说出来，
   不能给出「检查完成，未发现问题」这种会误导的结论。
4. 本轮**未改动**任何端侧/管理台代码；除 §5 的数据补充外，仓库改动仅为
   `server/packages/server/scripts/updates-smoke.ts` 的既有缺陷修复（见下）。

## 附：顺手修复的既有缺陷（冒烟脚本的环境加载）

`smoke:updates` 长期「假绿」：脚本缺 `process.loadEnvFile`，而 `.env` 只在 `server/.env`
（不在 `packages/server/.env`），于是回落到硬编码的 `55432`（compose 映射在 `15432`）→
打印 `SKIP` 并以 0 退出，**探针实际上从未真正跑过**。补上 env 加载后又暴露第二个缺陷：
它直接装配路由（不起 identity 进程），但路由里的 `recordAdminAction → resolveActorForClaims`
要读 `users` 表，干净冒烟库上没有 → `42P01` 500。按 `feedback-smoke.ts` 的写法补
`ensureSchema` + `ensureAuditSchema` 后全部断言通过（建表幂等 / 鉴权 / 两步式上传 /
sha512 base64 口径 / Range 续传 / 灰度分桶 / 删除清产物）。

**同类缺陷共 6 个脚本**：`identity` / `skills` / `agents` / `org` / `e2e` 写的是**裸**
`process.loadEnvFile?.()`，取 cwd 的 `.env` —— 用它们自己的 npm script
（`pnpm --filter @reactor/server smoke:x`，cwd 变成 `packages/server`）跑必然连 `55432` 失败，
只有手工 `node <path>` 从 `server/` 根执行才行。已统一改为绝对路径形式，
与 `admin` / `t34` / `audit` / `gateway-auth` 保持一致。

**结果：11 个冒烟全部 PASS**（`identity` / `admin` / `skills` / `agents` / `org` / `t34` /
`gateway-auth` / `admin-static` / `audit` / `feedback` / `updates`）。
`smoke:e2e` 仍红：它引用仓库里不存在的 `packages/sidecar`（`server/packages/` 下只有
`admin` / `server` / `shared`），与本次改动无关。
