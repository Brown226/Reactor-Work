# 文件审查板块

「审查」是界面模式的第三档。你在草稿首页把胶囊切到审查模式，然后用大白话说一句「帮我审这份文件」：Agent 按你选的审查类型加载对应技能（判定规则 + 提示词），必要时对照本地知识库，把问题逐条定位到原文并高亮，最后在对话里给出结论、并在正文下方挂出一张统一的审查结果面板。

这一页说明审查板块的**审查类型、结果形态、知识来源**，以及最重要的一件事——**哪些能力已经落地，哪些还没有**。

依据：`docs/未完成-审查板块-方案-v1.md`（方案与落地边界）、`docs/已完成/已完成-审查板块-标准库自测报告.md`（实测结论）、`docs/未完成-审查板块-流程问题清单-v1.md`（流程问题与已修项）。

> **本页的性质**：审查板块是**进行中**能力。下面每一项都标了状态，请按状态理解，不要把未落地项当成可用功能。

> **相关页面**：审查档位本身（取值、入口、收敛判据）见[界面模式](interface-modes.md)；审查技能随包内置，技能体系见[技能](skill.md)。

## 定位：审查 ≈ 办公模式的专项分支

审查不需要新的后端服务、不需要队列、也不需要移植原有的核审通代码。它与办公模式的差别只有两点：

1. **专项化的知识**：调用哪个知识库/标准库 + 挂哪个审查技能。
2. **专项化的结果形态**：问题清单要能点击定位到原文。

其余（会话、上传、预览、文件读写、报告导出）全部复用 Reactor 已有能力。因此所有审查类型都是同一个骨架：**Agent + 指定技能/提示词 + 可选知识库对照**。

## 审查类型（5 类）

草稿首页在审查档下展示**审查类型卡片**，点击即把提示词预填进输入框（不自动发送）。每张卡片与一个内置技能**硬绑定**：提示词正文以技能引用开头，运行时由技能工具加载，判定规则与输出格式都住在技能文件里。

| 卡片 | 技能 | 知识来源 |
| --- | --- | --- |
| 基础校对 | `review-proofread`（含错词表与标点规则附件） | 无（可参考术语白名单） |
| 全文一致性 | `review-consistency` | 无 |
| 以文审文 | `review-compare` | 参照文件（你上传） |
| 合同风险审查 | `review-contract` | 可选法务库 |
| 标准引用自检 | `review-standard-check` | **标准库**（管理员端维护） |

三条使用约定：

- 卡片是**菜单，不是推荐池**：固定显示全部 5 类，不受办公档「主动推荐」开关影响，也**没有「换一批」**。
- 点卡片只是**预填提示词**，你可以再补一句或直接发送。
- **「以库审文」不在卡片里**：它依赖的企业知识库本期不做（见下文「未落地」），不设「点了没反应」的死入口。

### 已裁剪的审查类型

| 原类型 | 处置 | 理由 |
| --- | --- | --- |
| 仅规则审查 | **删除，不实现** | 纯规则引擎不调模型的阶段产物，价值已被「技能固化判定规则 + 标准引用自检的机械匹配」覆盖 |
| DEC 规范审查 | **删除，不实现** | 与原「以库审文」重复，落地为同一套「Agent + 知识库」即可 |
| 图纸视觉 | **不在本板块范围** | 需要视觉模型 + 图元解析，另案 |

## 结果形态：对话为主 + 一个统一面板

### 对话消息

Agent 在对话里流式给出结论：整体判断、问题条数、按严重度分组摘要、以及建议。这就是普通对话输出，没有新增机制。

### 结构化结果面板

审查结论用**结构化输出**承载，渲染成一轮对话里的**一个统一面板**，挂在最终正文的下方、底部操作栏之上：

```text
用户提问
已处理 12 秒                       ← 工作过程（默认收起，过程不是产物）
  └─ 工具行：解析文档 / 审查问题清单 / 标准引用自检（只留一行摘要）
模型最终总结正文                    ← 正文照常流式
┌ 审查结果 ───────────────────────────────────────────────┐
│ 共 67 条问题 · 必须修改 12 · 建议修改 40 · 提示 15        │
│ ▾ 说明书.docx  23 条                                      │
│     标点 · 5 条                        第 12 行「…」建议… │
│     一致性 · 4 条                                         │
│ ▸ 接口需求规格书.docx  18 条                              │
└──────────────────────────────────────────────────────────┘
底部操作栏（复制 / 点赞 / fork）
```

四条硬约束：

1. **一轮只有一个面板**。本轮所有审查类工具结果（标准引用自检、术语白名单、自述型审查）聚合进同一个面板，按「来源文件 → 规则码族」两级分组并给计数；不按工具调用拆成多张卡，也不一条问题一张卡。
2. **过程与产物分家**。工作流水里的审查工具行只保留「图标 + 类型 + 条数」摘要，不展开细节。
3. **面板是前端组件**，不引入新路由或新页面；数据全部来自已投影的结果载荷，不额外请求。
4. **规则码用中文类别**：面板直接显示类别（如 `标点`），规则码另占一格（如 `标点-001`）。历史数据里的英文族名由内置映射翻成中文标签，**序号原样保留**；没见过的族名**不猜译名**，原样显示。

严重度分三档：**必须修改 / 建议修改 / 提示**。

### 点击问题 → 原文高亮（已落地）

点面板里的一条问题，会打开对应文件的预览并滚动到命中位置、高亮原文片段。三种渲染面共用同一套定位机制：

| 类型 | 原件渲染方式 | 原件高亮 |
| --- | --- | --- |
| `.docx` | docx 渲染成 DOM | **支持**（按片段定位 DOM 高亮） |
| PDF | 逐页文本层 | **支持**（先搜到目标页 → 跳页 → 文本层高亮） |
| 提取正文（快照） | markdown 渲染 | **支持**（按片段在渲染结果上定位） |
| `.doc`（旧版） | WASM 渲染 | 未做 |
| `.xlsx` / `.xls` | canvas 渲染（无文本层） | **不支持**（退回「原件看版面 + 提取正文看高亮」两标签） |

- **找不到就不装成可点**：定位不到的问题条不呈现为可点击，避免跳到无关位置误导复核。
- 高亮落在**渲染后的正文**上，不是源码；命中用实心琥珀底 + 下划线，所在整段再加一层淡琥珀底，并在需要时把视口滚到命中处。
- 修改意见跟着定位一起给：点一条问题会同时显示「命中的原文片段」「问题说明」「建议改成什么」。

### 采纳 → 一键修改（已落地）

审查的终点不是「知道哪错了」，而是「改掉」。

- 面板行与定位卡右上角各有对号：**一处勾上，另一处立刻是勾上的**（同一份标记状态）。
- 面板头显示「已采纳 N 条」与一个按钮：点一下即发一轮新对话，带上完整清单。
- Agent 逐条调用 **`docx_patch`**（手术刀工具）改字：只替换命中的那几个字，字体/字号/加粗/段落/表格/编号/页眉页脚都不动；默认另存为副本，一处都没命中就不写文件。
- 已知边界：**采纳标记不落盘**，刷新会丢，这是当前明确记录的边界。

## 知识来源：管理员端「知识」板块

原核审通里分散的几类「审查依据」数据，统一收敛为**企业服务端管理员端的一个「知识」板块**，下辖三个子域。**普通用户在客户端看不到任何管理入口**，只在执行审查时被 Agent 读取。

| 子域 | 内容 | 消费方式 |
| --- | --- | --- |
| 术语白名单 | 专业术语（含别名） | 全量拉成集合，**过滤**校对结果（命中即丢弃），防专业词误报 |
| 标准规范清单 | 标准编号 / 名称 / 状态 / 日期 | 全量拉轻量索引，本地机械匹配 |
| 规范库（条文 / 审点） | 条文原文 + 判定提示词 | 全量预取，逐条核对（供「以库审文」，后置） |

**这三类都不是语义检索，而是「全量拉取 + 本地确定性命中」**。这样同一文件 + 同一库 = 同一结论，审查结论可复现；语义检索做不到这一点。

### 端侧执行链路

```text
管理员端维护（唯一写入口）
      │  全量/增量下发 + 端侧缓存（按版本失效）
      ▼
客户端执行：本地命中 —— 零网络、零延迟、可复现
```

- **缓存位置**：用户数据目录下的知识缓存目录（`~/.reactor/knowledge/`），文件为 `standards.json` / `terminology.json` / `rule-libraries.json`。
- **同步触发点**：登录成功钩子 + 应用启动时已登录补齐；按服务端版本做条件请求，未变更则不重写；失败保留上一份可用缓存。
- **读取方**：CLI 侧的 `KnowledgeCheck` 工具，只读本地文件。**企业令牌不进入 Agent 进程**，因此离线可用、判定可复现。
- **不发布的库不下发**：编辑中的库服务端直接不下发，避免半成品让「同一文件 + 同一库 = 同一结论」失效。
- **缓存缺失时**：工具返回「未同步」状态 + 可执行提示，**不允许把「库没同步」当成「未收录」**（那是假结论）。

### 标准引用自检的判定口径

标准引用自检走**零模型的确定性比对**：提取引用 → 归一化编号 → 与本地标准库索引机械匹配。

| 判定 | 含义 |
| --- | --- |
| 通过 | 库中该编号该年代号为现行/即将实施 |
| 已废止引用 | 该编号该年代号已废止——最常见、也最有价值的缺陷 |
| 未注年代号 | 只写编号不写年代号 |
| 未写版本标注 | 同一年代号库里分多个版本（如「2018 年版」），应写明 |
| 编号不存在 | 同体系收录充分却查不到，更可能是笔误或前缀错 |
| 库未覆盖该体系 | 该体系（如 DL / NB / EJ / CECS）库里几乎没有条目，**无法核对**，需人工确认 |
| 未收录 | 同体系收录充分但查不到 |
| 即将实施 | 实施日期未到 |

**必须知道的三个数据事实**（来自实测报告）：

1. 标准库当前约 **1.34 万条**，来源是「图书标准库」全量导出后按核电设计院相关性筛选，**以通用工业标准为主、行业标准整体缺失**（DL / NB / CECS / EJ / HAF 等体系几乎为零）。
2. 因此「未收录」里有很大一部分是**库缺口，不是文档写错**；报告与对话都必须区分这两类，不得说成「该标准不存在」。
3. **废止标准必须保留**：自检的核心价值之一就是判定「你引用的这条已废止」，清掉废止数据会让该判定失效。

**两条必须带上界面的诚实边界**：

- **无文本层的文件（PDF 图纸 / DWG）必须明说「无法自检」**，不得输出「未发现问题」。
- 未注年代号、`GB` 与 `GB/T` 前缀混用、疑似笔误**只能给候选**，需人工确认。

### 已落地的能力

1. **三档界面模式 + 强收敛展示**：审查档下 Git 变更面板、终端、命令详情、代码 diff 全部收起。
2. **审查类型卡片（5 类）+ 预填 + 审查档问候语**。
3. **5 个审查技能随安装包内置**（`review-proofread` 另带错词表与标点规则附件），默认启用、离线可用；用户不需要执行任何命令、也不需要登录企业端。
4. **管理员端知识板块三子域**：术语白名单、规范库、标准清单都有管理页（含分页、搜索、筛选、JSON 批量导入，导入幂等）；标准库已导入约 1.34 万条；内置术语随建表幂等写入。
5. **端侧只读消费接口 + 端侧缓存**：三个子域按版本失效，断网仍可执行自检。
6. **确定性自检工具**：标准引用自检零模型依赖，无模型可用时该链路仍能出结果。
7. **问题点击定位 + 原文高亮**：docx 与 PDF 原件都已支持；提取正文视图支持字符级定位。
8. **自述型审查定位**：另外四类审查的结论也能点问题跳原文（由工具在正文里查找并算出偏移，找不到就不装成可点）。
9. **采纳 + 一键修改**：逐条拍板后一次性改，改动走保留原格式的 `docx_patch`。
10. **报告导出工具**：生成 `.docx` / `.xlsx`，报告带结论状态、核对引用数、库快照与覆盖缺口声明。
11. **流程问题清单 13 条中的 9 条已修**，包括：空问题表不再把「查不到」写成「未发现问题」、报告存库版本、报告附库覆盖免责声明、长文档改走外部文本文件（禁止手工切片）、标准库缺口与编号笔误分流、缓存年龄提示、空库不再误判为「未同步」。

### 已知数据问题（不影响链路可用性）

| 问题 | 现状 |
| --- | --- |
| 行业标准整体缺失 | DL / NB / CECS / EJ / HAF 等体系源数据即缺，实测「未收录」多半属于此类；需另找来源 |
| 其余分类丢弃率偏高 | 技术规范、保温、验收、电缆、电气、法兰等分类筛选可能同口径误删，需复核补入 |
| 术语白名单覆盖域不匹配 | 白名单偏核安全/设备/工艺，暖通/给排水/消防域几乎不在其中，校对仍会有专业词误报 |
| 正文快照生命周期 | 快照落在知识缓存目录下，无清理策略与容量上限，报告也未记录快照标识 |
| 企业令牌隔离是约定而非强制 | 默认密钥可推导，属于已知待办口径问题 |

## 验收场景

1. 胶囊切到审查档后高亮第三档，刷新后保持。
2. 审查档下草稿空态显示审查类型卡片；编程/办公档下不显示。
3. 选「基础校对」并上传一份含错别字的文档，Agent 给出结论 + 问题面板（每条含原文与建议）。
4. **点击任一条问题 → 打开该文件预览、滚动到对应位置并高亮**。
5. 选「标准引用自检」，Agent 调用确定性工具对照标准库，给出引用是否存在 / 已废止 / 版本不符的判定；**无模型可用时该链路仍能出结果**。
6. 审查档下 Git 面板、终端、命令详情、代码 diff 均不出现；切回编程档后恢复。
7. 办公/编程档现有行为零回归。
8. 首次引导仍只有「编程 / 办公」两档。
9. 审查类型入口**不出现**「仅规则审查」「DEC 规范审查」「以库审文」。
10. 管理端知识板块三个子域都有管理页；**普通用户界面无任何管理入口**。
11. 无文本层的文件必须明说「无法自检」，不得给出「未发现问题」这类结论。
12. 审查问题条可点击定位；偏移越界时不定位，不得跳到错误位置。
13. 端侧缓存生效：第二次执行审查时不再全量拉取，断网时用缓存仍可完成自检。
14. 一键修改后：改动只落在 `word/document.xml` 的文本节点，段落/表格/编号/样式/媒体按原字节写回，原文件逐字节不变。

## 与上游 ZCode 的差异

| 项 | 上游 ZCode | 本说明书 / 本仓 |
| --- | --- | --- |
| 文件审查板块 | **上游无此能力** | 审查档 + 审查类型卡片 + 统一结果面板 + 原文高亮 + 一键修改 |
| 审查知识来源 | — | 企业服务端「知识」板块（术语白名单 / 标准清单 / 规范库），端侧缓存、离线执行 |
| 确定性自检 | — | 标准引用自检整条链路零模型依赖 |
| 批量审查 | — | 批量技能与卡片已移除，仅保留导出工具 |

**本仓为什么需要它**：内网用户的核心工作之一是**文件合规与质量把关**（设计说明、材料表、合同、标准引用）。把这件事做成「切一个档位 + 选一个类型」，比让用户自己写提示词更能保证结论一致、可复现、可交付；而确定性工具 + 管理员统一维护的知识库，正好满足内网对「可审计、离线可用、同文件同结论」的要求。
