# 内网服务端总览与接线

本页讲清三件事：Reactor 的内网服务端负责什么、桌面端怎么接上它、以及为什么它**不**走上游 ZCode 的官方端点链路。适合部署与运维人员，也适合想搞明白「模型从哪来、身份从哪来」的使用者。

服务端本体在仓库的 `server/` 目录，它有独立的工作区与部署方式，本页只做面向使用者的转述；契约与实现请以 `server/README.md` 与 `docs/未完成-服务端接线-*.md` 为准。

## 1. 服务端的三项职责

服务端不是「一个代理」，而是三块能力的合集：

| 职责 | 内容 | 对外形态 |
| --- | --- | --- |
| 身份底座 | LDAP 与本地账号双源登录、JWT 签发与续签、组织树与角色权限（三级数据范围） | 身份进程，默认端口 `8791` |
| 模型网关 | 唯一模型出口：供应商 / 密钥 / 模型目录由管理台维护，模型可见范围按令牌身份决定 | 网关进程，默认端口 `8790` |
| 管理台 API | 用户、组织、权限、模型与供应商、密钥、用量、审计、技能、专家、知识库、软件更新、反馈受理 | 管理台页面挂在 `/console`，管理接口挂在 `/admin/*` |

三者的关系是：**没有网关，桌面端没有模型可用；没有身份底座，网关不知道调用属于谁**。所以登录是第一步，模型是第二步。

## 2. 两个进程、三个包

服务端是**独立 pnpm workspace**，不在主仓 `pnpm-workspace.yaml` 的匹配范围内，因此两边的依赖、lockfile 与门禁互不干扰。它由三个包组成：

| 包 | 角色 |
| --- | --- |
| `packages/server` | 服务端本体：身份、网关、管理台 API、技能 / 专家 / 知识库 / 审计 / 更新 / 反馈 |
| `packages/shared` | 契约层，服务端的**运行时**依赖（技能与专家模块有值导入，镜像里必须带产物） |
| `packages/admin` | 管理台单页应用（React + Vite），由服务端托管 |

同一个镜像、两个入口：身份进程跑登录与权限，网关进程跑模型代理，靠部署编排区分。想改跨进程共享的初始化，必须放在两边都能走到的位置。

## 3. 桌面端怎么接上服务端

桌面端只认一条链路：**设置页（或首次启动的登录页）填「服务端地址 + 账号 + 密码」**。之后令牌、企业模型条目与网关鉴权全部由客户端侧的一个服务独占管理，界面只读状态、只转发动作。

### 3.1 唯一所有者

| 状态 | 所有者 | 落在哪 |
| --- | --- | --- |
| 服务端地址 | 企业服务端接入服务 | 凭据库键 `reactor:serverUrl`，**不写应用设置** |
| 企业登录令牌（access / refresh） | 同上 | 凭据库 `reactor:*` 键（加密落盘），不进窗口桥 |
| 网关令牌 | 同上 | **只在内存**，从不落盘 |
| 企业 provider 条目 | 同上（经模型供应商配置的 overlay 写面） | `~/.reactor/v2/provider_config.json` |
| 企业模式开关 | 同上（由登录态派生，不单独存） | — |

「登录成功且 access 未过期」就等于企业模式，没有第二个开关。

### 3.2 登录时序

```text
设置页 / 登录页            客户端接入服务             服务端身份进程
      │  ① 地址 + 账号 + 密码        │                        │
      ├────────────────────────────►│  ② 登录请求            │
      │                             ├───────────────────────►│
      │                             │ ◄── access + refresh + 用户信息
      │                             │ ③ 写入凭据库 reactor:* │
      │                             │ ④ 申请网关令牌         │
      │                             ├───────────────────────►│
      │                             │ ◄── 网关令牌 + 有效期  │
      │                             │ ⑤ 拉取模型目录（带网关令牌）
      │                             ├───────────────────────►│
      │                             │ ⑥ 写企业 provider 条目 + 模型清单
      │ ◄── 已登录：显示账号 / 网关地址 / 模型清单            │
```

地址归一化只有两条规则，都是为了反向代理场景：**`http` 且未写端口**才补身份默认端口；`https` **不补**端口（补了会打到代理没监听的端口）。网关地址由身份地址推导：同主机、`http` 下换网关默认端口、路径改为 `/v1`。

### 3.3 模型调用时序

会话里的每一次模型请求都会走「现场取令牌」：

```text
Agent 运行时 ──► 客户端 Host：请求运行时鉴权头
                        │ 命中企业 provider 条目？
                        │   是 → 取最新网关令牌（过期先换）
                        ◄── 鉴权材料
Agent 运行时 ──► 企业网关 /v1/chat/completions（Bearer 网关令牌）
```

关键点是**网关令牌不进配置文件**：企业 provider 条目里的密钥字段是一个哨兵占位值，真实令牌每次请求由客户端现场解析。这样就不存在「两小时前的令牌写进了配置、过期后整轮请求全部失败」的窗口。

### 3.4 地址与登录态的生命周期

| 事件 | 行为 |
| --- | --- |
| 登录成功 | 写地址与令牌（地址保留、令牌更新），拉模型目录并写入企业 provider |
| access 即将过期 | 用 refresh 换新（refresh 是**滚动轮换**，必须存回新的那一个）；服务端也会在任一鉴权响应里捎带新 access |
| refresh 也失效 | 明确提示「需要重新登录」并清空会话；**绝不静默降级成直连上游**（静默降级等于绕过治理） |
| 重启应用 | 仍是已登录态（令牌在加密凭据库），地址保留，不必重抄 |
| 登出 | 清空令牌；企业 provider 的**模型清单清空、条目保留**（避免下拉里留一批「选中就报未授权」的条目，也避免下次登录重建条目） |

三类令牌的受众不同（access / refresh / 网关），**不可混用**；混用必然被拒。

> **提示**：身份进程没有独立的健康检查接口。探活只能用登录接口的错误码或身份自检接口，不要指望 `GET /health`。

### 3.5 落地状态

| 能力 | 状态 | 阶段标注 |
| --- | --- | --- |
| 企业登录与模型出口（令牌、网关地址推导、企业 provider、运行期鉴权注入） | 已实现，已真机验证 | P1 |
| 企业登录页唯一入口与强制登录门禁 | 已实现 | P1 |

## 4. 为什么企业服务端不塞进「官方端点」配置项

上游 ZCode 有一组「官方端点」配置（产品端点地址），它承载的是**官方托管服务**：官方接口、分享回调、订阅计费查询，以及把官方域名重写到自建地址的改写逻辑。

企业服务端**刻意不复用这个字段**，理由三条：

1. **语义不同**：它承载官方服务，企业服务端承载的是内网自建的身份与模型出口。塞进去会一次性改变一堆官方链路的行为。
2. **生命周期不同**：服务端地址与登录态同生命周期（登录时确定、登出后仍在），而端点配置属应用设置。同一事实放两处就是两个所有者。
3. **官方链路要保留**：本仓的既定方针是官方服务先不动（模型治理里那条「开发者模式旁路」也依赖它），隔离比合并更安全。

因此企业服务端地址单独存放，官方端点配置**不参与企业登录与模型出口**。两者在配置层面互不影响，也就不会出现「改了一个、另一个跟着变」的连带故障。

## 5. 部署形态：Docker Compose 一体化

服务端的推荐形态是 Docker Compose 一体化编排，把基础设施与应用服务一起拉起：

| 服务 | 作用 |
| --- | --- |
| 数据库 | 平台身份域数据库（身份、组织、权限、技能、专家、审计…），带向量扩展供知识库检索 |
| 目录服务 | LDAP 目录；测试环境可用内置 mock 域，真实内网切到实际域与加密连接 |
| 身份服务 | 登录 / JWT / 权限 / 组织，并托管管理台页面 |
| 模型网关 | 上游模型代理与模型目录下发 |

要点与常见坑：

- 数据卷按部署方式而分：部分卷是**外部**卷（指向历史已存在的卷）。**停服务时不要加删卷参数**，否则用户、组织与模型配置会不可恢复地丢失。
- 数据库的宿主端口曾因落在 Windows 保留端口段而绑定失败，现已改到保留段之外并只绑回环地址。若换机器后仍冲突，用系统命令查看保留端口段后另选。
- 容器内必须监听全零地址，否则宿主端口映射进不来；容器之间用**服务名**互连（不要写回环地址）。
- 管理台页面挂在 `/console`，管理接口挂在 `/admin/*`。两者前缀不同是**有意为之**：管理台前端自己的路由就叫 `/models`、`/providers`，挂到 `/admin` 会与前端路由回退冲突。

只要改服务端、不碰桌面端，在上面这个工作区里跑构建与类型检查即可；主仓的门禁不覆盖它，反之亦然。

## 6. 服务端还提供哪些面

除身份与模型之外，服务端已实现的面（本说明书不逐一展开，需要时查 `server/README.md`）：

| 面 | 说明 |
| --- | --- |
| 技能与专家市场 | 目录、安装、启停、收藏与使用量；桌面端下发见[技能与 Agent 下发](server-delivery.md) |
| 用量与审计 | 端侧上报、查询与聚合、策略下发；见[用量上报与策略下发](server-usage-policy.md) |
| 知识库与内容板块 | 知识库文件、标准清单、术语白名单、规范库 |
| 软件更新 | 桌面端自更新只认服务端下发的更新清单，发版走管理台 |
| 反馈与需求 | 桌面端的问题上报与需求提交落到服务端工单，管理台受理 |

> **待核实**：服务端与桌面端之间是否还有本页未列出的接缝（例如知识库缓存的端侧同步），需以 `server/README.md` 与对应契约文档为准——本页只承诺已列入上表与第 3 节的内容。

## 7. 两个已知未确认项

> **待核实**：用户把企业 provider 条目改坏或删除后，「重新登录能否恢复」在方案文档里被列为待验项（真机尚未走这一步）。已知的是：条目被删时网关鉴权解析会返回空，请求带着哨兵值当密钥打到企业网关被拒——**不会外泄到上游**，因为基址仍是企业网关。是否给该条目加只读标记，取决于这次真机验证的结果。

> **待核实**：身份基址到网关基址的推导规则在反向代理、多域名或网关单独部署（非默认端口）时是否仍成立，需按实际部署拓扑确认。

## 与上游 ZCode 的差异

| 关注点 | 上游 ZCode 官方文档 | 本说明书（本仓） | 原因 |
| --- | --- | --- | --- |
| 服务形态 | 官方托管服务：官方账号、官方网关、官方计费与额度 | 内网自建服务端：身份底座 + 模型网关 + 管理台，由你部署 | 内网隔离场景无法依赖公网服务 |
| 账号与登录 | 官方账号体系 | 企业账号密码登录（LDAP 或本地双源），登录是本产品唯一入口 | 归属要落到人，权限要落到组织 |
| 模型接入 | 官方端点与套餐额度 | 服务端下发模型目录，模型可见范围由令牌身份决定；企业目录即白名单 | 计量与治理必须在自己手里 |
| 模型鉴权 | 官方账号令牌 | 网关令牌每次请求现场签发、只在内存，落盘的是哨兵占位值 | 避免过期令牌写进配置造成整轮失败，也避免令牌落地 |
| 地址配置 | 官方端点地址一个字段 | 企业服务端地址**独立存放**，与官方端点隔离 | 语义与生命周期都不同；合并会连带改变官方链路行为 |
| 部署与分发 | 下载安装包、登录官方账号即用 | Docker Compose 一体化部署服务端；独立工作区、独立门禁 | 内网分发不依赖公网下载站与套餐 |
| 健康检查 | 官方服务自带探活 | 身份进程无独立探活接口，只能用登录接口错误码或身份自检接口 | 以服务端实际提供的接口为准 |
