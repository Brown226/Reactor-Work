# 反馈与支持

为帮助团队更高效地定位并排查你遇到的问题，建议在反馈时提供详细的使用场景、操作路径以及相关的报错信息。Reactor（数智堆脑）的反馈统一走**内网受理渠道**：桌面端提交，自建服务端落库，管理台受理。

本页说明应用内的反馈入口、工单填写方式、处理进度查看、日志打包，以及这条链路在服务端的接线口径。

## 应用内反馈入口

Reactor 内置统一的反馈体系。无论是主动提交建议，还是遇到报错时快速上报，都可以在应用内直接完成。

### 工作区帮助菜单

点击工作区右上角的帮助入口，展开菜单，反馈相关能力都收拢在这里：

| 菜单项 | 用途 |
| --- | --- |
| 问题上报 | 打开「提交反馈」面板，提交 Bug、异常表现等问题，支持附带截图与日志 |
| 给产品提需求 | 提交功能建议，工单类型标记为「功能建议」 |
| 产品文档 | 打开产品文档入口 |
| 导出日志 | 手动导出本地日志压缩包，用于作为反馈附件 |
| 资源管理器 / 检查更新 / 关于 Reactor | 桌面端专有的其他帮助项 |

### 报错提示入口

界面出现错误提示时，可以直接点击提示条上的「反馈问题」。这种入口会自动带入报错摘要与当前会话信息，适合反馈初始化失败、运行时报错等问题。

## 填写并提交反馈

进入「提交反馈」面板后，按引导补全以下字段即可提交：

- **反馈类型**：Bug 反馈 / 使用问题 / 功能建议 / 性能问题。选择后表单会调整问题描述的引导文案。
- **标题与详细说明**：描述遇到的问题与复现步骤。表单会按类型给出建议的叙述结构（例如 Bug 反馈包含「问题描述 / 操作步骤 / 期望结果 / 实际结果」）。
- **严重度**：完全用不了 / 影响使用 / 小问题建议，分别对应 P1 / P2 / P3。
- **发生位置**：从「Plugin / MCP」「Agent 任务执行失败」「模型配置 / API Key」「模型调用报错」「权限 / 配置保存」「SSH 连接失败」「WSL 连接失败」「UI 布局 / 交互」「模型响应慢 / 额度」「崩溃 / Internal Error」「文档 / 使用咨询」「其它」中选择。
- **截图**：支持粘贴、拖拽或选择文件，最多 5 张图片。
- **日志**：勾选「上传诊断日志」后会把日志压缩包作为附件一并上传。

> **提示**：截图前请留意图片中的隐私信息与内部地址。

**不再要求填写联系方式**：身份由登录态自带，工单上的报告人信息从访问令牌解析，界面上没有联系方式输入项。

## 提交后的处理语义

### 工单与状态

每条反馈都会生成一个工单，状态取值共 9 种：

| 状态 | 含义 |
| --- | --- |
| 已提交 | 工单已收到，等待处理 |
| 信息不足 | 还需要补充信息 |
| 已采纳 | 已采纳，会安排修复或改进 |
| 答复关闭 | 已答复并关闭，如仍有问题可重新提交 |
| 已归档 | 已归档 |
| 已拒绝 | 暂未纳入处理 |
| 开发中 | 正在处理中 |
| 已解决 | 问题已处理完成，等待版本上线 |
| 已上线 | 相关修复或改进已上线 |

### 我的反馈

在「提交反馈」面板中切换到「我的反馈」标签，可以查看提交过的工单及其处理进度、管理员回复与时间线，也可以在详情里继续补充复现步骤、截图或日志。

### 红点与事件语义

| 动作 | 结果 |
| --- | --- |
| 用户提交工单 | 工单状态为「已提交」，产生 `created` 事件 |
| 用户追加消息 | 工单被标记为「有新动作」（管理台列表标红点），活动时间更新，产生 `user_replied` 事件 |
| 用户上传附件 | 同样点亮红点并刷新活动时间 |
| 管理台打开详情 | 红点熄灭（视为已读） |
| 管理台改状态 / 指派 | 产生 `status_changed` / `assignee_changed` 事件 |
| 管理台回复 | 该条评论标记为官方回复，产生 `staff_replied` 事件 |

也就是说，**红点代表「用户有新动作、受理人还没看过」**，由服务端维护，不由客户端自行推断。

## 反馈链路在服务端的接线口径

这条链路的服务端实现与客户端既有协议保持一致，客户端侧只需切换请求基址。

### 客户端 wire 格式

客户端按既有格式提交，服务端照此实现，协议未新造：

```json
{
  "title": "问题标题",
  "device_mid": "设备标识",
  "content": {
    "description": "详细说明",
    "category": "bug",
    "function": "其它",
    "severity": "P2-中"
  },
  "environment": {
    "app_version": "3.14.0",
    "platform": "win32-x64",
    "os_category": "win32"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `ticket_id` | 工单唯一标识，字符串形式贯穿全程（不可枚举） |
| `content.category` | 反馈类型：`bug` / `usage` / `feature` / `performance` |
| `content.function` | 发生位置（模块分类） |
| `environment` | 提交时的设备与环境快照 |
| `messages[].sender_type` | 消息方向：`user` 为本人补充，`staff` / `admin` 为官方回复 |

### 公开段与鉴权段的分工

反馈接口横跨两个边界：

| 面 | 路径前缀 | 鉴权 |
| --- | --- | --- |
| 提交面 | `/feedback/ticket`（建单、列表、详情、追加消息、上传与取回附件） | **挂在公开段**：访问令牌可选，验过才填报告人 |
| 管理面 | `/admin/feedback/tickets`（受理列表、详情、状态流转、回复、附件下载） | 挂在鉴权段之后，且需要管理角色 |

提交面必须挂在公开段：自建服务端只认自家身份服务签发的令牌，不带令牌的上报也应能建单；若挂进强制鉴权段，会让本产品自己的上报全部被拒。

### 报告人身份取自令牌

报告人的账号与部门**只从验过的令牌解析**，客户端自报的报告人字段一律不采信：

| 工单字段 | 来源 |
| --- | --- |
| 报告人账号 | 令牌中的用户标识 |
| 报告人部门 | 由令牌中的部门标识查出的部门路径 |
| 报告人展示名 | 令牌中的姓名，缺失时回落到账号 |
| 设备标识 | 请求体中的 `device_mid`（与请求头同源） |

没有有效令牌时按匿名记录，并保留设备标识，用于「我的反馈」按设备过滤。

> **待核实**：「我的反馈」当前的归属口径是按设备标识过滤，尚未引入按账号查询工单的体系；若你需要跨设备查看自己提交过的工单，请与维护方确认。

### 附件字节直传

内网服务端没有对象存储直传通道，客户端的附件改为**直接把原始字节推给服务端**：

- 请求体就是文件原始字节流，文件名通过请求头携带并做百分号编码，以便中文名无损还原。
- 服务端边写边算校验值，先写临时文件再原子改名，避免留下半截文件被当成可用附件。
- 单文件后缀有白名单（压缩包、图片、文本、日志、JSON、Markdown、PDF、CSV 等），超出白名单会直接拒绝。
- 上传失败不会让已建好的工单变成「提交失败」：失败信息会降级成工单里的一条系统评论，正文与后续流转不受影响。

附件在服务端以随机名落盘，用户原始文件名只存在数据库里；用户面与管理面下载到的是同一份字节，并可在管理面记录下载审计。

## 如何打包日志

优先使用应用内置的**导出日志**功能；如果导出失败，再手工定位日志目录。

### 通用步骤

1. 点击工作区右上角的帮助入口，展开菜单。
2. 点击「导出日志」，按提示保存生成的日志压缩包。
3. 在「提交反馈」面板勾选上传诊断日志，或把压缩包作为附件添加。
4. 如果导出失败，手工定位日志目录后自行压缩。

### 日志目录位置

| 位置 | 路径 |
| --- | --- |
| 用户数据根 | `~/.reactor` |
| CLI 日志 | `~/.reactor/cli/log` |
| 导出日志产物 | `~/.reactor/export-log` |
| 反馈相关暂存 | `~/.reactor/feedback` |

> **提示**：导出时会做脱敏处理（识别敏感键名的值、连接串中的凭据等），并跳过凭据文件本身；但仍建议在提交前自行确认压缩包里没有内部地址与个人信息。

## 受理与跟进

| 环节 | 由谁负责 |
| --- | --- |
| 提交 | 使用者在应用内提交（也可从报错提示条直接进入） |
| 落库 | 自建服务端的反馈数据域 |
| 受理 | 管理台的反馈受理页面：状态与类型筛选、详情、状态流转、回复 |
| 回访 | 管理台回复会出现在你的「我的反馈」详情与时间线里 |

如你需要人工介入或补充说明，请在工单里追加消息；带上工单标识便于受理人直接检索到完整上下文。

## 与上游 ZCode 的差异

- 上游写法：列出用户反馈表、应用内反馈、GitHub Issues、加入社群四种渠道。→ 本说明书写法：只保留应用内入口，统一的受理方是内网服务端与管理台。→ 原因：内网隔离部署，公网表单、GitHub 仓库与社群入口与本场景无关。
- 上游写法：工单 ID 用于「在社群沟通或跟进问题时附上」。→ 本说明书写法：改为在工单内追加消息、由内网管理台受理跟进。→ 原因：删除社群入口后，跟进动作收敛到工单本身。
- 上游写法：联系方式字段（留邮箱便于联系）。→ 本说明书写法：明确说明该字段已下线，身份由登录态与访问令牌自带。→ 原因：本仓的产品决策是不再让用户填联系方式。
- 上游写法：附件走对象存储直传凭证（先领凭证、再把字节传对象存储）。→ 本说明书写法：附件改为字节直传内网服务端，并说明临时文件与失败降级语义。→ 原因：内网服务端没有对象存储直传通道，这是有意的取舍。
- 上游写法：日志目录给 `~/.zcode`、`%USERPROFILE%\.zcode`。→ 本说明书写法：`~/.reactor`、`~/.reactor/cli/log`。→ 原因：用户级目录已收口为 `.reactor`。
- 上游写法：报错入口与工单体系由官方后端承载。→ 本说明书写法：补充客户端 wire 格式、公开段与鉴权段分工、报告人身份取令牌、红点与事件语义。→ 原因：本仓把反馈链路接到自建服务端，这些是使用者与集成方都需要知道的口径。
- 上游写法：结尾「加入社群」列飞书群、微信群、公众号、小红书。→ 本说明书写法：删除，改为内网受理与跟进流程。→ 原因：社群入口与公网账号绑定，本仓未提供。

> **待核实**：管理台受理页面的具体筛选字段与角色可见范围随服务端版本演进，请以管理员实际配置为准。
