# 目标模式

面对需要跑很久的复杂任务，可以用 `/goal` 给当前会话设一个目标。设定之后，Reactor Agent 会围绕这个目标持续推进：每一轮结束都会自动校验目标是否达成，没达成就自己接着下一轮，确认完成才收尾——把「盯着 Agent 反复说继续」变成「设一个目标，等结果」。

**适合什么任务**：一句话说得清、但要多轮才能做完的活，例如——

- 「重构整个模块并保持测试通过」
- 「修复所有 TypeScript 编译错误」
- 「把这个页面的首屏加载时间压到 2 秒以内」

目标描述越具体、越可校验，每轮的判断就越准。比起「优化一下性能」，「把 `pnpm test` 跑通，并且首屏加载控制在 2 秒内」这样的说法效果会好很多。

## 设定目标

在输入框里输入 `/goal`，后面接一句话，就是这轮会话的目标。也可以先输入 `/`，在建议面板里选 goal。

一个会话同一时间只有一个目标。常用写法：

```text
/goal 查看当前目标
/goal <目标描述> 设定目标；已经有目标时会替换掉它
/goal replace <目标> 明确替换当前目标
/goal pause 暂停
/goal resume 恢复
/goal clear 清除
```

> **提示**：再次输入 `/goal <新目标>` 视为**显式替换**，会用新目标覆盖旧的，不会因为你漏写 `replace` 而保留旧目标。
> `/goal` 是会话级目标命令，只在**新会话的空草稿**里由 `+` 菜单提供；消息中间插入的 `/goal` 不会被执行。

目标设定后，右侧状态面板会出现目标卡片，显示目标描述、状态与已用时间。下面按迭代分组，列出每一轮做完的清单项；最下方是当前这一轮的进度和待办。每轮的标题来自上一轮校验给出的下一步动作，所以顺着往下看，就是这个任务一路是怎么推进的。

一件小事值得知道：清单项归属于它第一次出现的那一轮，哪怕是在后面几轮才做完，也仍然显示在原来那一组里。这样回头看每轮的实际产出才不会错位。

状态取值与含义：

| 状态 | 含义 |
| --- | --- |
| **进行中** | 目标已激活，正在推进或校验 |
| **已暂停** | 被主动暂停、被停止键打断，或预算耗尽后等待显式恢复 |
| **已完成** | 校验判定达成 |
| **预算受限** | 达到为该目标配置的用量上限而停下 |

## 每轮自动校验

一轮结束后，Reactor 会单独做一次校验，判断目标有没有达成。

没达成时，会给出下一步该做什么，并自动开启下一轮——不需要你手动追问「继续」。

达成时才会收尾，输出总结。

校验看的是实据。写了一份计划、列了一份待办清单、跑了很久，或者给出一段听起来很像结论的回复，这些本身都不算数；要有改出来的文件、命令输出、测试结果这类能核对的东西才算。另外，只要还有待办没做完，校验就不会判定完成，而是优先把它做完。

校验由独立的校验请求完成，它只做判定、不做实现，并返回结构化的结论（是否通过、原因、下一步动作）。如果校验请求本身失败或返回不可用，会按「未完成」处理，继续推进而不是误判为已完成。

> **提示**：目标是纯文本，运行时把它当作「要完成的任务」而不是更高优先级的指令来对待。

## 中途介入

目标设定后随时可以调整。最省事的办法是直接用自然语言告诉 Agent 你的想法——换个方向、先停一下、这个目标不要了，它会据此替换、暂停或清除。

暂停不会丢东西：已经跑过的轮次、工具调用记录和产出的文件都在，状态面板顶部的图标会变成继续，随时可以接着跑。中途按停止键取消任务时，目标也会自动暂停，不会在你没留意的时候继续消耗额度。

关掉会话再打开也一样。目标状态由系统保存，重新进入这个会话时它还在，可以从上次的地方继续。

目标会在三种情况下停止自动推进：校验判定完成、你主动暂停或清除、以及跑到为这个目标配置的用量上限。

> **平台差异**：状态面板里的暂停 / 继续按钮是桌面端的主要入口；输入框里的 `/goal pause`、`/goal clear` 在当前客户端不作为命令消费。

> **待核实**：CLI 端 `/goal pause`、`/goal clear` 的完整可用范围。

## 什么情况下设不了目标

有两种情况会被拦下来，界面上会直接说明原因。

**计划模式**专注于先把方案讨论清楚，不会自动往下执行，所以和目标模式的自动续跑是冲突的，需要先切回其他执行模式。界面提示为「Goal 无法在 Plan 模式下使用，请切换模式。」。

**任务正在运行**时也设不了目标，提示为「请结束任务后设定目标。」。等这一轮跑完，或者先按停止。目标命令会被排到队列里，在合适的边界执行，而不是被丢弃。

## 与执行模式搭配

目标模式和[执行模式](agent.md)管的是两件事：目标决定「做到什么程度才算完」，执行模式决定「过程中多少操作需要你确认」。

长目标任务建议搭配 **完全访问** 或 **自动编辑**，中途打断少，迭代会更连贯。反过来，如果这个任务会改动重要文件，用 **变更前确认** 也没问题，只是需要你在旁边盯着确认。

## 与上游 ZCode 的差异

| 项 | 上游写法 | 本说明书写法 | 原因 |
| --- | --- | --- | --- |
| 产品名 | ZCode | Reactor（数智堆脑） | 本仓品牌已改名 |
| 用量上限表述 | 强调「为这个目标配置的用量上限」 | 保留，并补上「预算受限」状态词条 | 本仓状态词条为「预算受限」，与上游措辞不同 |
| 校验失败语义 | 未说明校验请求自身失败时的行为 | 补上「按未完成处理」 | 本仓源码按 fail-open 继续推进，避免误判完成 |
| 暂停 / 清除入口 | 以 `/goal pause`、`/goal clear` 为主 | 说明桌面端以状态面板按钮为主，并标注待核实项 | 当前客户端不消费这两条命令；未核实部分按待核实标注 |
| 计划模式冲突 | 说明会被拦下 | 保留，并写入实际界面文案 | 本仓已有对应提示词条 |
| 套餐与非任务内容 | 涉及额度与订阅的表述 | 已删除 | 与内网隔离部署无关 |
