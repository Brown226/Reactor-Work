## 〇、先给结论

**"单加一个 Bot 模块"不够，而且方向偏了。** 它会把产品变成"一个窗口里的两个 App"：两个输入框、两个模型选择器、两套记忆、两套权限，用户每天要额外判断一次"这事该问哪边"。这正是路线 B1（嵌入面板）作为**过渡手段**可以、作为**终态**不行的原因。

更好的想法是：**不做第二个模块，做同一条会话画布的「第二种节奏」。**

一句话概括两个产品各自缺什么：

> **Reactor 有"活"，没有"人"；OpenMausBot 有"人"，没有"活"。**
>
> Reactor 的一切围绕任务与产物（会话、diff、终端、浏览器、产物），但屏幕上没有"谁在替我干活"；OpenMausBot 的一切围绕身份与陪伴（bot、人格、记忆、在场、审批），但它的"活"是不可审查的黑盒——你只能看着它操作一台你看不见细节的电脑。
>
> 融合 = **给"人"配上"活"，给"活"配上"人"**：一个画布里，一个有名有姓、记得住上下文的同事，正在产出你可以逐行审查的工作。

## 一、先否掉三个"看起来合理"的形态

| 候选形态 | 为什么诱人 | 为什么不行（作为终态） |
| --- | --- | --- |
| **① 侧栏加一个「Bot」标签页**（把 OMB 的 UI 搬进来或嵌进来） | 最快、最直观、几乎零设计成本 | 两个 App 拼在一起：两套会话列表、两套模型、两套记忆。更致命的是**它无法使用你的工作区**——bot 改的文件不在你的 diff 里，你审不了、回滚不了。价值最低、割裂最重 |
| **② 把 bot 当 subagent 列表**（"同事"= 一群子代理） | 复用现有 subagents 机制，实现最省 | 丢掉 OMB 唯一的差异化：**身份 + 长期记忆 + 在场 + 异步**。改名之后的 subagent 还是一个一次性任务角色，用户感知不到"同事"，也就没有理由用它 |
| **③ 照搬 OMB 的通讯录/房间/频道** | 体验完整、社交感强 | 那是"个人助理 + 社交"的产品骨架。编程工作台里，"房间"应该是**项目**，"频道"没有意义。照搬会把工具做成聊天软件 |

三个候选的共同错误：**都在 UI 层做加法，而没有改变"会话是什么"这个底层定义。**

## 二、设计原则：两条节奏、一个画布、四个物件

### 2.1 核心模型：会话有两种节奏

融合的本质，是承认"AI 干活"有两种时间尺度，并让**同一个界面同时承载它们**：

| | **前台节奏（任务）** | **后台节奏（同事）** |
| --- | --- | --- |
| 单位 | 一次任务 / 一个线程 | 一个长期在岗的同事 |
| 生命周期 | 分钟到小时，任务结束即归档 | 天到月，跨任务存在 |
| 你与它的关系 | **盯着它干**（同步、阻塞） | **知道它在干**（异步、通知） |
| 失败代价 | 重跑一次 | 记忆/信任受损，要能追溯 |
| 现在谁有 | Reactor 的全部体验 | OpenMausBot 的全部体验 |

> 关键判断：**不要把两者做成两个页面，而要做成同一画布的两种"在场状态"。** 前台任务在某条线程里展开；后台同事的状态以"心跳"的形式叠加在同一条画布上（正在工作 / 等待批准 / 完成待查 / 失败待重试）。

### 2.2 一个画布 + 四个界面物件

不做"Bot 模块"，做这四个东西：

| 物件 | 解决什么 | 承接谁的基因 |
| --- | --- | --- |
| **同事条（Team strip）** | "谁在替我干活、现在什么状态" | OMB 的在场感（presence） |
| **会话流（One stream）** | 唯一对话画布，人和同事的发言在同一个时间线里，靠身份标签区分 | Reactor 的会话 + OMB 的身份 |
| **工作痕迹面板（Work pane）** | 每条发言背后"到底干了什么"：差异 / 终端 / 浏览器 / 云电脑 / 产物 / 工具调用 | Reactor 的可审查性（这是最强资产） |
| **收件箱（Inbox / 值班）** | 需要你出手的事：审批、失败重试、后台完成待查收 | OMB 的异步审批模型（这是被低估的资产） |

### 2.3 线框（桌面端）

```
┌────────────────────────────────────────────────────────────────────────────────────┐
│ [项目: example-repo ▾]      ● 审查员 工作中 3m   ● 测试员 待批准(2)   🔔 5   ⚙ │ ← 同事条
├────────────────┬───────────────────────────────────────────────┬───────────────────┤
│ 同事（本项目）  │  会话流（唯一画布）                            │  工作痕迹          │
│ ● 审查员  值班  │  ┌ 我 14:02 ─────────────────────────────┐    │ [差异][终端]       │
│ ● 测试员  空闲  │  │ 把 3.x 章参数表核一遍                  │    │ [浏览器][产物]     │
│ ○ 文档员  离线  │  └───────────────────────────────────────┘    │ ─────────────────  │
│ ─────────────  │  ┌ 审查员 · 并行线程 #482 ───────────────┐    │ 参数 3.2.1        │
│ 个人助理        │  │ 比对 128 处，3 处偏差（详情见右）      │    │  - 12.5 → 12.8    │
│ ● 助理   空闲   │  │ ↳ 请求批准：读取企业网盘 [批准][拒绝]  │    │  + 单位缺失       │
│ ─────────────  │  └───────────────────────────────────────┘    │                   │
│ 项目            │  ┌ 我 14:06 ─────────────────────────────┐    │ ← 点任意一条消息，  │
│ ▾ example          │  │ @测试员 按这份差异跑一遍回归           │    │   右栏切到对应证据  │
│   · 参数核校    │  └───────────────────────────────────────┘    │                   │
│   · 报告生成    │  ┌ 测试员 · 并行线程 #483 ───────────────┐    │                   │
│ ▸ sar-review    │  │ 已跑 12 用例，1 个回归失败（见右）     │    │                   │
│                 │  └───────────────────────────────────────┘    │                   │
│ 今日 (5)        │  [ 输入框：说话，或 @ 同事派活 ]              │                   │
└────────────────┴───────────────────────────────────────────────┴───────────────────┘
```

三个要点：

1. **左栏不是"两个 App 的列表"，是一个信息架构的两个区**：项目 → 任务线程；同事 → 常驻线程；个人助理是全局那一组。**同事默认按项目归属**（见 §3.3），因为编程工作台的身份是项目，不是通讯录。
2. **中栏只有一种消息组件**。任务消息和同事消息用同一个渲染器，靠**身份芯片**（头像 + 角色 + 模型 + 状态）区分。这样"同事说的话"和"任务里 agent 说的话"不打架。
3. **右栏是融合发生的地方**。OMB 的"看着它操作"（屏幕流）和 Reactor 的"逐行审查"（diff）在这里合并成**按消息上下文切换的证据面板**——这是两个产品各自单独都做不到的体验。

## 三、五个交互原语（价值都在这里，不在布局里）

布局只是壳。真正让融合"有用"的是下面这五条**跨身份的动作**：

### 3.1 @委托（task → teammate）

在任务会话里 `@审查员 把 3.x 章核一遍`，系统为该同事创建一个**并行线程**（`parentThreadId` = 当前任务），它的输入带上当前任务的上下文（文件、diff、已选片段），产出以**消息 + 产物**的形式回流到任务流。

- 与 subagent 的区别：subagent 是"临时分身"，记忆为零；**同事有持久记忆**，这次学到的项目规范下次直接用。
- 与 OMB 的区别：OMB 里派活是"另开一个对话"，**结果回不到你的任务里**；这里结果原地回到任务流，且带 diff。

### 3.2 提升为同事（thread → teammate）

一个跑顺了的任务线程，可以一键**沉淀成同事**：把当前的提示词、工具授权、工作区绑定、关键上下文固化成一个常驻角色，之后可被 @、可定时、可跨任务复用。

这条解决了 Reactor 的真实痛点：**好用的提示词/权限配置每次都要重配**。也给了"团队"一个自然的生长方式——同事不是配置出来的，是**从成功任务里长出来的**。

### 3.3 绑定工作区（workspace binding）

同事必须绑定一个工作区（项目目录），这是**和 OMB 最大的一处改造**：OMB 的 bot 有一台"自己的电脑"，你看不见细节；Reactor 的同事应该有一台"**你的工作区 + 可选隔离 VM/云电脑**"。

- 改文件 → 进 diff，可审查、可回滚（拿到 Reactor 的全部资产）。
- 需要跑危险/联网动作 → 进隔离环境，屏幕流在右栏可见。
- 这条是"活"能配上"人"的技术前提：**没有工作区绑定，同事就还是黑盒。**

### 3.4 分叉为任务（teammate → task）

同事正在做的一件复杂事，可以"拎出来"变成你当前的前台任务：带着已有上下文进入当前会话，你接管、改、批准。相当于把后台节奏**临时拉回前台**。

### 3.5 值守与定时（routine）

OMB 的 routines / 主动任务映射为"值守"：同事可按计划或事件自动开工（每日核对、提交前检查、监控目录变化），结果进收件箱，而不是打断你。

- **Reactor 已有地基，别重造**：`automations` 表 + 常驻 cron scheduler 进程（`packages/desktop/src/scheduler/*`）已经能"到点新建会话跑一轮"。缺的不是调度器，而是**归属和收口**：现在产出的是一个"新会话"，不是一个"同事在值班"；结果落在会话列表里，不落到收件箱。值守 = 已有 automation + 绑定到某个同事身份 + 结果进收件箱。
- 对"团队"叙事仍是必需的：**没有值守，同事就只是另一个聊天框。**

## 四、一段端到端场景（用来检验形态是否成立）

> 我在做 参数核校。
> 1. 我在任务会话里说"把 3.x 章参数表核一遍"——**前台节奏**开始。
> 2. 我 `@审查员`。它在并行线程里开工，**同事条**上它变成"工作中 3m"，我不需要切窗口。
> 3. 它比对到一半，要读企业网盘 → **收件箱亮起**"审查员请求批准：读取企业网盘"。我在**当前画布**里点批准（不用去另一个 App）。
> 4. 它跑完，结果回流到我的任务流：3 处偏差。我点其中一条，**右栏**直接是高亮原文 + 参考来源。
> 5. 我 `@测试员 按这份差异跑回归`。它回归失败 1 个，右栏是失败的 diff。
> 6. 任务收尾，我把它**提升为"参数审查"常驻同事**，绑定 `example-repo` 工作区，设"每次提交前跑一遍"。
> 7. 第二天早上我打开 Reactor，**收件箱**里是"夜间：审查员完成 2 次值守，1 份待查收"。

**检验点**：全程我没有打开第二个 App、没有第二个输入框、没有"这事问哪边"的判断。这就是形态成立的标志。

## 五、演进路径：别一步到位，但每一步都要朝这个形态走

| 阶段 | 形态 | 技术改动 | 什么时候算到站 |
| --- | --- | --- | --- |
| **V1 过渡（1–2 周）** | 外壳先行：同事条 + 收件箱 + 右栏复用；同事线程由**适配层**调 OMB（路线 A/D），UI 用 Reactor 自己的组件渲染，**不嵌 OMB 页面** | 一层 `TeammateAdapter`（OMB Bot API / MCP）；全局事件通道（把 OMB 的审批/完成事件推进 Reactor 的收件箱） | 用户能在 Reactor 里完成"@同事 → 拿到结果 → 批准"闭环；左栏不再需要独立 OMB 窗口 |
| **V2 双向（3–6 周）** | 加上 §3 的五个原语（@委托、提升、分叉、工作区绑定、值守） | 会话模型扩展：`agentId` / `visibility(foreground|background)` / `parentThreadId` / `workspaceBinding`；值守**复用已有 automation**（补"归属同事"与"结果进收件箱"）；跨会话事件路由（现在是按会话 RPC，缺一个全局 channel） | 同事能改你的工作区并产出可审查 diff；值守能自动开工 |
| **V3 收敛（2–3 个月）** | **同事 = 一种长驻会话**，由 Reactor 的运行时统一执行；OMB 退化为"身份/记忆/定时"服务或被替换 | 执行引擎收敛（`apps/zcode-cli` 为主），内存/记忆做一层适配；OMB 的 CUA 按需接入 | 只有一套 agent 运行时、一套凭据、一套权限模型；OMB 的 UI 可完全下线 |

> 诚实说明：V1 有一个**看得见的缝**——同事的记忆在 OMB 那边，产物在你的工作区那边，两边靠适配层传。这个缝在 V3 才会真正消失。所以 V1 的价值是"验证交互"，不是"完成融合"。**别把 V1 的适配层当成终态架构去加固。**

## 六、反模式清单（比"要做什么"更容易出错）

- ❌ **两个输入框**：任何让用户"选在哪边说"的设计都是失败。
- ❌ **第二个模型/凭据面板**：同事的模型应该继承项目配置或账号体系，不要让用户为每个 bot 再登一次。
- ❌ **把 OMB 的频道/房间搬过来**：项目就是房间。
- ❌ **同事的"工作"不可审查**：只有屏幕流、没有 diff 的同事，等于把 OMB 的黑盒问题原样继承。
- ❌ **用"在线/离线"表示状态**：真正的状态是 `空闲 / 工作中 / 待批准 / 失败待重试`，这才是决策信息。
- ❌ **把审批做成消息流里的普通消息**：后台同事的审批会落在你没看的线程里；审批必须是**全局可路由的收件箱**。

## 七、怎么判断这个形态成立了（可观测）

| 指标 | 目标 | 含义 |
| --- | --- | --- |
| "这事该问哪边"的提问次数 | ≈ 0 | 没有双入口 |
| 从后台请求批准到你点下去的中位时延 | 分钟级 | 收件箱有效，不靠盯 |
| 同事产出中"带 diff 可审查"的比例 | 高（>80%） | 工作痕迹真的接住了 |
| 用户从任务线程 @ 同事的比例 | 上升 | 委托路径被用起来，而不是当摆设 |
| 切换窗口 / alt-tab 次数 | 下降 | "一个画布"成立 |

## 八、它跟 Reactor 现有的「专家」到底差在哪（关键，也是上一版设计的修正）

**先给结论：你的「专家」已经是 OpenMausBot 那个 bot 的"定义层"，缺的是它的"实例层"。** 我说的"同事"不是新物种，而是**专家 + 三段生命**：人级记忆、会话外在场、跨会话审批路由。如果这三样都不要，那就不需要 OMB——直接用专家就够了。

### 8.1 事实对齐（都有代码依据）

| 能力 | Reactor 现状 | 证据 |
| --- | --- | --- |
| 专家定义（人格、模型、技能、权限、开场白） | ✅ 已有，字段相当完整 | `packages/shared/src/server-agents-types.ts`：`persona` / `provider` / `modelId` / `skills[]` / `policyMode`(readonly·balanced·trust·strict) / `thinkingLevel` / `starters` / `tags` / `category` / `official` |
| 召唤专家 = 建会话时绑定 | ✅ 已有 | `server/packages/shared/src/session.ts:63`「建会话时绑定的专家名（slug）」；**会话创建后不再变，换专家 = 派生新会话** |
| 分发与治理（市场、安装、启停、收藏、热度） | ✅ 已有，甚至比 OMB 更企业化 | 「专家·技能」市场、企业服务端下发、`agent_installs` / `agent_favorites` / `agent_usage` |
| 记忆 | ⚠️ **有，但属于"工作区"不属于"专家"** | `packages/services/src/memory/memoryService.ts` → `cli/memories/projects/<workspaceId>/MEMORY.md`，同项目所有会话共享 |
| 在场 / 常驻 | ❌ 没有 | 没有"某专家正在工作中"的全局状态；后台只有会话内 background subagent |
| 会话外触发 | ⚠️ 部分（调度器有，身份没有） | `automations` 表 + `packages/desktop/src/scheduler/*` 常驻 cron 进程，但产出的是"新会话"，不是"某同事在值班" |
| @ 委托 | ❌ 没有 | composer 的 mention 只是**预填**（`ComposerMentionPrefill`，供技能/插件用），不是跨会话派活 |
| 跨会话审批 | ❌ 没有 | 审批在会话内 `ElicitationDialog`，阻塞当前会话 |

### 8.2 三个本质差异（也是融合的唯一增量）

1. **依附关系是反的。** 现在是「**会话持有专家**」——一次会话绑一个专家，换专家就派生新会话；"同事"需要「**专家持有会话**」——一个身份，多个任务线程，跨任务在岗。这是数据模型上最根本的一次翻转，也是为什么在 8.1 里专家字段全都对得上、但体验完全不同。
2. **记忆的归属不同。** 现在是"**项目记得一切，人什么都不记得**"：MEMORY.md 归工作区，任何 agent 进来都读同一份。同事需要两层——项目记忆（共享，别丢）+ **人级记忆**（"这个人上次跟你发现过 3.x 章单位不统一"）。OMB 给的正是第二层。
3. **时间范围不同。** 专家只在你召唤它的那几分钟存在；同事在你不在场时也存在（值班、待批准、失败重试）。这决定了 UI 必须有"在场"和"收件箱"，否则你根本看不见它。

### 8.3 一段对照，感受差别

- **专家**：新建会话 → 选「审查员」→ 它带人设干完 → 关掉就没了。下次再选，它**不记得**上次发现过什么；它只在你的会话里工作，你不在的时候它不存在。
- **同事**：审查员一直在侧栏（空闲/工作中/待批准）；记得上次的结论；你换到别的任务它还在；半夜按值守跑了一遍，早上在收件箱等你批；你说"@审查员 顺手把这个也看了"，它在当前任务派生一个并行线程，结果带着 diff 回到你的任务流。

**一句话**：专家是**岗位说明书**（招聘市场里那份），同事是**入职后在岗的人**。说明书你已经有了，OMB 补的是"人"的那部分。

### 8.4 所以上一版设计要改一处

上一版把"同事"写成新实体，有和专家重复造轮子的风险。正确做法是：

- **不改**：专家定义、市场、召唤流程、会话上的 `expertName` 绑定——`expertName` 本身就是天然的 join key。
- **只加一个实例层** `AgentInstance`：`{ expertName, workspaceBinding, agentMemory, inbox, status, scheduleRef }`。这层是 Reactor 完全没有、而 OMB 全部有的东西。
- **UI 不新建"Bot 模块"**：把「我的专家」升级为「我的团队」——同一个列表，多一列"在岗状态"，点进去就是同事的常驻线程。

## 九、一句话回答你的问题

- "单加一个 Bot 模块"：**只能当第一周的过渡壳**，它的天花板是"两个 App 并排"。
- 更好的想法：**把 OMB 的"人"注入 Reactor 的"活"**——一个会话画布、两条节奏、四个物件（同事条 / 会话流 / 工作痕迹 / 审批收件箱）、五个原语（@委托 / 提升 / 绑定工作区 / 分叉 / 值守）。

**判断标准只有一句**：用户还需要想"这事该问哪个 App"吗？需要，就说明还没融合。
