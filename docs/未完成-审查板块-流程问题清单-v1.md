# 审查板块 —— 操作运行流程问题清单 v1

> **日期**：2026-09-23　**性质**：缺陷清单（不修，交修复方执行）
> **方法**：对照 `docs/未完成-审查板块-方案-v1.md` 的设计意图，实跑端到端链路 + 逐处核对代码。
> **实测环境**：identity `http://127.0.0.1:8791`（本地实例，登录身份 `tiankd` / role=user）、
> 端侧缓存 `~/.reactor/knowledge/`、file-tools 插件 0.1.0。
> **结论**：链路本身是通的（取数、判定、定位、导出都能跑），但**流程上有 13 处不合理**，
> 其中 3 处会让流程产出**错误结论**（假阴性），必须优先修。

---

## 0. 流程全景与断点位置

设计意图的完整流程：

```
①切审查档 → ②选类型卡片(预填提示词) → ③抽取正文 → ④KnowledgeCheck(stale 判定)
    → ⑤逐条汇报+点击定位 → ⑥ExportReviewReport 出报告
```

各环节实测状态：

| 环节 | 状态 | 断点 |
| --- | --- | --- |
| ① 档位与卡片 | ✅ 通 | — |
| ② 5 张卡片预填 | ✅ 通 | — |
| ③ 抽取正文 | ❌ **无可用工具** | 见 P0-1 |
| ④ 自检判定 | ✅ 通（实测 18 条引用/14 通过/4 未收录） | 见 P1-3、P1-4、P2-1 |
| ⑤ 定位高亮 | ✅ 通（字符偏移自渲染 + 快照） | 见 P3-1 |
| ⑥ 导出报告 | ✅ 通 | 见 P0-2、P1-1、P1-2、P2-4 |

**一句话**：③ 这一环没有落地工具，⑥ 会把"查不到"写成"没问题"。这两处不修，其余优化都是次要的。

## P0：会让流程产出错误结论（必须修）

### P0-1　抽取正文这一环没有可用工具，且流程没有"解析器失败"分支

**证据**

- `review-batch/SKILL.md` 第 2 步明确要求：「`parse_document`（或 `ocr_scan` / `parse_dwg`，按文件类型选）抽成 markdown」。
- 实测该工具在本机**对 .docx 直接硬失败**：`未找到 anydoc 原生资产（file-tools 资产不完整）`。
  文件本身正常（108KB，可正常打开），是插件的原生依赖缺失。
- `docs/未完成-审查板块-方案-v1.md` 缺口 3 自述：`Read` 原生支持 PDF 与文本，但 **docx / xlsx / pptx 会按 utf8 读成乱码**。
- 因此本轮两次审查都得**绕过工具链**、自己写 python-docx 脚本才拿到正文。

**为什么不合理**

`review-standard-check/SKILL.md` 步骤 1 只写了**一个**异常分支：「若文件是图纸类、没有文本层，直接说明无法自检」。
那是"抽到了但没文本"，与"抽取工具本身失败"是两件事。后者没有任何指引，Agent 的默认行为会退化成
用 `Read` 读成乱码、然后**对乱码做审查**并输出一份看起来正常的报告。

**修复方向**

1. 抽取失败（工具报错）必须和"无文本层"一样显式终止，禁止静默降级。
2. 两个分支都要产出可机检的标志位（如 `extraction: "failed" | "no-text-layer" | "ok"`），
   并在报告里留痕，不能只靠 Agent 自觉。
3. 落到方案缺口 3（M1b）——这是阻塞主链路的缺口，应在 M4 之前补。

### P0-2　`issues` 为空 → 报告写"本次审查未发现问题"，把"查不到"写成"没问题"

**证据**

- `apps/zcode-cli/packages/core/src/tool/handlers/export-review-report.ts:136-137`：

  ```ts
  ...(input.issues.length === 0
    ? [new Paragraph({ text: "本次审查未发现问题。" })]
    : [ ...问题表 ]),
  ```

- 实测：一份**根本不含标准引用**的文档（一段 AI 对话转成的 docx）跑 `KnowledgeCheck` 返回
  `共 0 条引用 — 通过 0，…`，`summary.total = 0`。若据此导出，报告会写"本次审查未发现问题"。

**为什么不合理**

`issues.length === 0` 混淆了三种完全不同的情况：

| 真实情况 | 报告现行措辞 | 应措辞 |
| --- | --- | --- |
| 查了，全部通过 | 未发现问题 | 未发现问题（引用 N 条，全部通过） |
| 查了，**一条引用都没有** | 未发现问题 | **未检出标准引用，请确认范围** |
| 没查成（抽取失败/非文档） | 未发现问题 | **未完成审查** |

这是**假阴性**，且是最危险的一类：报告是交付物，收报告的人会据此签字。
`summary.total` 字段已经存在（`KnowledgeCheck` 返回），但导出链路完全没用它。

**修复方向**

报告需要"审查覆盖率"概念：输入一个 `coverage`（引用总数 / 是否检出内容 / 抽取是否成功），
空 `issues` 时按覆盖率分三种措辞，禁止统一写"未发现问题"。

### P0-3　长文档没有分批路径，`text` 无上限且偏移语义绑定"单次传入"

**证据**

- `apps/zcode-cli/packages/contracts/src/tools/knowledge-check.ts:32-37`：`text` 是无上限的 `z.string().optional()`。
- 同文件 `:92-95`：`line` / `startOffset` / `endOffset` 的语义是「**相对传入的 text**」。
- 工具会把整份正文**落盘成快照**（`textPath`）并全量正则抽取引用。

**为什么不合理**

一份 PSAR 或设计说明可能几十万字符。当前只有两条路，都有害：

- 一次性全传：无上限、无分块、内存与正则开销不可控。
- 手工切片多次传：**`startOffset` 的相对基准变成切片起点**，前端按偏移高亮会定位到错误位置
  （而 `方案-v1.md` §3.3 明确写了"偏移越界一律不钳位，跳错位置比不跳更误导复核者"——
  切片后偏移是"合法但错的"，越界保护拦不住）。

**修复方向**

引入 `textRef`/`offsetBase`（或分块 id + 全局偏移基准），让多次取得同一份文档的偏移可拼回全文；
或由工具内部按行窗口扫描，对外只报全局偏移。

## P1：结论可信度与可追溯性（应修）

### P1-1　报告不存判定所依据的库版本，方案声称的字段全库无实现

**证据**

- `docs/未完成-审查板块-方案-v1.md` §4.4.3 自述：「自检报告天然抗迁移：报告里已冗余存
  `libraryStandardNo` / `libraryStandardName` / `libraryStandardStatus`，标准库变更不会让历史报告失真」。
- **实测：这三个标识符在 `apps/` `packages/` `server/` 全库 grep 命中数为 0**，从未实现。
- 报告实际字段（`contracts/src/tools/export-review-report.ts:19-31`）只有：
  `severity` / `code` / `quoted` / `message` / `suggestion` / `location` / `line`。
- `KnowledgeCheck` **返回了** `stamp`（`maxUpdatedAt` / `fetchedAt` / `count`），
  但导出链路把它整条丢掉了。

**为什么不合理**

「同一文件 + 同一库 = 同一结论」是这套能力对外的核心承诺（方案 §4.4.0），
但"同一库"没有落到交付物上。拿到 .docx 的人无法知道这条"已废止"是对着哪一版库判的；
库迭代后历史报告无法回溯验证。**方案文档把它写成已完成，实际是未落地**——修复方需注意别被文档误导。

**修复方向**

`ReviewReportIssueSchema` 增可选 `libraryNo`/`libraryName`/`libraryStatus`；
报告元信息增 `库快照：<maxUpdatedAt>（<count> 条，端侧写入于 <fetchedAt>）`。

---

### P1-2　报告没有"库覆盖缺口"免责声明，`missing` 最容易被误读

**证据**

- 报告文末只有一句通用话术（`export-review-report.ts:161-164`）：
  「本报告由 Agent 依据给定依据自动生成，供复核参考；正式交付前请由专业人员确认。」
- `missing` 的正确话术**只到对话层**：`review-standard-check/SKILL.md` 规定「必须写"需人工确认"」，
  且「不要把 `missing`（库待补充）说成"该标准不存在"」。
- 实测库覆盖（`GET /v1/standards/index`，13,445 条）：
  `GB` 5,181 / `GB/T` 3,989 / `JJG` 1,831 / `JJF` 1,223，而
  **`NB` 0 条、`CECS` 0 条、`DL` 2 条、`EJ` 4 条、`HAF`/`HAD`/`HAB` 0 条**。

**为什么不合理**

用户审的是核电/常规岛设计文件，行业标准（DL/NB/EJ/CECS）是高频引用，但库里**整类缺失**，
会大面积落进 `missing`。报告读者看到"未收录"极易理解成"这条标准号有错"。
对交付物来说，缺这句免责声明的后果比对话里说错更严重——对话有人追问，报告没有。

**修复方向**

报告固定附一条数据边界声明，包含本次判定所依据库的**覆盖范围**（可按 ident 前缀统计）：
「未收录 ≠ 标准不存在；本库当前未覆盖 DL/NB/EJ/CECS 等行业标准体系，此类引用需另行人工核对。」

---

### P1-3　审查开始时不做缓存新鲜度校验，可静默基于旧库出结论

**证据**

- 同步触发点只有两处（`packages/services/src/node.ts:2111` 登录钩子、`:2144` 应用启动补齐），
  与方案 §4.4.3 自述一致；**没有任何"审查开始时刷新"的触发**。
- `KnowledgeCheck` 只判 `stale`（缓存缺失/读取失败），`fetchedAt` 仅被写入 `stamp` 后**从不与当前时间比较**
  （grep `fetchedAt` 在 handler 内仅出现在类型与赋值处）。

**为什么不合理**

管理员今天发布新标准库、或把规范库置为 `published`，端侧要等用户**重启应用或重新登录**才生效。
在此期间审查会基于旧库出结论，且 `stale=false`、报告里也看不出快照有多旧。
`stamp.fetchedAt` 是现成的，判定逻辑却没用它。

**修复方向**

`stale` 之外增加"缓存年龄"判据：`fetchedAt` 超过阈值（如 24h）时返回提示性 `notice`
（如"库快照距今 N 天，建议先同步"），并在报告元信息里带出快照时间（与 P1-1 合并做）。

---

### P1-4　`rules` 把"服务器上没有已发布库"错判成 `stale`，给出无效指引

**证据**

- `apps/zcode-cli/packages/core/src/tool/handlers/knowledge-check.ts:575`：`stale: items.length === 0`。
- 实测服务器权威口径：`GET /v1/rule-libraries` → `{"items":[],"total":0}`，即**服务器上就是 0 个已发布库**。
- 工具返回的 notice：「规范库需要在管理台把状态置为「已发布」后才会下发」。

**为什么不合理**

`stale` 的语义按契约（`contracts/src/tools/knowledge-check.ts:120-121`）是
「缓存缺失或读取失败，结论不可当真」——这是**端侧缓存问题**。
但空库是**服务端的合法状态**，同步一百次也不会变。当前实现把两者混为一谈，
于是告诉用户"先同步知识库"（无效动作），且对**普通用户**提"管理台"（他不是管理员，界面里也没有管理入口）。

**修复方向**

`rules` 的空库应返回**非 stale** 的结构化结果（如 `items: []` + `notice: "当前无已发布的规范库，该能力不可用"`），
且 notice 面向普通用户，不提管理台操作。

## P2：信噪比与效率（建议修）

### P2-1　`missing` 不区分"库缺口"与"编号笔误"，可用现成数据拆开

**证据**

- `handlers/knowledge-check.ts:332-340` 与 `:370-378`：两种情况都返回同一个 message
  「标准库中无此编号：可能库待补充，也可能是编号笔误，需人工确认」，`severity: "warning"`。
- 判据只到**"编号族"**一层（`KEY_FAMILY`），即同一编号换前缀（`GB` vs `GB/T`）才命中 `not_in_library`；
  行业标准在库里连族都没有，一律落 `missing`。
- 但库数据里 `ident` 前缀分布是现成的：`GB` 5,181 / `GB/T` 3,989，而 `NB` **0** / `CECS` **0** / `DL` **2** / `EJ` **4**。

**为什么不合理**

自检的信噪比直接决定它能不能用。方案 §4.4.1 自述实测"6 条未收录里 5 条属行业标准缺失、1 条疑似笔误"——
两类混在一起，每条都要求人工确认，报告就退化成人工清单。而**判定所需的覆盖度统计就在同一份缓存里**，
不需要任何外部数据。

**修复方向**

按 `ident` 前缀覆盖率分流（确定性、零额外数据）：

- 该前缀在库中**近乎无覆盖**（如 NB/CECS/DL/EJ/HAF）→ 判为「该标准体系整体未收录」，
  `severity: info`，不计入问题、不进报告问题表，只在汇总里给一句库缺口说明。
- 该前缀**覆盖充分**但此编号不存在（如 GB/GB/T）→ 更可能是笔误或年代号写错，
  维持 `warning` 并要求人工确认。

### P2-2　术语白名单的覆盖域与实际审查的文件不匹配，校对防误报失效

**证据**

- `GET /v1/terminology/index` → 112 条，分类分布：核安全 48 / 设备 21 / 工艺 20 / 电气 14 / 建筑 9。
- 实测传入消防/给排水类候选词，**命中 0 条**：
  `消火栓 / 水喷雾 / 预作用 / 雨淋阀 / 集油坑 / 六爪喷嘴 / 固气转换剂 / 电引发器 / 组合分配系统 /
  磷酸铵盐干粉灭火器 / 超细干粉灭火装置 / 阀位监视装置 / 水流报警装置` 全部落入"需继续判断"。
- 方案 §4.4.1 自述白名单是"审查的**执行前提**"「校对要先排除专业词，否则核岛设计说明满屏误报，
  空库状态等于该能力不可用」。
- 而 `review-proofread` 的错词表是 **218 条**（核审通迁移），量级上白名单挡不住专业词误报。

**为什么不合理**

目标域（常规岛/消防/给排水设计说明）的专业词几乎全在白名单外，白名单对当前场景实际上不生效。
但流程上没有任何"覆盖域是否匹配当前文件"的判据，用户会拿到大量专业词误报且不知道原因。

**修复方向**

1. 补白名单（按"暖通/给排水/消防"域，与标准库的 475 条同类目对齐）。
2. 增加命中率观测：`terminology` 模式的 `remaining` 占比过高（如 >95%）时，
   在结果里提示"术语白名单可能未覆盖本文档领域"，避免用户把误报当成文档问题。

### P2-3　批量流程按"文件数"扇出，真正的成本驱动是文本量；且未提 5000 条上限

**证据**

- `review-batch/SKILL.md` 第 3 步：「≤3 个文件：顺序处理即可……>3 个文件：用 `CreateWorkflow` 按文件扇出」。
- `handlers/export-review-report.ts:241-245`：`if (parsed.issues.length > 5_000) throw`（直接抛错终止）。

**为什么不合理**

- 3 份各 5 万字的设计说明，比 10 份各 2,000 字的通知更难处理，但按文件数会走"顺序、不起工作流"。
- 5000 条上限 skill 里完全没提。批量审查一批大文件很容易撞上，撞上后是**硬失败**，
  没有"分批导出还是收敛范围"的指引。

**修复方向**

扇出判据改为"文件数 **或** 预估总文本量"；skill 里写明 5000 条上限与超限处置（分批导出）。

### P2-4　报告导出被当作 `edit` 权限 + 每次审批，批量场景反复打断

**证据**

- `handlers/export-review-report.ts:275-281`：`readOnly: false`、`riskLevel: "medium"`、`needsApproval: true`。
- `:296-305`：`permission: "edit"`、`needsApproval: true`、`alwaysAllowPatternSources: ["path"]`。
- `:68-80`：默认输出路径含时间戳（`<stem>-审查报告-<YYYYMMDD-HHmm>.<ext>`）。

**为什么不合理**

该工具**不改被审文件**，只写一个报告文件，却按"修改"级别审批。批量审查要出 `.docx` + `.xlsx` 就是两次审批；
而 `alwaysAllowPatternSources: ["path"]` 本想记住授权，但**路径带时间戳，每次都不同，记不住**——
于是每次都问。批量场景下会造成审批疲劳，用户习惯性点同意，反而削弱审批本身的意义。

**修复方向**

降级为写入 workspace 的常规权限（或按目录而非完整路径做 always-allow 匹配），
保留"改被审文件才需审批"的口径。

## P3：卫生与一致性（可择期）

### P3-1　正文快照无生命周期管理，且落在语义不符的目录

**证据**

- `handlers/knowledge-check.ts` 的 `persistReviewText(text, cacheDir)` 把被审文件**全文副本**
  写入 `~/.reactor/knowledge/review-text/<sha1>.txt`。
- 实测该目录已累积 3 个文件，其中 2 个是同一份文件的两次审查；无 TTL、无清理、无容量上限。
- 导出报告**不含快照路径**，报告交付后无法回溯对应快照。

**为什么不合理**

`knowledge/` 目录的语义是"知识库缓存"（写入方是同步服务），不是"审查留痕"。
把含敏感工程内容的全文副本放在这里，既无清理策略也无访问边界，
且与报告的生命周期完全脱钩（报告可交付留存，快照却随时可能被清或长期堆积）。

**修复方向**

拆出独立的审查留痕目录（或明确 TTL + 容量上限），并在报告元信息里记录快照标识，
使报告与快照可对应。

## 专项：一处"文档声称已生效、实际不成立"的隔离

### S-1　「企业令牌不进入 Agent 进程」是约定，不是强制边界

**证据**

- 契约注释（`contracts/src/tools/knowledge-check.ts:12-14`）声称：
  「企业令牌只存在于桌面主进程/渲染进程的凭据存储里，**Agent 进程拿不到（也不该拿到）**」。
- 但 `packages/services/src/credential/providers/credentialCipherProvider.ts`
  在 `ZCODE_CREDENTIAL_SECRET` 未设置时（实测本机未设置）退回可推导密钥：
  `zcode-credential-fallback:${os.platform()}:${os.homedir()}:${userInfo().username}`
  → 即 `zcode-credential-fallback:win32:C:\Users\24800:24800`，**全部是公开可推导信息**。
- 实测：用 `sha256(该串)` 作 AES-256-GCM 密钥，成功解出 `~/.reactor/v2/credentials.json`
  里的 `reactor:accessToken`，并直连 `http://127.0.0.1:8791` 打通三个消费面接口：
  `/v1/standards/index`（200，13,445 条）、`/v1/terminology/index`（200，112 条）、
  `/v1/rule-libraries`（200，0 条）。

**为什么不合理**

"令牌不进入 Agent 进程"是"判定可复现/离线可用"这条设计的信任基础，
但它目前只是**写法上的隔离**。任何能以同一 OS 用户运行代码的进程都能拿到令牌并直连服务器，
绕过端侧缓存——即绕开"同一文件 + 同一库 = 同一结论"里的快照语义。

代码注释已自述「后续可切换到 Electron safeStorage（钥匙串）托管密钥」，所以是**已知待办而非新 bug**。
但需注意：**管理面的角色边界是真生效的**（实测 `/admin/standards`、`/admin/terminology`、
`/admin/rule-libraries` 对 role=user 一律 403「仅平台管理员可操作」，
`/me/nav` 只下发 `["account"]`）。只有令牌本身的保护偏弱。

**修复方向**

若"Agent 不应能读取企业令牌"是硬要求，需切钥匙串托管，或让 Agent 进程**根本无法读取该文件**
（当前是靠约定而非权限）。若是软要求，则应在契约注释与方案文档里如实改口径，不要写成已生效的边界。

> 复现注意：Node `os.platform()` 在 Windows 返回 `win32`，写成 `windows` 会得到 `InvalidTag`。
