# 网关模型能力同步桌面端 ModelConfig（方案 v1）

> **日期**：2026-10-13　**状态**：已拍板，实现中
> **上游**：`packages/shared/src/model-config.ts`（桌面端 ModelConfig 契约）、`server/packages/server/src/gateway/{registry,proxy}.ts`（网关目录）
> **要解决的问题**：管理台在网关加的模型，桌面端拿到后**只有 id**，上下文窗口、最大输出、
> 多模态、推理档位全部丢失，导致四类现象（见 §1）。

---

## 1. 根因（已核实，非推测）

服务端网关 `/v1/models` **早已下发**完整能力（`gateway/proxy.ts` `listModels`）：

| 下发字段                                                                           | 来源                    |
| ---------------------------------------------------------------------------------- | ----------------------- |
| `context_length`                                                                   | `ai_models.max_context` |
| `max_completion_tokens`                                                            | `ai_models.max_output`  |
| `supports_tools` / `supports_reasoning` / `supports_vision` / `supports_anthropic` | `ai_models.features`    |
| `features` / 四段价 / 币种                                                         | `ai_models`             |

但客户端接收段把它们**整段丢弃**：

```
reactorServerClient.ts  models()      → 只解析 id / model_type / display_name
reactorServerService.ts syncModels()  → 只取 id 数组
reactorServerService.ts reconcileProviderModels()
                                     → addPersonalModel(providerId, modelId, {}, true)
                                        config 传空对象；注释称"由 provider 侧推荐配置补齐"，
                                        但网关 provider 的推荐配置里没有这些元数据
```

因此桌面端的网关模型实际使用**兜底推断值**，表现为：

1. 上下文窗口 / 最大输出与管理台配置**不同步**（客户端从未接收这两个值）；
2. 管理台标了 `vision`，桌面端 `inputFormat.supportsImage` 仍为 false；
3. 推理档位：网关只有布尔 `supports_reasoning`，桌面端 `optionSpecs.reasoningLevel`
   需要**带可选值集合的 enum spec**，无法从布尔推导；
4. 桌面端打开思考后请求带上上游不认的参数 → **必须关闭思考才能正常对话**。

---

## 2. 方案（大王拍板：方案 A + 两者结合）

**核心**：补齐客户端接收段，让管理台已配的数据真正到达桌面端；推理档位服务端可配、
桌面端有族推断兜底。

### 2.1 服务端（`server/` workspace）

`ai_models.params`（jsonb，**已存在**，rerank 的向量维度已在用）新增两个可选键，
**不改表结构、不加 migration**：

| 键                 | 类型       | 语义                                                                      |
| ------------------ | ---------- | ------------------------------------------------------------------------- |
| `reasoning_levels` | `string[]` | 推理档位可选值，按语义强度从低到高（如 `["disabled","enabled"]`）         |
| `reasoning_map`    | `string`   | 受限 CEL 表达式，把档位值 patch 进请求体；缺省 `"{}"`（**不写任何字段**） |

- `gateway/registry.ts`：`ModelEntry` 增补 `reasoningLevels: readonly string[]`、
  `reasoningMap: string`，从 `params` 解析并归一化（非法值回落缺省，不抛错）。
- `gateway/proxy.ts` `listModels()`：下发体增补 `reasoning_levels` / `reasoning_map`。
- `gateway/admin-schema.ts` + `admin-routes.ts`：管理台模型编辑支持这两个键（存进 `params`）。

### 2.2 客户端（主仓）

- `reactorServerClient.ts`：`ReactorServerModelInfo` 扩展为全字段
  （`contextWindow` / `maxOutputTokens` / `supportsTools` / `supportsReasoning` /
  `supportsVision` / `reasoningLevels` / `reasoningMap`），`models()` 全部解析。
- `reactorServerService.ts`：`syncModels()` 传完整模型信息；
  `reconcileProviderModels()` 用真实能力构造 `ModelConfigObject`，**不再传 `{}`**。
- 新增纯函数 `buildGatewayModelConfig(model)`（放 `packages/services/src/reactor-server/`）：
  网关模型 → 桌面端 `ModelConfigObject`，含**模型族推断兜底**。

### 2.3 映射口径（`buildGatewayModelConfig`）

```
properties.contextWindow        ← contextWindow            （缺省不写，走端侧既有兜底）
properties.inputFormat          ← supportsText: true
                                  supportsImage: supportsVision
                                  supportsVideo/Audio/Pdf: false（网关无此信息，保守 false）
properties.outputFormat         ← supportsText: true
properties.supportsToolCall     ← supportsTools
properties.supportsJsonSchemaOutput / supportsNativeWebSearch
  / supportsMidConversationSystem / requiresMfjsToolSchema
                                ← false（网关无此信息，保守 false）
optionSpecs.maxOutputTokens.max ← maxOutputTokens          （缺省不写）
optionSpecs.reasoningLevel      ← values: reasoningLevels  （空则不写整个 spec）
                                  map:    reasoningMap     （缺省 "{}"）
```

**族推断兜底**（仅当服务端未配 `reasoning_levels` 且 `supports_reasoning` 为真时）：
按模型 id 前缀给 `["disabled", "enabled"]`，`map` 固定 `"{}"`。
选 `"{}"` 而非真实字段名是**刻意的安全缺省**：宁可思考强度不写进请求（功能降级），
也不能让"开思考"直接 400 —— 那正是本次要修的现象。

### 2.4 明确不做

- 不改 `ai_models` 表结构（复用 `params`）。
- 不动桌面端 ModelConfig schema 本身（`packages/shared/src/model-config.ts` 零改动）。
- 不动专家（server agents）的 `policyMode` / `thinkingLevel` 机制。
- 不引入新的环境变量或新的下发通道（仍走 `/v1/models` 这一个接口）。

## 4. 2026-10-14 补充：v1 上线后发现的两个缺陷（已修）

v1 落地后大王实测反馈「在服务端配置好了上下文参数和支持多模态，桌面端还是默认的初始状态」。
核实后确认**不是解析问题、不是打包问题**，而是同步链路有两处主动放弃更新：

### 4.1 缺陷一：`reconcileProviderModels` 跳过已存在的模型

`reconcileProviderModels` 里原有 `if (currentSet.has(model.id)) continue;`。
这个 `continue` 本是必要的防御 —— `addPersonalModel` 对已存在的模型会直接 throw
`Model 已存在`（见 `packages/provider/src/config-service.ts`）。

但它带来一个隐蔽后果：**端侧永远停在首次登录时那份配置**。管理员后来在管理台改的
上下文窗口 / 最大输出 / 多模态 / 推理档位，桌面端一律当"已存在"跳过，永不下发。
（用户侧表现就是"服务端配了，桌面端不生效"。）

**修复**：新增 `refreshGatewayModelConfig()`，对已存在模型走
`providerSettings.savePersonalModelDraft()` 刷新配置，而非删了再建
（后者会丢掉用户自己排的模型顺序，且中间态会被 UI 看到）。要点：

- `basedOnRevision` 必须**现取** —— 该接口带乐观锁，同一轮 reconcile 里上一条模型的写入
  已让快照 revision 前进，复用旧值必然冲突；
- **不传** `useRecommendedConfig` —— 传 true 会把规则类型从 `manual-provider-model`
  改写成 `provider-model`（推荐规则），让"恢复推荐配置"之类的操作有机会把它冲掉；
  传 false 则相反。缺省值保持模型原有类型，只更新配置内容本身；
- 单条失败只记 `warn`，不阻断整轮同步（一个坏模型不能让整份目录对不齐）。

### 4.2 缺陷二：`syncModels()` 只在登录时调用

即使修好 4.1，用户不重新登录仍拿不到新目录 —— `syncModels()` 原本只在 `login()` 里调用
（`reactorServerService.ts` 的登录成功分支），启动链路只 bootstrap 用量上报与策略缓存。

**修复**：在 `bootstrapOnStart` 分支里补一次 fire-and-forget 的模型目录同步
（未登录则直接返回）。管理员改完配置、用户重启桌面端即生效，不必重新登录。

### 4.3 验收（本轮新增，均真实执行）

| #   | 场景                                                       | 期望                                                   |
| --- | ---------------------------------------------------------- | ------------------------------------------------------ |
| 7   | 模型已存在时执行同步                                       | 走 `savePersonalModelDraft`，不再 `continue` 跳过      |
| 8   | 服务端改能力后再次同步                                     | 新值真正写下去（不是只加不更新）                       |
| 9   | 新模型 / 下线模型                                          | 仍走 `addPersonalModel` / `deletePersonalModel`（回归）|
| 10  | 单条模型刷新失败                                           | 只记日志，其余模型照常处理，`syncModels` 不 reject     |
| 11  | 启动时（已登录）                                           | 自动同步一次模型目录                                   |
| 12  | 启动时（未登录）                                           | 不做同步、不发请求                                     |

测试：`packages/services/test/gatewayModelReconcile.test.ts`（6 例全绿）。

## 5. 2026-10-14 补充：推理档位配置改点选（管理台）

大王反馈推理档位的两个自由文本框（逗号分隔档位 + CEL 表达式）"太复杂，不知道怎么填写"。
v1 的实现假设管理员既知道上游认哪个参数名、又会写 CEL，实际没人填得对。

**改为语义化点选**：`server/packages/admin/src/lib/reasoning-presets.ts` 新增预设表，把
「档位集合 + 请求体映射」捆成一个选项（不支持思考 / 思考开关不传参 / `reasoning_effort` /
`thinking`（智谱）/ `enable_thinking`（通义）），模型编辑表单只暴露一个下拉；
「自定义（高级）」展开后才显示原来的两个文本框。**存储格式不变**
（仍是 `params.reasoning_levels` + `reasoning_map`），服务端契约与桌面端消费逻辑零改动。

**关于"智能检测"的边界**（明确记录，避免过度承诺）：这里做的是**按模型 id/显示名保守匹配
+ 预填**，不是真的探测上游支持什么 —— 探测需要发真实请求、花 token，且结果随上游版本变化，
做成隐式自动行为风险更大。预填值管理员看得见、能改，配完可用模型行上既有的「测试」按钮
发一次真实调用验证。匹配不上的模型一律落「思考开关（不传参）」安全缺省。

冒烟：`pnpm --filter @reactor/admin smoke:reasoning-presets`（33 项，含一条安全断言：
任何非 `off` 预设在 `disabled` 档都不许往请求体写字段 —— 否则等于把"打开思考就 400"
这个故障扩大到所有档位）。

## 6. 2026-10-14 补充：桌面端「高级配置」剩余 6 项能力也走服务端下发

v1 只同步了上下文窗口 / 最大输出 / 视觉 / 工具调用 / 推理档位。桌面端
`ModelConfig`（`packages/shared/src/model-config.ts`）共 14 个高级配置项，
其中 9 项此前在端侧**写死**，管理台勾不勾都一样：

| 端侧字段 | 扩量前 | 扩量后 |
| --- | --- | --- |
| `inputFormat.supportsVideo/Audio/Pdf` | 硬编码 false | `supports_video/audio/pdf` |
| `supportsJsonSchemaOutput` | 硬编码 false | `supports_json_schema` |
| `supportsNativeWebSearch` | 硬编码 false | `supports_native_web_search` |
| `supportsMidConversationSystem` | 硬编码 false | `supports_mid_conversation_system` |

**复用现有机制，不加表、不加列、不动 `params`**：`ai_models.features` 本就是 JSONB 数组，
管理台也早有「能力标记」勾选组，缺的只是三个地方的枚举各加 6 个值
（`registry.ts` 的 `KNOWN_FEATURES`、`proxy.ts` 的下发体、`ModelsAndProviders.tsx` 的
`FEATURES`），客户端把 `buildGatewayModelConfig` 里对应的 6 处硬编码 false 换成读真实值。

**安全性**：未勾选 = 不下发 = 端侧 false，与扩量前的硬编码行为**完全一致**，
所以不会让任何现有模型突然"多出能力"。

**刻意不暴露的两项**：
- `requiresMfjsToolSchema` —— 桌面端内部工具 schema 转换开关，与"模型支持什么"无关，
  暴露到管理台只会让人困惑，因此没有对应的网关字段，端侧恒 false。
- `anthropic` —— 协议标记（决定走哪套 API 格式），不是模型能力，桌面端 `ModelConfig`
  没有对应字段，因此仍只作为协议标记使用、不下发成布尔能力。

**白名单职责划分**（冒烟里钉住的事实，避免按错的理解写断言）：`hasFeature` 的运行时实现就是
`entry.features.includes(feature)`，**不过滤**；过滤分在三处 —— 编译期入参类型
`KNOWN_FEATURES[number]`、管理台保存时 `FEATURES` 常量过滤、`proxy.ts` 只对 9 个已知 key
调 `hasFeature`。`registry` 则全量保留 `features`（未知 key 原样进 entry，但永远不会被下发）。

**验收**：`pnpm --filter @reactor/server smoke:admin`（能力标记断言）、
`packages/services/test/gatewayModelConfig.test.ts`（9 例，含"勾选后 6 项原样到达桌面端"
与"未勾选一律 false"两条反向用例）。
