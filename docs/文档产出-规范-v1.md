# 文档产出规范 v1

Reactor 自己生成 `.docx` / `.xlsx`（审查报告、Markdown 导出）时，排版只有一处来源：**
`packages/shared/src/document-style.ts` 的排版令牌 + 各自包内的样式表适配器**。

这份规范解决的是一个具体的坏结果：报告"丑"不是审美问题，而是**排版被交给了读者本机的 Word**。
早期版本 `new Document({ sections })` 里没有 `styles`，生成的 `word/styles.xml` 中
`<w:docDefaults><w:rPrDefault/><w:pPrDefault/></w:docDefaults>` 是空的，于是同一份报告在不同机器上
字体不同、表格列宽由 Word 自动分配决定，七列长表里的「序号 / 严重度」被压成竖排两行。

## 1. 适用范围

| 输出 | 位置 | 样式表 |
| --- | --- | --- |
| 审查报告 `.docx`（横向 A4、七列长表） | `apps/zcode-cli/packages/core/src/report/report-docx.ts` | `report/docx-style.ts` |
| 审查报告 `.xlsx`（问题清单 + 摘要） | `apps/zcode-cli/packages/core/src/report/report-xlsx.ts` | `report/docx-style.ts`（列定义同源） |
| Markdown 导出 `.docx`（纵向 A4、流式长文） | `packages/ui/src/lib/markdownToDocx.ts` | `packages/ui/src/lib/docxStyle.ts` |

**不在适用范围**：用户提供的文件本身。`docx_patch` 的设计前提就是**保留原文档格式**，
只改 `<w:t>` 文本节点；给别人的文件套我们的样式是 bug 而不是功能。

两条链路不能共用一份样式定义，因为 `ui` 与 `zcode-cli` 在架构策略里是两个独立模块
（UI 依赖 Agent-CLI 包会把运行时打进渲染进程）。所以**共享的是令牌值，映射各写一份**：
改字号字体只改 `document-style.ts` 一处，两边一起变。

## 2. 令牌（唯一来源）

`DOCUMENT_STYLE_TOKENS` 是纯数据，单位是人的单位（pt / mm / 倍行距 / 十六进制色），
到 OOXML 单位（half-point / twip / 240 分之一行）的换算由同文件的函数负责 —— 换算只准有一份实现。

- **字体**：标题 `微软雅黑`（西文 Arial）、正文 `宋体`（西文 Times New Roman）、等宽 `Consolas`。
  中西文两组都要写（`w:ascii` + `w:eastAsia`），并带 `w:hint="eastAsia"`；
- **字号**：报告标题 18pt、一级标题 14pt、二级 12pt、正文 10.5pt（五号）、表格 9pt（小五）、页脚 9pt；
- **颜色**：正文黑、次要信息 `595959`、表头底纹 `E7E6E6`、注释底纹 `F2F2F2`；
  严重度 `C00000`（必须修改）/ `BF8F00`（建议修改）/ `595959`（提示）；建议 `1F7A3D`；
- **表格**：外框 1pt `808080`、内线 0.5pt `BFBFBF`、单元格内边距上下 3pt / 左右 5.4pt；
- **页面**：A4，上下 20mm、左右 18mm 版心。

## 3. 样式表结构

样式定义分三档，**生成器只准挑样式名**：

1. **`docDefaults`**（`styles.default.document`）：正文体、10.5pt、1.3 倍行距、段后 6pt。
   这是地基 —— 不写它，字体字号就由读者本机 Word 决定。
2. **内置样式覆盖**（`styles.default.title / heading1..3`）：报告标题居中加粗、标题黑体加粗，
   **必须覆盖颜色** —— `docx` 库给内置标题默认带蓝色 `2E74B5` / `1F4D78`，中文工程文件里是错的。
   注意库是「先展开 `{id, name}` 再展开传入的 options」，传 `id` 会把 styleId 覆盖成空。
3. **自定义样式**（`paragraphStyles` / `characterStyles`）：
   - 段落：`ReactorMetaLabel` / `ReactorMetaValue`（元信息键值）、`ReactorTableHeader` / `ReactorTableBody` /
     `ReactorTableMeta`（表格三档）、`ReactorNote`（注释块，浅底 + 左竖线）、`ReactorFooter`（页眉页脚）、
     `ReactorCodeBlock` / `ReactorQuote`（Markdown 导出）；
   - 字符样式：`ReactorSeverityError/Warning/Info`、`ReactorSuggest`、`ReactorCode`。

## 4. 验收不变量（`test/document-style.test.ts`、`test/markdownToDocx.test.ts`）

文档写一百遍不如一条断言。以下每条都有测试钉住，**绕过样式表就会红**：

1. `word/document.xml`、`word/header1.xml`、`word/footer1.xml` 里每个 `<w:rPr>` **只准**包含
   `w:rStyle` —— 出现 `w:rFonts` / `w:sz` / `w:color` 即判定绕过了样式表。
   报告侧连 `w:b` / `w:i` 一起禁；Markdown 导出允许它们，因为 `**粗体**` 是**内容语义**
   （等同于用户按 Ctrl+B），不是排版。
   断言的另一半是「样式表里必须真的有字体字号」—— 否则全都不设也能"通过"。
2. 内置标题不得保留 `2E74B5` / `1F4D78`，且必须加粗、指定中文字体。
3. 表格：`tblLayout=fixed` + 每条 `gridCol` 与样式表算出的列宽一致 + **列宽之和等于版心宽度**。
   总和对不上时 Word 会把表格拉出正文区或在窄列上再挤一次 —— 这正是「序号」竖排两行的成因。
   余数补给最后一列（`columnWidthsFromPercents`），每列还要自带 `tcW`。
4. 表头行有底纹、`tblHeader`（跨页重复）、行 `cantSplit`（一条问题不被页码切开）。
5. 页面尺寸与页边距来自令牌；页脚是 `PAGE` / `NUMPAGES` 域（并置 `updateFields`，否则页数停在生成时的缓存值）。
6. 文档属性必须有 `dc:title` 与 `dc:creator=Reactor`（此前是 `Un-named` 且无标题）。
7. **docx 与 xlsx 信息口径一致**：`conclusion`（结论状态）、`coverage.referenceCount`（核对引用数）、
   库快照、覆盖缺口，两种格式都要有 —— 收报告的人可能只看其中一种。
   口径由 `report/report-content.ts` 的 `reportMetaRows()` 一处产出，两个渲染器各自排版。

## 5. 布局规则

- **列数决定纸张方向**：报告问题表是 7 列且三列是大段中文，必须横向 A4
  （纵向版心只有 15.9cm，每列不到 2.3cm）；Markdown 导出是流式长文，纵向。
  注意 `docx` 的 `width/height` 要传**纵向**尺寸，横向由 `orientation` 让它自己换 —— 换两次会换回纵向。
- **列宽配比**（`REPORT_TABLE_COLUMNS`）：序号 5 / 严重度 8 / 类别 12 / 位置 16 / 原文片段 18 /
  问题说明 23 / 建议 18（合计 100）。xlsx 列宽按同一份配比摊开，只是总量更大（Excel 可横向滚动）。
- **元信息排成两列小表**（项 / 值、无边框），不排成一串等权正文：眼睛要能直接落到「结论状态」那一行。
- **注释块不提升为标题**：数据边界、免责话术用 `ReactorNote` 的浅底 + 左竖线，
  用 Heading 会让人误以为是章节。
- **颜色只表达"这条要干什么"**：严重度列按值着色、建议列绿色、编号列等宽灰、位置列次要灰。

## 6. 新增一种文档产出时

1. 先确认它属于「Reactor 生成」还是「用户文件」—— 后者一律不套样式；
2. 只从 `DOCUMENT_STYLE_TOKENS` 取值，缺的令牌往 `document-style.ts` 加（不要在生成器里写死颜色字号）；
3. 在对应包内写适配器把令牌映射成 `docx`/`exceljs` 的样式定义（不要跨包 import 另一侧的适配器）；
4. 补一条不变量测试：解包 + 断言 `rPr` 只有 `rStyle`、列宽之和等于版心、文档属性有标题；
5. 渲染出来看一眼（见下）。

## 7. 怎么验收「真的变好看了」

解包看 XML 只能证明属性写对了，证明不了 Word 打开后的样子。视觉验收要真渲染：

```bash
# 1. 生成样张：字段用真实的（不要 aaa/bbb 占位），否则看不出列宽是否够
# 2. 逐页渲染成 PNG（同时打印每页尺寸与列宽，作为可复核的证据）
pnpm render:docx <样张.docx> .tmp-render
# 3. 逐页看图判定
```

`pnpm render:docx`（`scripts/render-docx-pages.mjs`）用仓库里已有的 `docx-preview`（应用内
docx 预览用的就是它），按 OOXML 的 `tblGrid` / `shd` / `borders` / `rFonts` 渲染，
用独立浏览器进程，不碰运行中的应用。**保真度边界**：页眉页脚与页码域不如 Word ——
本机 Word 自动化被系统策略拒（`0x800702E4` 需要提升），这两项改由单测从 XML 断言。

判定标准（按用户能否接受，不看代码）：

- 每个单元格都放得下自己的内容，没有被压成竖排或从词中间断开；
- 表头与表体一眼可分，表头在跨页处重复；
- 标题层级、表格文字、注释块三类信息的字号与灰度分明；
- 颜色只在有语义处出现（严重度、建议），占位的「—」不着色；
- 正文里不出现 markdown 记号（`**粗**`、反引号）—— 报告没有渲染器，会原样印出来。
