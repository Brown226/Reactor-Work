## 1. 产品规则（用户看得见的行为）

| #   | 规则                                                                                                            | 备注                                                    |
| --- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| R1  | 客户端可配置"企业服务端地址"，登录后进入**企业模式**；未登录时行为与今天完全一致（官方账号继续可用）            | 企业模式是**叠加**，不替换官方登录（P4 才谈解耦）       |
| R2  | 企业模式下，模型调用**统一走企业网关**，调用可归属到人；模型清单由服务端下发                                    | 服务端硬约束：`/v1/models` 与模型可见范围由令牌身份决定 |
| R3  | 令牌过期时**无感刷新**；刷新失败则明确提示"需要重新登录"，绝不静默降级成直连上游                                | 静默降级 = 绕过治理，是安全事件                         |
| R4  | 企业模式下可"下载/更新"服务端下发的**技能**与**数字人（Agent）**；用户本机自建的技能/Agent **不受影响**、可共存 | 同名冲突规则见 §4.3                                     |
| R5  | 服务端下发的技能/Agent 在列表里**可区分来源**，且不能被误删成"用户自建"                                         | 需要可辨识 + 可整体回收                                 |
| R6  | 企业模式下模型调用的 token 用量**上报服务端**（否则管理台用量/额度报表为空）                                    | 服务端网关**不写审计**，用量只能由端侧上报              |

**非目标（本方案不做）**：把官方 OAuth 登录换掉；把桌面端工具调用审计（tool_call/approval）上报服务端（那需要旧项目 sidecar 的能力，属后续阶段）；知识库（KB）客户端侧接入。

## 2. 状态所有者与唯一写入路径

> 原则：**一处状态一个所有者**。下面每个"状态"都只有一个写入者；其余模块只读或通过该所有者变更。

| 状态                                    | 所有者（唯一写入点）                                                   | 落盘位置                                            | 备注                                                                                                                            |
| --------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 服务端地址                              | `IReactorServerService`                                                | `ICredentialService` 键 `reactor:serverUrl`         | **不写 AppSettings**：地址与登录态同生命周期，放两处就是"同一事实两个所有者"；也免得动 `protocol.ts`/`validationAppSettings.ts` |
| 企业登录令牌（access/refresh/网关令牌） | 新增 `IReactorServerService`                                           | `ICredentialService` 键 `reactor:*`（AES-GCM 加密） | 不写 preload bridge（仓库明文约定：凭据不进 `window.zcode`）；**网关令牌只在内存**，从不落盘                                    |
| 企业 provider 条目                      | `IReactorServerService` 经 `ProviderConfigService` 写 personal overlay | `{数据根}/v2/provider_config.json`                  | 走既有 overlay 写面；识别靠 baseUrl，id 记在 `reactor:providerId`                                                               |
| 企业模式开关                            | `IReactorServerService`（由登录态派生，不单独存）                      | —                                                   | "登录成功且 access 未过期"即企业模式                                                                                            |
| 服务端技能落盘                          | 新增 `IServerSkillSyncService`（待定名）                               | 见 §4.3 决策                                        | 与现有 `skillsService` 的发现目录**隔离**                                                                                       |
| 服务端 Agent 落盘                       | 同上                                                                   | 见 §4.4                                             | 复用 subagent markdown 格式                                                                                                     |
| 用量上报队列                            | 新增上报器（唯一写入者）                                               | 内存 + 失败落盘（待定）                             | 幂等键 `eventId`（服务端已支持去重）                                                                                            |

### 2.1 登录与模型调用时序（所有者 / 事件顺序）

```
Renderer(设置页)         Host: ReactorServerService        Server
     │  ① 输地址+账号密码          │                          │
     ├────────────────────────────►│                          │
     │                             │ ② POST /auth/login       │
     │                             ├─────────────────────────►│
     │                             │ ◄── {accessToken,refreshToken,user}
     │  ③ 写入 credential(reactor:*)│                          │
     │                             │ ④ POST /auth/gateway-token
     │                             ├─────────────────────────►│
     │                             │ ◄── {token, expiresIn}   │
     │                             │ ⑤ GET /v1/models（带网关令牌）
     │                             ├─────────────────────────►│
     │                             │ ◄── 模型目录              │
     │                             │ ⑥ 写 provider_config.json（企业 provider + 模型清单）
     │ ◄── 登录成功/模型可用         │                          │

会话中（每个物理模型请求前一次）：
CLI(agent) ──interaction/requestProviderRuntimeHeaders──► Host(zcodeAgentService)
                                                          │ 若 providerId = 企业 provider
                                                          │ → 取最新网关令牌（过期则先换）
            ◄── {headersApplied:true, requestAuth:{apiKey}} ─┘
CLI ──► 企业网关 /v1/chat/completions（Authorization: Bearer <网关令牌>）
```

**关键点**：网关令牌**不进配置文件**，每次请求由 Host 现场解析 —— 因此不存在"令牌写进 2h 前的配置文件、过期后全部 502"的问题。

## 3. 服务端契约（客户端必须遵守的部分）

### 3.1 身份（身份进程，默认 `:8791`）

| 接口                       | 请求                       | 响应                                           | 注意                               |
| -------------------------- | -------------------------- | ---------------------------------------------- | ---------------------------------- |
| `POST /auth/login`         | `{username,password}`      | `{accessToken,refreshToken,user}`              | 本地/LDAP 同接口，无 mode 字段     |
| `POST /auth/refresh`       | `{refreshToken}`           | `{accessToken,refreshToken}`                   | **滚动轮换**，必须存回新的 refresh |
| `POST /auth/logout`        | Bearer access              | `{ok:true}`                                    | 只吊销 refresh                     |
| `POST /auth/gateway-token` | Bearer access，**无 body** | `{token,audience:"gateway",expiresIn,subject}` | 网关令牌 TTL 默认 = access TTL     |
| `GET /me`                  | Bearer access              | `{user,scope}`                                 | 用来自检登录态                     |

- access 默认 **2h**、refresh **7d**；`aud` 分别为 `access` / `refresh` / `gateway`，**不可混用**（混用必然 401）。
- **必须处理 `x-new-token` 响应头**：access 剩余 < 5 分钟时，任何鉴权请求的响应会带一个新 access。不处理 → 2 小时后全量 401。
- 错误体 `{error:{code,message}}`；`code` 多为字符串化的 HTTP 状态。**LDAP 不可用是 500**（不是 401），文案要与密码错误区分开。

### 3.2 网关（网关进程，默认 `:8790`）

- 路由：`/v1/chat/completions`、`/v1/messages`、`/v1/embeddings`、`/v1/rerank`、`/v1/models`、`/health`。
- 鉴权头：`x-api-key` **优先**，其次 `Authorization: Bearer`。客户端统一用后者即可。
- 回执头（用于诊断，建议在日志里留痕）：`x-reactor-auth`(user/dev)、`x-reactor-subject`(uid)、`x-reactor-upstream`、`x-reactor-clamped`、`x-reactor-catalog`。
- 错误体含 `type`：`authentication_error` / `model_forbidden`(403，模型不在可见范围) / `model_not_found`(404，带 `available_models`) / `protocol_mismatch`(400) / `config_error`(503)。
- `/v1/models` 每项含 `id/display_name/model_type/context_length/max_completion_tokens/supports_*/prices...`；**`model_type` 是区分 chat/embedding/rerank 的唯一依据**（db 目录会把所有板块混在一个列表里）。

### 3.3 技能 / Agent / 审计

| 用途                               | 接口                                                                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 技能注入集（启用态，用于内核）     | `GET /me/skills/state?workspaceKey=`                                                                                       |
| 技能落盘集（可见 ∩ 已安装/自动装） | `GET /me/skills`                                                                                                           |
| 技能详情（含正文与附件清单）       | `GET /me/skills/:name`                                                                                                     |
| 附件内容（按需）                   | `GET /me/skills/:name/file?path=` → `{content}` 或 `{contentB64}`，附 `size/sha256`                                        |
| 安装/启停/收藏/使用上报            | `POST                                                                                                                      | DELETE /me/skills/:name/install`、`PUT                                       | DELETE /me/skills/:name/enabled`、`POST /me/skills/:name/use` |
| Agent 目录                         | `GET /me/agents`（一次性返回，无分页）                                                                                     |
| Agent 安装/启停/收藏/使用          | `POST                                                                                                                      | DELETE /me/agents/:name/install`、`PATCH /me/agents/:name/install {enabled}` |
| 用量/审计上报                      | `POST /desktop/audit/batch`（≤500 条；**body 带 uid/deptId 会 400**；`summary`≤200 字；`cost` 服务端优先按自身价目表核算） |
| 策略天花板                         | `GET /desktop/policy` → `DesktopPolicy`                                                                                    |

⚠ 三条容易踩的：

1. `/me/skills` 与 `/me/skills/state` **语义不同**（落盘集 vs 注入集），别互相替代。
2. 可见性过滤**全在服务端 SQL**完成，响应里**不含 scope 字段**；客户端拿到即已过滤，不要再自己判断。
3. 身份进程**没有 `/health`**；探活只能用 `POST /auth/login` 的错误码或 `/me`。

## 4. 关键设计决策（含取舍理由）

### 4.1 服务端地址与官方端点分开

**决策**：服务端地址存 `ICredentialService` 的 `reactor:serverUrl`（**不新增 `AppSettings` 字段**），网关地址由它推导（同主机、端口换 8790、路径 `/v1`）。

**理由**：① 与官方链路彻底隔离——`zcodeEndpointOrigin` 承载官方 CDN/配置/分享等官方服务（`rewriteZCodeEndpointUrl` 会把 `zcode.z.ai` 改写到它），把企业服务端塞进去会一次性改变一堆官方链路的行为，且与"官方服务先保留"的既定方针冲突；② 地址与登录态同生命周期，放 AppSettings 与凭据库两处就是同一事实两个所有者，还得顺带改 `protocol.ts` + `validationAppSettings.ts`。

### 4.2 模型出口：企业 provider + 每请求现取令牌（**含一处 CLI 改动**）

**决策**：

1. 登录成功后，在 **personal overlay** 写入一个 provider：`api.type=openai-chat-completions`、`api.baseUrl={网关}/v1`、`access.type=api-key`、`apiKey` 写**哨兵值** `managed-by-reactor-server`。
2. 模型清单**不能**靠 overlay 的 `personalModelIds` 字段写入——`savePersonalProviderOverlay` 会用"已存配置的模型成员关系"覆盖它（真机踩坑，见 §4.6-4）。必须逐个调用 `addPersonalModel` / `deletePersonalModel` 对齐到网关 `/v1/models` 的 chat 板块。
3. 该 provider 的 id **由 baseUrl 反查**得到（`createPersonalProvider` 的 id 是配置服务生成的，客户端无权指定），并把 id 记进 `reactor:providerId`，模型请求热路径据此做 O(1) 判断。
4. **CLI 侧新增一个识别条件**：`apps/zcode-cli/packages/adapters/src/model/runner.ts` 里决定"是否消费调用级 runtime header Port"的表达式，加上 `apiKey === 哨兵值` 这一支；哨兵常量定义在 `@zcode/shared`，两侧共用。
5. Host 侧在 `interaction/requestProviderRuntimeHeaders` 处理链**新增一条分支**（排在账号分支之前）：provider 命中企业 provider → `IReactorServerService.resolveGatewayAuth()` 现场换令牌 → 回 `{headersApplied:true, requestAuth:{apiKey}}`。写法与日志字段照抄 `respondAccountRequestAuthWithoutInteraction`。

**为什么必须动 CLI**（这是实现阶段实测出来的、与初稿不同的关键点）：`runner.ts` 原逻辑是「**只有 `access.type === "zhipu-account"` 的账号型 Model 才消费 runtime header Port**；普通 API-key Model 若也消费，会把静态鉴权误送到 Host 刷新并在请求前失败」。也就是说普通 api-key provider 走的是配置里的静态密钥，**根本不问 Host**。因此"令牌不落盘"这条路必须有 CLI 的配合；用哨兵值（而不是伪造 `zhipu-account` 类型）是让这个判断显式、可读、不污染账号语义。

**为什么不用"把令牌写进配置文件 + 定时刷新"**：初稿考虑过（配置仓库有 1s 轮询，改完能传播）。放弃的理由是：网关令牌 TTL 只有 2h，落盘就要处理定时刷新、休眠唤醒、以及"配置里的旧令牌让整轮请求 502"的窗口，而且令牌明文进配置文件；现方案令牌只存在于内存与加密凭据库，且**每次请求都是新的**。

### 4.3 技能下发：新增独立目录 + 新增来源标记

**决策**（推荐方案，代价明确）：

1. 落盘到用户级独立目录：`{数据根}/server-skills/<name>/`（与用户自建 `{数据根}/skills/` 分离）。
2. 扩展 `SkillScope`：`"workspace" | "user" | "plugin" | "server"`（`packages/shared/src/skills-types.ts`），并在技能发现的根列表里加一项；UI 侧按 scope 分组/加徽标/隐藏"删除"（改为"卸载"）。
3. 同步策略：**以服务端为真相**——按 `GET /me/skills`（或 `state`）的清单做增量：新增/更新（按 `sha256` 比对，附件逐个校验）/下架删除，**只动自己这个目录**。
4. 同名冲突：服务端技能与用户自建同名时 **服务端优先**（与现有"工作区优先于用户级"的方向一致），并在 UI 上提示冲突来源。

**理由**：混进用户目录会让"用户自建"与"服务端下发"无法区分（R5 要求可区分），且卸载/更新时容易误删用户文件。

**替代方案（若想最小改动）**：写进现有用户级 `{数据根}/skills/` 并用 `_meta.json` 打来源标记。**不推荐**：删除与冲突处理都不安全。

### 4.4 Agent 下发：物化为 server scope 的 subagent markdown（2026-09-22 修订）

**产品语义（已定）**：v1「数字人」= **Task / @mention 可调用的子代理**，不是「主会话换 persona」。
「以此专家开会话」是薄封装（仅应用 `model`；persona 可作系统附注），不另建会话预设状态机。
**不照搬** Reactor-Desktop 的 `agents.json` + `new_session` 注入（那是 sidecar 会话预设链路）。

**状态所有者**

| 状态 | 唯一写入者 | 落盘 |
| --- | --- | --- |
| 安装 / 启停 / 收藏关系 | 服务端 `agent_installs` 等 | 不落本地第二套启用位 |
| 物化 `*.md` | 同步器（挂 `IReactorServerService` 扩展） | `{数据根}/server-agents/<name>.md`，**只动本目录** |
| 市场卡片字段（hot/tags/emoji…） | 内存短缓存 | 不进 markdown |

**字段映射（修订：`skills` 直通；`provider` 不得字面写入）**

| 服务端字段 | 客户端落点 | 处理 |
| --- | --- | --- |
| `name` / `description` | frontmatter 同名 | 必填校验沿用 |
| `persona` | 正文 = systemPrompt | 直通 |
| `modelId` + `provider` | frontmatter `model` | 映射为 `{本地企业 providerId}/{modelId}`（`reactor:providerId`）；服务端 `provider` 是网关逻辑名，**禁止**字面写入 |
| `thinkingLevel` | `thoughtLevel` | 有则写 |
| `policyMode` | `permissionMode` | `readonly`/`strict`→`plan`，`balanced`/`trust`→`auto`；不可逆 |
| `skills[]` | frontmatter `skills` | **直通**（subagent 已支持；未安装技能运行时自然过滤） |
| `title` / `emoji` / 市场字段 | 不进 frontmatter | UI 徽标用内存投影 |
| `installed && installEnabled` | 是否物化 + 发现过滤 | 只物化已安装且启用 |

**同步语义（写后 re-GET 全量，不本地推算聚合字段）**

1. 登录 / 启动已登录 / 手动刷新：`GET /me/agents` → 目标集 = `installed && installEnabled` → **增量 reconcile** `server-agents/`（增/改/删只动本目录）。
2. 安装/启停：`POST|DELETE|PATCH /me/agents/:name/install` 成功后 re-GET 再 reconcile。
3. 卸载/下架：删除对应 `.md`；**永不**写用户 `agents/` 或 `.zcode/agents/`。
4. 登出：清空 `server-agents/`（与 P1 登出清模型清单同构）。
5. 同名：`source=server` 独立 id；只读；卸载只能走服务端 API。

**发现层**：`AgentSource` 增加 `"server"`；`discoverServerAgents`（或扩展 `discoverFileAgents` 第三根）；precedence：`built-in → user → workspace → server → plugin`；CRUD **不**开放 server 文件；CLI `bootstrap/src/subagents.ts` 同步加根，避免 GUI/CLI 列表分叉。

**API 扩展（identity，Bearer，非网关）**：`listAgents` / `installAgent` / `uninstallAgent` / `setAgentInstallEnabled`；错误体已由 `ReactorServerHttpError` 承载。

**验收**

1. 服务端安装启用后，设置页「企业专家」分组与 @/Task 可选，persona/model/skills 映射正确。
2. 卸载/停用后文件与列表立即消失；用户自建 agent 字节不变。
3. 登出清空 server-agents，再登录可恢复。
4. 模型请求仍走 P1 运行期鉴权（providerId = 企业 provider）。

### 4.5 用量上报：v1 只上报模型调用

**决策**：v1 上报 `action:"model_call"` + `usage`（input/output/cache/总 token）。`eventId` 用会话内稳定 id 做幂等键；`summary` 不写正文（服务端限制 200 字且禁正文）。

**理由**：服务端网关**不写审计**，不报则用量报表与额度告警全空（BRD 的计量要求）。tool_call/approval 类事件需要工具审批链路的钩子，属后续阶段。

### 4.6 P1 UI 轮补充的实现决策

1. **地址归一化的端口默认值只对 http 生效**：`http://10.0.0.5` 补 `:8791`（内网最常见写法），`https://reactor.corp.example` **不补端口**（https 意味着前面有反向代理，补 `:8791` 会把请求打到代理没监听的端口）；网关推导同理——http 才换 `:8790`，https 保持隐式 443 只把路径改成 `/v1`。写死端口是初稿的漏洞，反向代理部署必然踩到。
2. **`getStatus()` 在内存缓存为空时从企业 provider 回读模型清单**：进程刚启动时 `cachedModels` 是空的，若只报内存值，用户重启后打开设置会看到"企业模型 0 个"的假象（而模型下拉其实是好的，因为它读的是 provider 配置）。回读的是 `reactor:providerId` 指向条目的 `personalModelIds`，纯本地读取，不需要联网。
3. **登出清空企业 provider 的模型清单、保留 provider 条目**：只清令牌不清模型，会让用户在模型下拉里看到一批"选中就报未授权"的条目，比看不到更糟；而删掉条目本身会让下次登录再建一个新条目（用户可能手动调过它的展示名）。这里的取舍是"条目留着、模型清空"。
4. **模型清单必须走 `addPersonalModel` / `deletePersonalModel`，不能写 overlay 的 `personalModelIds`**（真机验证暴露，初稿与首版实现都错了）：
   - 现象：登录后 provider 条目、名称、baseUrl、哨兵密钥全部正确落盘，但 `personalModelIds` 是空的，聊天里选不到任何企业模型。
   - 原因：`ProviderConfigService.savePersonalProviderOverlay` 会用"当前已存配置的模型成员关系"覆盖入参里的 `personalModelIds`（`normalizePersonalProviderMembership` + `withModelMembershipFrom`），而且成员关系只有 `addPersonalModel`/`deletePersonalModel`/`reorderPersonalModels` 这几个明确的领域操作能改。overlay 写入负责的是 group/access/api/visibility。
   - 处置：`reconcileProviderModels()` 按网关目录做增量（缺的 add、多的 delete），登录与"刷新模型"都走它；同时**把验证脚本里的假 provider 设置改成同样的语义**（overlay 忽略 `personalModelIds`），否则测试会给一个假绿灯——第一版假实现就是直接存 config，导致这个问题直到真机才暴露。

## 7. 与既有机制的关系（避免重复造轮子）

- **不复用** `settings-sync` / `skill-sync` / `plugin-sync`：它们全是**本地/远端文件系统之间**搬运（本机 ↔ SSH/Docker 远端工作区），没有 HTTP 服务端这一侧，也没有账号维度。
- **沿用** `ICredentialService`（加密 + 文件锁 + 原子写）、`ApiClient`/`createNodeApiClient`（代理/CA/超时/`x-request-id`）、`ProviderConfigService` 的 overlay 写面、`subagentStorage` 的 markdown 约定。
- **不碰** `zcodeEndpointOrigin` 与官方 OAuth 链路。
- `onboarding-record.json` 里预留的 `uploadState:"pending"` 与本方案同源（服务端要收 onboarding），但不在 v1 范围。
