# 文件审查板块 —— 方案 v1

> **状态**：**方案待评审，未实现**　**日期**：2026-09-22
> **目标**：在主面板「编程 / 办公」胶囊上新增第三档「审查」，把原核审通（`file-compliance-web`）的各类文件审查能力，以 **Agent + Skill + 知识库** 形态落进 Reactor。
> **参考**：`interface-mode.md`（三档契约，本文实现之）、`CONTEXT.md`（领域词汇）、`DESIGN.md`（UI 规范）
> **来源项目**：`E:\工作\file-compliance-web`（核审通，Vue3 + Express + Prisma + Bull + MaxKB/RAGFlow）

---

## 0. 一句话目标

用户在草稿首页把胶囊切到「审查」，用大白话说「帮我审这份文件」，Agent 按所选审查类型加载对应 Skill（判定规则 + 提示词），必要时检索企业知识库/标准库，把问题逐条定位到原文并高亮，最后在对话里给出结论、并挂出结构化结果卡。

**核心判断（收敛后的定位）**：**审查 ≈ 办公模式的专项分支**。它不需要新的后端服务、不需要队列、不需要移植核审通代码。它与办公模式的差别只有两点：

1. **专项化的知识**：调用哪个知识库/标准库 + 挂哪个审查 Skill（内含判定规则与提示词）。
2. **专项化的结果形态**：问题清单要能点击定位到原文。

其余（会话、上传、预览、文件读写、报告导出）全部复用 Reactor 已有能力。

## 1. 为什么不复用核审通的服务端

核审通现有实现的耦合度（详见其 README 与本次调研）：

| 项 | 规模 |
| --- | --- |
| 后端 | Express 23 组路由、Prisma 42 模型 / 14 枚举、Bull 4 队列、Redis、Python 解析与 OCR 微服务 |
| 审查编排 | `review.service.ts` 2041 行，强依赖 WebSocket 推送 + 阶段状态机 + 误报库 + 并发槽 |
| 规则引擎 | 20 组规则前缀、14 个 `.rule.ts`，运行时从 `review_rules` 表读启停与严重度 |
| 前端 | 24 个 `TaskDetails/*.vue` + 9 个 composables + 1 个 2552 行的结果工作台 |
| 依赖外部 | MaxKB、RAGFlow、doc-parser、OCR、OnlyOffice、pgvector |

**结论**：不搬服务、不搬表、不搬队列、不搬前端。**只继承「审查什么」的领域知识**（模式划分、判定规则、标准条目），落成 Skill 与知识库资产。

用户已明确：原审查质量不达标，本次**全面转向 Agent 审查**。

## 2. 能力映射：核审通模式 → Reactor 原语

**统一骨架**：所有模式都是「**Agent + 指定 Skill/提示词 + 可选知识库检索**」的组合，只是这三项取值不同。

核审通原有 9 个 `ReviewMode`（README 口径「8 种审查模式」，因 `SELF_CHECK` 走独立端点）：本次**保留 6 种**，删除 `RULE_ONLY` 与 `DEC_REVIEW`（理由见 §2.1），`DWG_VISION` 另案。

| 原模式 | Reactor 承载 | 知识来源 | 需要新造什么 |
| --- | --- | --- | --- |
| `LIBRARY_REVIEW` 以库审文 | Agent + `review-standard` Skill | 企业知识库（**本期不做**，见 §4.3） | Skill（知识库后置） |
| `TYPO_GRAMMAR` 基础校对 | Agent + `review-proofread` Skill（内含错词表附件） | 无（或术语表） | Skill |
| `CONSISTENCY` 全文一致性 | Agent + `review-consistency` Skill | 无 | Skill |
| `DOC_REVIEW` 以文审文 | Agent + `review-compare` Skill | 参照文件（用户上传） | Skill |
| `CONTRACT_REVIEW` 合同风险审查 | Agent + `review-contract` Skill（风险条款清单） | 可选法务库 | Skill |
| `SELF_CHECK` 标准引用自检 | **确定性工具**（提引用 + 匹配判定，**零 LLM**）+ Agent 编排与解释 | **标准库**（管理员端管理，见 §4.4） | 工具 + 标准库数据 |
| `DWG_VISION` 图纸视觉 | **不在本板块范围**（需视觉模型 + 图元解析，另案） | — | — |

### 2.1 已裁剪的模式

| 原模式 | 处置 | 理由 |
| --- | --- | --- |
| `RULE_ONLY` 仅规则审查 | **删除，不实现** | 纯规则引擎不调模型的阶段产物；其价值已被「Skill 固化判定规则 + `SELF_CHECK` 机械匹配路径」覆盖，独立模式是重复入口 |
| `DEC_REVIEW` DEC 规范审查 | **删除，不实现** | 与 `LIBRARY_REVIEW` 重复：核审通里它本就是 `LIBRARY_REVIEW` 检测到审点库后自动升级的分支，不是用户可选模式；落地为同一套「Agent + 知识库」即可 |

**裁剪后的模式集合**：以库审文、基础校对、全文一致性、以文审文、合同风险、标准引用自检，共 **6 种**（另 DWG 视觉另案）；其中**以库审文依赖的企业知识库本期不做**，见 §4.3。

**要点**：

- **提示词不一定要有**。用户可直接在对话里说「帮我查错别字」，Agent 用通用能力即可；Skill 的价值在于**固化判定规则、输出格式、术语表**，让结果稳定可复现。
- **规则与提示词都住在 Skill 里**（`SKILL.md` + `references/*.md` 附件），不引入第二套规则引擎，也不新建数据库表。
- **确定性优先**：`SELF_CHECK` **整条链路零 LLM**（调研已证实：核审通 `self-check.service.ts` / `standard-check.service.ts` / `standard-extractor.service.ts` 对 `LlmService|maxkb|embedding|vector|rag` 零引用）。它就是「提引用 + 查库 + 比对」的确定性工具，Agent 只负责触发与解释结果。

## 3. 结果展示形态（关键设计）

采用「**对话为主 + 结构化结果为挂件**」的双层形态：

### 3.1 主形态：对话消息

Agent 在对话里流式给出结论：整体判断、问题条数、按严重度分组摘要、以及建议。这就是普通对话输出，零新增机制。

### 3.2 结构化结果：工具调用产生的卡片

审查结论用**结构化输出**承载，随工具调用一起渲染进对话流（与现有 `ToolCallBlocks` 同构），内容包括：

- 每条问题：`severity`、`ruleCode`、`originalText`、`suggestion`、`description`、**定位锚点**（见 3.3）
- 统计：总数 / 按严重度 / 按类型
- 动作：导出报告（`.docx` / `.xlsx`）

这套卡片**只作为前端组件**，挂在工具结果上，可折叠。它不引入新的路由或新页面。

### 3.3 点击问题 → 原文高亮（复用已有机制）

**现成能力，几乎不用新造**：Reactor 已有 `code-review` 预览源与「评论锚点」机制。

```
AssistantCodeCommentCards.tsx:113  ── onOpenCodeViewer({ type: "code-review", review: {...} })
        │                               CodeReviewAnchor { requestId, title, body, priority?, startLine?, endLine? }
        ▼
lib/codeViewer.ts:31-46              CodeReviewAnchor / CodeReviewCodeViewerSource
        ▼
PreviewPane(395) → previewPaneContent.tsx:405-455
        │  resolveCodeReviewContentProjection(source, content)
        │    → { inlineComments, topComment, focusedRange, targetLineOutOfRange }
        ▼
CodeContent  focusedRange + focusRequestId   ← 自动滚动到行 + 高亮
```

**审查问题卡点击后复用同一条链路**：把问题的定位信息映射成 `CodeReviewAnchor`，打开对应文件的预览并高亮目标行。

**需要新增的一点**：现有锚点只有**行号**（`startLine`/`endLine`），适合代码/纯文本。审查场景多为**字符级**定位（错别字往往在行中间），且目标是 PDF/DOCX/XLSX。

建议的最小扩展（在 `CodeViewerAnchor` 上新增**可选**字段，不破坏现有行号语义）：

```ts
interface ReviewAnchor {
  // 与行号二选一：字符级偏移（相对提取文本）
  startOffset?: number;
  endOffset?: number;
  // 无行号文本兜底：按原文片段在提取文本中查找定位
  quote?: string;
  severity?: "error" | "warning" | "info";
}
```

三种文档类型的落法：

| 类型 | 定位方式 | 复用程度 |
| --- | --- | --- |
| 纯文本 / 已提取文本 | 行号（现成）或字符偏移（新增） | 高：直接走 `code-review` |
| PDF | 提取文本视图 + 字符偏移；后续可加 bbox 层 | 中：先落文本层定位 |
| DOCX / XLSX / PPTX | 同上（Office 预览组件目前无定位能力） | 中：先落文本层定位 |

**落地状态（2026-09-23）**：定位链路已通 —— `CodeReviewAnchor` 增加可选 `startOffset/endOffset/quote/severity`；
`resolveCodeReviewContentProjection` 优先用显式行号、否则由偏移换算出所在行，并把命中原文放进评论的
`selectedText`；`KnowledgeCheck` 结果由专用卡片渲染（`ToolCallBlocks/renderers/knowledge-check.tsx`），
**点问题条即打开工具落盘的正文快照并滚到该行高亮**。偏移越界一律不钳位（跳错位置比不跳更误导复核者）。
**字符级高亮（已实现）**：核实 `@pierre/diffs`（1.1.22）公开 API 后确认无法在它上面做字符级 ——
`FileOptions` 没有 `decorations`/`transformers` 选项，`createDiffSpanDecoration` 返回的是 Shiki 的
`DecorationItem`（服务于内部 diff 渲染），`LineDecoration` / `getUnifiedLineDecoration` 是
`DiffHunksRenderer` 的 protected 方法。因此**带字符偏移的审查文本改为自渲染**
（`ReviewTextContent` + 纯函数 `reviewTextModel.ts`：按原始偏移切出普通段/命中段、跨行各自切段、
区间无效时不猜位置、超长截断并显式提示）；只有行号的行级锚点仍走原代码预览器（既有评论功能零回归）。

**为什么自渲染是对的**：审查文本是我们自己落盘的**提取正文**，不需要语法高亮、diff 与折叠，
需要的只有「行号 + 标出命中的那几个字 + 滚到那儿」——自渲染更简单、更可控，也不受第三方库版本变化影响。

**务实做法**：M1 先把「提取文本 + 字符偏移高亮」打通（覆盖绝大多数问题），Office/PDF 的原生高亮作为后续增强。这符合用户「当前项目已经能展示各类文件了」的现状——先挂上文本定位，不推倒现有预览。

### 3.4 展示层收敛

审查档与办公档一样要**收纳编程向 UI**（git 面板、终端、命令详情、代码 diff 全部不出现）。
判据、逐文件归属表与改动纪律见 [interface-mode.md](interface-mode.md) 第 5 节，本文不重复。
一句话：引入 `isFocusedMode = office || review` 作收敛判据；26 个 `isOfficeMode` 消费文件逐个
归类为「改收敛判据 / 保持办公独有 / 按档位三分」，**不许整批替换**。

### 4.2 审查类型入口（轻量，非 subagent）

**不需要为每个类型建 subagent**。审查类型由「**用户选择 + Skill 加载**」表达：

- 入口方式一：草稿首页在「审查」档位下展示审查类型卡片，点击即预填提示词。本期卡片集合
  （**6 种**）：**基础校对 / 全文一致性 / 以文审文 / 合同风险 / 标准引用自检 / 批量审查出报告**；
  「以库审文」在知识库数据补齐前**不出现**（避免死入口，见 §4.3）。
  卡片与技能是**硬绑定**，不是「提示词里提一句」：正文以 `$<skill-name>` 技能引用开头
  （`packages/ui/src/v4/reviewQuickActionPrompts.ts`），进 Composer 渲染成技能 chip，运行时由
  Skill 工具加载。这条约定断了不会报错，只会让结果从「按 SKILL.md 判定」退化成「模型自由发挥」，
  所以有 `packages/ui/test/reviewQuickActionPrompts.test.ts` 钉住「按钮 ↔ 技能」对应关系。
- 入口方式二：用户直接输入，Agent 自行判断加载哪个 Skill（`description` 驱动）。

若某类型需要固定 persona 与工具白名单（例如「标准引用自检」只允许读标准库、不允许改文件），再把它做成 `server-agents/*.md`，不预先批量创建。

### 4.3 知识库（**本期不做，仅登记方向**）

企业知识库（MaxKB 型语义检索）端侧接入**本期不做**（用户已确认尚未补全）。登记方向备用：

- 复用 `server/src/datasets/` 的既有知识库域，不新建第二套库表（`kb_datasets` + 三级可见性
  `personal` / `department` / `org` + 广场审核流）。
- **受影响范围**：仅「以库审文」的 RAG 分支依赖它，整体后置。
- **不要与 §4.4 的知识板块混淆**：见 §4.4.0 的区分说明。

### 4.4 知识板块（管理员端统一管理）

原核审通里分散的几类「审查依据」数据，**统一收敛为管理员端一个「知识」板块**，
下辖三个子域。普通用户在客户端**看不到任何管理入口**，只在执行审查时被 Agent 读取。

#### 4.4.0 关键区分：哪些是「检索」，哪些是「全量命中」

这是本方案最容易被误设计的一点。**三类知识数据都不是向量检索，全是「全量拉取 + 本地确定性命中」**
（核审通实测：对 `embedding|vector|cosine|相似度检索` 零引用）：

| 子域 | 核审通实际消费方式 | 客户端执行时要做的事 | 数据量 |
| --- | --- | --- | --- |
| **术语白名单** | `refreshCache()` 全量拉进**内存 Set**；审查结果逐条查 Set，命中即丢弃（`rules/typo.rule.ts:308`） | 全量拉成 Set，**过滤**问题（不是"检索"） | 小（内置数百条） |
| **标准规范清单** | `loadStandardLibrary()` 一次 `findMany` 全量，再逐条字符串比对（8 级链） | 全量拉轻量索引，**本地匹配** | 约 1.34 万条（筛选后） |
| **规范库（条文/审点）** | `RuleLibraryItem.clauseText` **预加载**进 `ctx.checkpoints`（`review.service.ts:640-682`） | 全量预加载，**逐条核对** | 中 |

**因此客户端不需要「每次执行都去服务端检索」**，而是：

```
管理员端维护（唯一写入口）
      │  全量/增量下发 + 端侧缓存（带版本失效）
      ▼
客户端执行：本地命中 —— 零网络、零延迟、可复现
```

**为什么必须确定性而非检索**：审查结论要可复现（同一文件 + 同一库 = 同一结论），
语义检索做不到这一点；而这三类数据的判定本质都是字符串/规则匹配，注定是确定性的。
**唯一走真检索（RAG）的是 MaxKB 型知识库，本期不做**（见 §4.3）。

#### 4.4.1 数据模型与来源

| 子域 | 关键字段 | 核审通来源 | 规模 |
| --- | --- | --- | --- |
| 术语白名单 | `term` / `category` / `aliases` / `isBuiltin`（`terminology` 表） | 内置核安全/设备/工艺/建筑/电气 5 类术语 + 管理员补充 | **112 条内置**（随建表幂等 seed）+ 人工补充 |
| 标准规范清单 | `standardNo` / `standardName` / `ident` / `status` / 发布·实施·废止日期 / `replaceInfo` | 见下方「数据来源与筛选」 | **13,445 条** |
| 规范库（条文/审点） | 库：`name` / `description` / `status`(draft/published/archived) / `standardNo`；条目：`ruleCode` / `ruleName` / `category` / `clauseText`（条文原文）/ `checkPrompt`（判定 prompt）/ `severity` / `mandatory` / `sourceLocation` / `clauseHash` / `enabled` | 核审通 `rule_libraries` + `rule_library_items` | 中 |

三处**与核审通不同**的字段决策（都是"删掉没有消费方的列"）：

1. **规范库条目收在 10 个字段**：核审通的 `rule_library_items` 有 22 列，其中 `execution_type` /
   `builtin_prefix` / `params` / `message_template` / `check_method` / `target_scope` 全部服务于
   **机械规则引擎**（按前缀注入规则参数），而「仅规则审查」已在本期裁掉（§2.1），留着就是死列；
   `audit_dimension`（compliance/fact/text）随被删的 DEC 三维度审查一并去掉。
   真正有消费方的是**条文原文 + 判定 prompt**（以库审文，后置期消费）。
2. **`clause_hash` 由服务端推导且 NOT NULL**：它同时是导入**幂等键**，让调用方传就会
   因人而异、重复灌库；统一按 `sha256(条文)前 16 位` 推导（与核审通历史数据同口径）。
   编辑条文会**重算**该键——否则「改完条文再导入同一份清单」会被旧键挡住、静默不更新。
3. **规范库不建外键到标准库**：标准库整批重导会换 id，外键会把「重导标准库」变成
   「必须先删规范库」；自检本来就是按编号做字符串比对，关联只存 `standard_no`。

**内置术语为什么放进代码随建表 seed**：白名单是审查的**执行前提**（校对要先排除专业词，
否则核岛设计说明满屏误报），空库状态等于该能力不可用。seed 每次启动都跑、靠
`(term, category)` 唯一键吞重复——这样版本升级增补的专业词也能进已有环境，
而不是"只在空库 seed"导致后续补不进。`is_builtin` 是**权限**字段：删除接口拒绝它。

#### 4.4.2 管理端落地路径（新增一个业务域，分三个子域）

服务端（`server/packages/server/src/`）：

```
knowledge/                      ← 或按子域拆为 standards/ terminology/ rule-libraries/
  schema.ts   CREATE TABLE IF NOT EXISTS + ALTER ... ADD COLUMN IF NOT EXISTS（幂等，无迁移框架）
  repo.ts     SQL；可见性走 common/scope.ts 的 visibilitySql
  routes.ts   /admin/standards* 等（requireAdmin）+ 只读消费接口（见 §4.4.3）
```

硬约束（调研实测，逐条为踩坑记录）：

1. **建表幂等**：`CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`；
   老库加列必须 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`（`CREATE TABLE IF NOT EXISTS` 不加列）。
2. **挂载顺序**：`identity/server.ts` 中 `app.route(...)` **必须排在 `createPermissionsRoutes` 之前**，
   否则权限点扫描漏项。
3. **管理台**：`packages/admin/src/pages/Knowledge*.tsx` + `services/knowledge.ts` +
   `menu.tsx` 加 `NavItem`（路由由菜单表自动生成，无需改 `console.tsx`）。
4. **导航下发**：`identity/routes.ts` 的 `/me/nav` 必须补同一个 key，否则页面永不显示（两处逐项对齐）。
5. **Excel 导入**：沿用两套模板口径（通用 9 列 / Normative 6 列）+ 列名智能识别 + 中文状态映射
   （`现行/即将实施/已废止` 文本优先，缺失时按日期推断）；**批量插入 5000 一批**（核审通已验证的规模适配值）。
6. **搜索与分页**：1.34 万行需分页 + 关键词检索（编号/名称）。先 `LIKE` 分页，按需再评估 `pg_trgm`。

#### 4.4.3 客户端只读消费接口（必须新增）

三个子域各自的消费契约。**核心纪律：一次拉取 + 端侧缓存 + 版本失效，禁止每次执行都拉全量。**

> **路径已按实现收敛为扁平前缀**（不再用 `/v1/knowledge/*` 聚合前缀）：三个子域的表与路由本来
> 就是彼此独立的（`standards` / `terminology` / `rule-libraries`），聚合前缀要多一层无意义的
> 路由分组，且 M3a 先落地的 `/v1/standards/index` 已经在用扁平形式。

| 接口 | 返回 | 缓存策略 |
| --- | --- | --- |
| `GET /v1/terminology/index` | **全量**术语：`{ term, category, aliases: string[] }`（`aliases` 在服务端拆好，端侧不必各自 split） | 端侧 Set 缓存，按 `maxUpdatedAt` 失效 |
| `GET /v1/standards/index` | 全量**轻量索引**（id/编号/名称/状态/ident/发布日期，**不含替换信息与全文**） | 端侧缓存表 + `maxUpdatedAt` 失效 |
| `GET /v1/rule-libraries` | 可下发的库列表（**仅 `published`**，带 `itemCount`/`enabledItemCount`） | 先列库，再按需拉条目 |
| `GET /v1/rule-libraries/:id/items` | 该库元信息 + **启用中**条文/审点条目 | 按库缓存；删/改字段变更影响幂等键 |

- **权威**：服务端唯一真相；端侧缓存**只读**，不回写。
- **权限**：这些接口是**执行期只读**，只要登录态（Bearer）**不校验角色**；但**不出现在任何
  用户可见导航**中（用户"看不见"指的是没有管理入口，而非不可调用——否则 Agent 无法审查）。
- **未发布的库不下发**（404）：`status !== published` 的库是"还在编辑"的状态，下发半成品会让
  「同一文件 + 同一库 = 同一结论」这条纪律失效。停用的条目同样不下发。
- **标准库索引是全链路唯一有性能压力的接口**（1.3 万行），端侧必须落本地缓存表。
- **端侧实现（已落地）**：
  - 写入方 = `packages/services/src/knowledge/knowledgeSyncService.ts`（服务端进程内，持有 `reactor:*` 凭据）：
    按 `maxUpdatedAt` 作版本做条件请求，304 不重写；原子写（`.tmp` + rename）；**失败保留上一份可用缓存**。
    触发点：登录成功钩子 + 应用启动时的已登录补齐（与 server-agents 同口径）。
  - 读取方 = CLI 工具 `KnowledgeCheck`（`apps/zcode-cli/packages/core/src/tool/handlers/knowledge-check.ts`），
    只读本地文件，**企业令牌不进入 Agent 进程**，因此离线可用、判定可复现。
  - 缓存目录 = `<用户数据目录>/knowledge/`（`resolveKnowledgeCacheRoot`，`REACTOR_KNOWLEDGE_DIR` 可覆盖），
    文件 `standards.json` / `terminology.json` / `rule-libraries.json`，正文快照在 `review-text/<sha1>.txt`。
  - 缓存缺失时工具返回 `stale: true` + 可执行提示，**不允许把"库没同步"当成"未收录"**（那是假结论）。
- **自检报告天然抗迁移**：报告里已冗余存 `libraryStandardNo / libraryStandardName / libraryStandardStatus`，
  标准库变更不会让历史报告失真。

## 5. 三个真实缺口

坦诚记录，不假装没有：

### 缺口 1：端侧没有语义知识库检索工具（**本期不做**）

服务端 `/v1/kb/search`（MaxKB 型语义检索）已可用，但**主仓对该 API 零消费**
（`grep -rn "v1/kb" packages apps` 无命中）。Agent 目前调不到它。

补齐方式（择一，待知识库数据补齐后再定）：

- **A（推荐）新增一个 Host 服务**：按既有范式加服务，走 `IServiceAccessor` → RPC。落地需改 11 处
  （`channels.ts` / 契约类型 / `services/*` 实现与注册 / `accessor.ts` / `remoteServiceAccess.ts` 等），范式明确。
- **B 包成 MCP server**：零内核改动，但需要额外维护一个进程。

> 注：`docs/服务端接线-方案-v1.md` 明确把「KB 客户端侧接入」列为**非目标**。若采用 A，需同步修订该文档的非目标清单。
> **只服务「以库审文」，本期后置。**

### 缺口 2：端侧没有知识板块消费链路（**知识板块的接线点**）

§4.4 的三类数据（术语白名单 / 标准规范清单 / 规范库）在端侧**完全没有消费方**，
需要新增「拉取 + 缓存 + 执行期读取」。这不是"检索"，是**全量拉取 + 本地确定性命中**（见 §4.4.0）。

需要落地：

1. 服务端三个只读接口（契约见 §4.4.3）。
2. 主仓新增 Host 服务（与缺口 1 的 A 方案同范式，但**是独立服务**，不要合并）。
3. 端侧缓存与 Agent 读取工具：术语白名单 → 过滤用 Set；标准索引 → 匹配用；规范库条目 → 核对用。

**与缺口 1 是两件独立的事**（确定性知识 ≠ 语义检索），不要合并实现。

### 缺口 3：Agent 的 `Read` 工具不解析 docx/xlsx（**阻塞审查主链路，须在 M1 解决**）

`Read` 原生支持 PDF 与文本，但 **docx / xlsx / pptx 会按 utf8 读成乱码**。现有路径是内置办公插件的 `docx` / `xlsx` SKILL 用脚本处理。

审查链路里的处理：**先转文本再审查**。复用办公 Skill 或服务端 `@firecrawl/anydoc`（`datasets/parse.ts` 已在用），把 office 文件落成提取文本，再进审查与定位链路。这与 §3.3 的「先挂文本层定位」一致。

## 7. 验收场景

1. 胶囊出现三档「编程 / 办公 / 审查」，切到审查档后胶囊高亮第三档，刷新后保持。
2. 审查档下草稿空态显示审查类型卡片；编程/办公档下不显示。
3. 选「基础校对」并上传一份含错别字的 docx，Agent 给出结论 + 问题卡（每条含原文与建议）。
4. **点击任一条问题 → 打开该文件预览、滚动到对应位置并高亮**。
5. 选「标准引用自检」，Agent 调用确定性工具对照标准库，给出引用是否存在 / 已废止 / 版本不符的判定；
   **无模型可用时该链路仍能出结果**（零 LLM），不得因模型不可用而整条失败。
6. 审查档下 git 面板、终端、命令详情、代码 diff 均不出现；切回编程档后恢复。
7. 办公/编程档的现有行为**零回归**（`isFocusedMode` 引入后原 `isOfficeMode` 分支语义不变）。
8. 首次引导仍只有「编程 / 办公」两档（已确认不变），选择结果不受影响。
9. **审查类型入口不出现「仅规则审查」与「DEC 规范审查」**（已裁剪，见 §2.1）。
10. 管理台「标准清单」页可见（`platform_admin`），非平台管理员被 403 拦；**普通用户界面无任何标准库入口**
    —— `standards` 只下发给 `platform_admin`，`/me/nav` 不含它则菜单项不渲染（两处必须逐项对齐）。
10.1 分页/搜索/状态筛选/分类筛选/排序同时生效，且**「共 N 条」随筛选变化**
    （实测：全量 13,445、搜索 `GB 150` 16、状态=已废止 6,248、分类=材料/冶金 2,436、
    分类=暖通/给排水/消防 475）。
10.2 编辑：只提交单字段（如 `status`）时**其余日期不被清空**；空日期串表示清空；
    日期无法解析返回 400 而不是 500。
10.3 乱码护栏：编号或名称含 U+FFFD（替换字符）时导入丢弃该条、PATCH 返回 400，
    不静默入库 —— 一旦写成 `????` 就无法从别处恢复，且会污染自检比对结果。
10.4 导入幂等：同一 `(编号, 名称)` 重复导入第 2 次返回 `inserted=0, skipped=1`，总数不变。
10.5 消费面 `GET /v1/standards/index` 带 `Last-Modified`，条件请求返回 304。
10.6 **误删护栏**：此前被白名单误删的现行消防/给排水国标（`GB 50222-2017`、`GB 55037-2022`、
    `GB 50116-2013`、`GB 3445-2018` 等）在库中可被判为「通过」；补充批次导入幂等，重复导入总数不变。
10.7 **无文本层文件必须明说**：PDF 图纸 / DWG 等抽不到文本的文件，输出「该文件无法自检」，
    不得给出「未发现问题」这类结论（实测 `2.pdf` 只能抽到标题栏 581 字符）。
10.9 **审查问题条可点击定位**：点问题条打开正文快照并滚动到命中的行高亮，卡片里显示命中的原文片段；
    偏移越界时不定位（降级为顶部评论），不得跳到错误位置。
10.10 **报告导出**：`ExportReviewReport` 生成的 `.docx`/`.xlsx` 是合法 OOXML 包，问题表内容与输入一致；
    默认输出落在被审文件同目录，文件名带时间戳；Excel 单元格做控制字符净化与 32768 上限截断。
10.8 版本标注参与判定：`GB50016-2014（2018年版）` 判为通过（命中库中带标注的现行版），
    不得因剥掉尾注而误报「已废止」。
11. **以库审文入口在知识库数据补齐前不出现在审查类型卡片中**（本期不做，见 §4.3）；不出现"点了没反应"的死入口。
12. Git 侧侧栏项显示为「变更审查」（改名后），与文件审查档不混淆。
13. 知识板块三个子域（术语白名单 / 规范库 / 标准规范清单）在管理员端都有管理页
    （`/terms`、`/rule-libraries`、`/standards`，菜单顺序即审查时的使用顺序）；
    普通用户界面**无任何管理入口**。
13.1 **内置术语随建表 seed 且幂等**：空库启动后术语总数 = 112（5 类），重复启动不重复插入。
13.2 术语按 `(术语, 分类)` 唯一：同分类重名新增 → 409（不静默成功）；按**别名**搜索能命中主术语
    （搜「安注」能搜到「安全注射」）；分类下拉含**尚无词条**的默认分类（否则新分类建不出来）。
13.3 **内置词条不可删除**：单删返回 403；批量删除跳过内置并如实回话 `skippedBuiltin`
    （勾了 2 条只删掉 1 条时，管理台必须能如实提示，不能让管理员以为删干净了）。
13.4 **规范库状态是有语义的**：`draft` 库的消费面返回 404（不下发半成品）；切到 `published`
    后才可读，且**只下发启用中**的条目；停用条目立即从消费面消失。
13.5 **条文幂等键由内容派生**：同库同条文重复新增 → 409、重复导入 `inserted=0`；
    编辑条文后该键**重算**（否则"改完条文再导入同一份清单"会被旧键挡住、静默不更新）。
13.6 删库连带删条目（`ON DELETE CASCADE`），接口回话 `deletedItems` 供管理台如实提示。
13.7 三个子域的导入都丢弃含 U+FFFD 的条目、PATCH 返回 400（乱码是文本已损坏的确定信号，
    静默入库会污染字符串比对结果）。
14. 三域名录在客户端执行期被读取：术语白名单命中项被过滤掉不报错；标准清单能判出「已废止 / 编号错误 / 版本不符」；规范库条目能被逐条核对。
15. **端侧缓存生效**：第二次执行审查时不再全量拉取（按版本号/`updatedAt` 判定未变更即跳过），
    断网时用缓存仍可完成自检。
