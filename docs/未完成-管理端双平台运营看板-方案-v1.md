# 管理端双平台运营看板 方案 v1

> 目标：在管理员服务端（`server/packages/admin`）新增「双平台运营」页与总览卡片，
> 呈现 **桌面端 / Web 端** 各自的在线人数、活跃度、使用热度与用量对比。
> 现状：**服务端当前没有任何平台维度数据，也没有在线/心跳概念**，因此这是"先补埋点、再做看板"的活，不是加个页面。

## 1. 现状核查（决定了为什么要先埋点）

| 事实 | 证据 | 影响 |
| --- | --- | --- |
| `usage_ledger` 有 uid/dept/model/tokens/ts，**无平台字段** | `metering/schema.ts` | 用量无法按平台拆分 |
| `audit_event` 有 uid/session_id/action/tool_name，**无平台字段** | `audit/schema.ts` | 工具调用无法按平台拆分 |
| 登录只提交 `{username, password}`，**不上报客户端类型** | `reactorServerClient.ts` login | 无法区分是谁从哪个端登录 |
| 全仓无 device / heartbeat / presence 表或接口 | 检索无命中 | **"在线人数"当前无数据来源** |
| 管理端已有「运营总览」「用量」页 | `admin/src/menu.tsx`、`pages/DashboardPage.tsx`、`pages/Usage.tsx` | 新看板应复用现有分组与鉴权 |

结论：历史数据不可回溯。看板只能**自埋点上线之日**开始有数据，页面必须显式标注这一点。

## 2. 指标定义（先定义清楚，再谈实现）

| 指标 | 定义 | 数据来源 | 精确度 |
| --- | --- | --- | --- |
| 在线人数 | 最近 60s 内有心跳的客户端连接数 | 心跳表（阶段三） | 精确 |
| **活跃用户**（MVP 替代） | 最近 N 分钟内产生过登录/刷新/用量/审计事件的去重 uid | 登录表 + ledger + audit | 近似 |
| 日活 / 周活 | 自然日/自然周内去重 uid | 同上 | 近似 |
| 会话数 | 去重 session_id 计数 | audit_event.session_id | 准 |
| 请求数 / Token 量 | 按平台分组的请求与 token 汇总 | usage_ledger（需加平台） | 准 |
| 使用热度 | 24h × 7d 的请求/token 矩阵 | usage_ledger | 准 |
| 人均时长 | 会话首末事件时间差均值 | audit_event | 近似 |
| 平台构成 | 活跃用户中 desktop / web 占比 | 需平台字段 | 准 |

术语纪律：**阶段一二只能叫「活跃」，不叫「在线」**。页面上必须区分，否则运维会拿近似值当实时值用。

## 3. 平台维度的来源（核心设计）

三种判定手段，按可靠性排序：

1. **客户端声明（首选）**：登录与心跳带 `X-Reactor-Client: desktop|web` 与 `X-Reactor-Version`。
   桌面端已在构造版本信息，web 端固定为 `web`。声明值写入登录记录，并**随令牌下发**（JWT claim 或
   session 记录），使 gateway 与审计上报能把平台带到 `usage_ledger` / `audit_event`。
2. **User-Agent 兜底**：Electron UA 含 `Electron/`；浏览器 UA 不含。用于旧版本客户端（未声明平台）的
   归类，标记为 `desktop_legacy` / `web_guess`，看板上单独显示，不混入主口径。
3. **来源地址**：web 请求来自 web 容器，桌面请求来自用户机器。仅作交叉校验，**不作判定依据**
   （内网 NAT、反代会打平）。

> 为什么必须让令牌携带平台：`usage_ledger` 的写入方是 **gateway**，它只看到模型请求，
> 没有浏览器上下文。只有令牌带平台，gateway 才能在落账时写入 `platform`。

## 4. 数据结构变更

```sql
-- 新增：客户端登录记录（同时承担日活与阶段三的心跳载体）
CREATE TABLE IF NOT EXISTS client_login (
  id            BIGSERIAL PRIMARY KEY,
  uid           TEXT NOT NULL,
  dept_id       INT REFERENCES departments(id) ON DELETE SET NULL,
  dept_path     TEXT,
  platform      TEXT NOT NULL,            -- desktop | web | desktop_legacy | web_guess
  client_version TEXT,
  user_agent    TEXT,
  ip            TEXT,
  logged_in_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_seen_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON client_login (platform, logged_in_at DESC);
CREATE INDEX ON client_login (uid, last_seen_at DESC);

-- 已有表加列（可空，旧数据留空 = 未打标）
ALTER TABLE usage_ledger ADD COLUMN IF NOT EXISTS platform TEXT;
ALTER TABLE audit_event  ADD COLUMN IF NOT EXISTS platform TEXT;
ALTER TABLE audit_event  ADD COLUMN IF NOT EXISTS client_version TEXT;
```

- 加列全部可空、不设默认值：历史行保持 `NULL`，看板口径里空值归入「未打标」一档，不伪造数据。
- 阶段三若需要真实在线，`client_login.last_seen_at` 即为心跳时间，无需再加表。

## 5. 接口设计（挂现有 `/admin/*`，复用 `authed` + `platform_admin`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/admin/metrics/platform/overview?range=24h\|7d\|30d` | 两平台：活跃用户、会话数、请求数、token 数、人均时长 |
| GET | `/admin/metrics/platform/series?metric=tokens\|requests\|active&interval=hour\|day` | 时序，返回 `{desktop:[], web:[], untagged:[]}` |
| GET | `/admin/metrics/platform/heatmap?range=7d` | 24×7 热度矩阵，分平台 |
| GET | `/admin/metrics/platform/presence` | 在线快照（阶段三）；阶段一二返回 `activeApprox` 并标注 `approx: true` |
| GET | `/admin/metrics/platform/sessions?cursor=` | 明细列表（uid、平台、版本、UA、首末时间），支持导出 |

约定：
- 所有响应带 `generatedAt` 与 `coverage: { since, untaggedRatio }`，让前端能如实展示"自 X 起统计"
  与"未打标占比"。
- 权限沿用现有模型：`platform_admin` 看全量；`dept_head` 仅本部门（复用 `audit/routes.ts` 的部门范围解析）。
- 聚合查询走索引，禁止全表扫；`range=30d` 走按天预聚合（可后续加物化视图，先不引入）。

## 6. 页面设计

在 `session/packages/admin/src/menu.tsx` 的「运营」组下新增一项：

```
运营
├── 运营总览        /            （现有，增加双平台卡片区）
└── 平台运营        /platform    （新增）
```

**运营总览（改造）**：顶部加 4 张卡——桌面端在线/活跃、Web 端在线/活跃；下方一条双平台趋势迷你图。

**平台运营页（新增）**：

1. **平台对比条**：desktop / web / 未打标 的活跃用户构成
2. **双平台趋势**：请求数、token 数、活跃用户（三条线，可切换指标与时间粒度）
3. **24×7 使用热度**：两平台并排热力图，复用客户端 `UsageHeatmap` 的色阶思路（服务端配色另定）
4. **会话明细表**：uid、部门、平台、客户端版本、UA、首末时间；支持筛选与导出
5. **空态与口径说明**：无数据时展示"自 2026-xx-xx 起统计"，未打标占比高于 20% 时给出提示

## 7. 分期落地

| 阶段 | 内容 | 改动面 | 工期 |
| --- | --- | --- | --- |
| **一** | 登录记录平台（UA 兜底 + 头部声明取其一）+ `client_login` 表 + overview/series 接口 + 总览卡片 | server（identity 登录、新增 metrics 路由）、admin | 1 周 |
| **二** | 令牌携带平台 → gateway 写 `usage_ledger.platform`；审计上报带平台；补 heatmap 与明细 | server（token claims、gateway、audit）、client（上报头） | 1~2 周 |
| **三** | 心跳（客户端 60s）+ web 容器 WS 连接数上报 → 真实在线人数 | client（desktop/web 都改）、server | 1 周 |

阶段一即可交付"能看的双平台对比"，但**必须标注为近似口径**；只有阶段三之后"在线"才名副其实。

## 8. 验收场景

1. 只有桌面端在用：`/platform` 显示 desktop 有数据、web 为 0，且不报错
2. 只有 web 在用：反之
3. 两端混用：构成比、趋势线、热力图分别正确
4. 存在未打标历史数据：`untaggedRatio > 0` 时页面显示提示，且不把未打标算进任一平台
5. `dept_head` 登录：只能看到本部门数据；越权直连接口返回 403
6. 空库：返回全 0 与"自 X 起统计"，不出现 NaN / 空图表崩溃
7. 大范围查询（30 天）：响应时间可接受（目标 < 2s），无全表扫

## 9. 风险

- **历史不可回溯**：上线首日看板几乎是空的，需要提前与使用方对齐预期。
- **UA 兜底会误判**：浏览器 UA 可被改写；因此 UA 结果只进 `web_guess` 档，不并入主口径。
- **web 端"在线"语义**：浏览器标签可能长期挂着不动，心跳只能证明"页面开着"，不能证明"人在用"；
  看板需同时给出"在线连接数"与"活跃用户数"两个口径。
