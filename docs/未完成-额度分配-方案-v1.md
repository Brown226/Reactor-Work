> **状态**：**P1–P4 已实现并验证**（2026-10-09；实现记录与验收证据见 §11）。本文兼作开工计划与实现对照表。
> **日期**：2026-10-09

> **现状基线**：服务端只有「组织级单一月度上限 + 阈值告警（不阻断）」，无分配维度、无强制执行、计量依赖端侧自愿上报。证据见 §1。
> **原则**：一处状态一个写入者；账本权威、端侧上报只作对账；执行在网关（唯一模型出口）；不动端侧既有契约形状（仅扩）。

## 0. 一句话目标

企业管理员可以**按组织 / 部门 / 用户分配月度额度**；**网关按账本权威计量并可选硬阻断**；管理台与桌面端看到的进度与实际消耗一致、可对账。

## 2. 已拍板决策（不再讨论）

| # | 决策 | 理由 / 代价 |
| - | ---- | ----------- |
| Q1 | **网关写 `usage_ledger` 计量账本，作为报表 / 额度 / 告警的唯一权威口径**；端侧 `model_call` 上报保留，仅用于对账视图 | 解决缺口 4：账本是网关侧事实，旁路调用（不经网关）不属于本产品计量范围；端侧改造仍可绕过，故执行必须也在网关 |
| Q2 | **阻断默认关闭**：`REACTOR_QUOTA_ENFORCE=false` 上线，观察一轮后按组织开启；规则上 `action` 字段（`warn`/`block`）只在开关打开时对 `block` 规则生效 | 单点事故面控制；关闭时行为与现状完全一致（回归可证） |
| Q3 | **v1 分配维度 = 组织 / 部门（含子树继承）/ 用户**；模型、供应商维度、成本（¥）额度列入 P5 | 工期与收益平衡 |
| Q4 | **周期保持 UTC**（`currentPeriod()` 现状），新增 `REACTOR_QUOTA_PERIOD_TZ` 可配（默认不设 = UTC）；中国部署建议设 `Asia/Shanghai` | 直接改本地时区会与既有 `quota_alert.period` 历史数据错位，不做历史回填 |
| Q5 | **系统调用（KB 向量化等）记为 `system:kb` 主体**：计入组织额度，不进入任何个人/部门额度 | KB embedder 用的 `REACTOR_GATEWAY_TOKEN`/`REACTOR_DEV_TOKEN` 是 dev token（`kind=dev`，无主体，见 `auth/token.ts:26`），若不计入则上游费用与账本对不上；但 dev token 无法归属到人，硬记个人额度是伪造归属 |
| Q6 | **P4 决策修订**：D5「硬限流将来放网关」= 本次 P3 交付；D6「服务端不写网关审计」开孔 = 仅限计量账本（`usage_ledger`）与 `policy_block`（`audit_event`），**不写工具/会话类审计** | 修订记录落 P4 文档 §7 之后，两份文档不互相矛盾 |
| Q7 | **口径优先级 = 叠加检查，不做覆盖**：一条调用同时受组织、命中的部门祖先链、个人三类规则约束，**任一 `block` 规则超限即 429** | 与端侧「mode 天花板取更严一档」的既有语义一致（P4 §1 D2）；避免"部门规则覆盖组织规则"这类隐式层级语义 |

### Q7 语义示例

```
组织 5000万 / 研发部 1000万 / 研发部>平台组 300万 / 张三 50万（全部 block）
张三当前月用量 60万（含个人 50万内的部分）
→ 个人规则超限（60 ≥ 50）⇒ 429，即使组织/部门都还有余量
员工转岗「研发部>平台组 → 研发部>数据组」后，历史用量归属按写入时快照不变（与审计表 dept 快照既有纪律一致）
```

## 3. 状态所有者（一处状态一个写入者）

| 状态 | 唯一所有者 | 落盘 | 读写方 | 备注 |
| ---- | ---------- | ---- | ------ | ---- |
| 额度规则 `quota_rule` | identity 管理面 API（`PUT/DELETE /admin/quota-rules`） | PG 表 | 写：identity；读：identity、gateway（同库） | gateway 只读，不建表不迁移（沿用 T3-4 纪律） |
| 计量账本 `usage_ledger` | **gateway 进程**（每次代理成功落一行） | PG 表 | 写：仅 gateway；读：identity（报表/告警/回读）、gateway（执行前计数） | 幂等键 `request_id`；建表归 identity `ensureSchema` 批，**两进程间存在建表窗口，见 §6「启动竞态」** |
| 告警记录 `quota_alert` | identity 与 gateway 双触发，插入 `ON CONFLICT DO NOTHING` 幂等 | PG 表 | 写：两侧；读：管理台 | 扩 scope 列（§4.3） |
| 端侧额度进度 | 端侧只读服务端聚合 | — | 读：桌面端 | 不新增端上权威状态 |

**事件顺序（一次模型调用）**：

```
端侧/Web ──(reactor token: sub/role/deptId)──▶ gateway
  ① 认证 → ② 可见范围拦截（现状不动）
  ③ resolveEffectiveRules({uid, 部门祖先链, model})
        └─ 从 usage_ledger 按规则 scope 取当期计数
  ④ 任一 block 规则超限 && 开关开启 ? 429 + 写 policy_block 审计（异步、best-effort）
                                     : 放行
  ⑤ 转发上游（流式 tee / 非流式缓冲）
  ⑥ usage 提取 → computeCost（四段价，复用 common/pricing.ts）
       → INSERT usage_ledger（request_id 幂等）
       → evaluateQuotaAlerts(scope)（复用现有幂等与 webhook 通道）
```

失败语义：③/④/⑥ 任何一步抛错都**不阻断转发**（fail-open），但必须落日志；`block` 规则自身的查询失败按"放行 + 记 error 日志"处理（宁可放行不可误杀）。**账本不可用（表未建 / 连接失败，见 §6 启动竞态）时进入「记账暂停」降级态**：模型调用照常转发，`/health` 暴露 `ledger: "degraded"`，恢复后自动回正常态。

### 3.1 日志分级

| 事件 | 级别 | 说明 |
| ---- | ---- | ---- |
| 每次账本落账成功 / 每请求解析 | `debug` | 高频，不落盘 |
| 额度规则变更、开关状态、降级进入/退出 | `info` | 生产可查 |
| usage 解析失败（上游形状变化，丢该条计量） | `warn` | 可恢复，需可见 |
| 账本写失败、`block` 规则查询失败 | `error` | 必须人工可查 |

## 4. 数据与接口契约

### 4.1 `usage_ledger`（新表，identity `ensureSchema` 批建表）

```sql
CREATE TABLE IF NOT EXISTS usage_ledger (
  id BIGSERIAL PRIMARY KEY,
  request_id TEXT NOT NULL UNIQUE,     -- gateway 生成；重放不重复计账
  ts TIMESTAMPTZ NOT NULL DEFAULT now(),
  subject_kind TEXT NOT NULL CHECK (subject_kind IN ('user','system')),
  uid TEXT NOT NULL,                   -- user = 令牌 sub；system = 'system:kb' 等
  dept_id INT,                         -- 写入时快照（同 audit_event 纪律）
  dept_path TEXT,
  model TEXT,
  provider TEXT,
  api_shape TEXT,                      -- anthropic | openai | embeddings | rerank
  input_tokens INT,
  output_tokens INT,
  cache_read_tokens INT,
  cache_write_tokens INT,
  total_tokens INT,
  cost NUMERIC(16,6),                  -- 服务端四段价核算；价目缺失时 null
  cost_source TEXT,                    -- server | none
  currency TEXT,
  pricing_snapshot JSONB,
  outcome TEXT NOT NULL DEFAULT 'ok',  -- ok | error | aborted（上游 4xx/5xx/断流）
  http_status INT
);
CREATE INDEX IF NOT EXISTS idx_ledger_ts ON usage_ledger (ts DESC);
CREATE INDEX IF NOT EXISTS idx_ledger_uid_ts ON usage_ledger (uid, ts DESC);
CREATE INDEX IF NOT EXISTS idx_ledger_dept_ts ON usage_ledger (dept_id, ts DESC);
```

### 4.2 `quota_rule`（新表，identity `ensureSchema` 批建表）

```sql
CREATE TABLE IF NOT EXISTS quota_rule (
  id SERIAL PRIMARY KEY,
  scope_type TEXT NOT NULL CHECK (scope_type IN ('org','dept','user')),
  scope_id TEXT,                       -- org: NULL；dept: departments.id；user: uid
  period TEXT NOT NULL DEFAULT 'month' CHECK (period IN ('month')),
  limit_tokens BIGINT,                 -- 与 limit_cost 至少一个非空
  limit_cost NUMERIC(16,2),
  alert_thresholds INT[] NOT NULL DEFAULT '{80,100}',
  action TEXT NOT NULL DEFAULT 'warn' CHECK (action IN ('warn','block')),
  enabled BOOL NOT NULL DEFAULT true,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_by TEXT,
  UNIQUE (scope_type, scope_id, period)
);
```

规则解析（`resolveEffectiveRules`）：输入 `{uid, deptId}`，输出适用规则集合 —— 组织规则（scope_type=org）+ 该用户部门祖先链上每条启用的 dept 规则（`departments` 已有 `path` 字段，`identity/depts.ts` 的 `subtreeIds`/`loadAllDepts` 可复用）+ 个人规则。解析只做**取集**，不做优先级合并（Q7）。

### 4.3 `quota_alert` 扩列

```sql
ALTER TABLE quota_alert ADD COLUMN IF NOT EXISTS scope_type TEXT NOT NULL DEFAULT 'org';
ALTER TABLE quota_alert ADD COLUMN IF NOT EXISTS scope_id TEXT;
-- 老行回填 org（DEFAULT 已覆盖）；唯一约束迁移：
--   原 UNIQUE (period, threshold) → UNIQUE (period, scope_type, scope_id, threshold)
```

webhook payload 增 `scopeType` / `scopeId`（老消费者忽略新字段不受影响）。

### 4.4 HTTP 面

| 面 | 路径 | 鉴权 | 说明 |
| -- | ---- | ---- | ---- |
| 规则读 | `GET /admin/quota-rules` | Bearer + platform_admin | 返回全部规则 + 组织缺省（无规则时合成 org 规则来自 `desktop_policy.quota`，见 §6） |
| 规则写 | `PUT /admin/quota-rules` | 同上 | 全量 upsert（按 `(scope_type, scope_id)` 覆盖），写后立即复评告警；手写审计留痕 `quota_rule.upsert`（含改前快照，走 `details` 字段）。`limitTokens` **支持单位后缀**：`5M` / `500K` / `1.5M` / `500万` / 裸数字（服务端换算后回显，见 §11.4） |
| 规则批量写 | `POST /admin/quota-rules/batch` | 同上 | 一次给**多个目标**同值下发（组织 / 部门 / 部门下每个用户 / 指定 uid 列表）；`dryRun` 只解析不写。契约见 §11.7 |
| 规则删 | `DELETE /admin/quota-rules/:id` | 同上 | 留痕 `quota_rule.delete` |
| 个人额度 | `GET /desktop/quota/me` | Bearer（任意角色） | 返回本人适用的 org/部门/个人规则与当期用量（口径一致，可正确渲染百分比） |
| 对账 | `GET /admin/usage/reconciliation?from&to` | Bearer + platform_admin | 账本 vs 端侧上报按 model 的漂移对比 |
| 报表口径 | `GET /desktop/usage/summary` | 不变（按角色收敛） | **数据源切换为账本**（P4 阶段完成后端侧上报仍在，但不再参与该端点） |

429 回执形状（网关）：

```json
{ "error": { "type": "quota_exceeded", "message": "已达部门额度上限", 
             "scope": "dept", "scopeId": "42", "limit": 10000000, "used": 10423011 } }
```

### P3 — 网关强制执行（1.5–2 人日）

- 并发口径：允许少量在途超发（后置计数、无预留量），写进注释与文档；预留量列 P5。
- 端侧 429 可读文案（`packages/ui/src/lib/providerBusinessError.ts` 同类错误映射，最小改动）。

**验收**（`smoke:quota` 扩展）：warn 规则不拦、block 规则 429、开关关闭放行、额度调高/跨月后恢复、`policy_block` 落库（含 scope 归属）、dev token 场景 `system` 计量但不触发个人规则。

## 7. 已知边界（写进实现注释，不当 bug 修）

1. **网关计量只覆盖经网关的调用**；直连上游的个人 provider / 开发者模式旁路仍不计量（P4 §7-1 的边界不变，本次不给旁路补计量）。
2. **dev token 无主体**：`system:kb` 只计入组织额度；跨部门 KB 用量无法归属到部门，这是身份信息缺失，不是实现折扣。
3. **`REACTOR_QUOTA_ENFORCE=false` 时**系统与现状完全等价 —— 上线第一步就是它，观察一整个周期再开。
4. **并发窗口**：后置计数在并发高峰允许少量在途超发（数量级 ≤ 在途请求数 × 单次用量）。
5. **周期时区默认 UTC**：与既有 `quota_alert.period` 历史口径一致；改 `REACTOR_QUOTA_PERIOD_TZ` 后当期切分点变化，不做历史回填。
6. **月度周期只做自然月**；周/日周期留 P5。

### 11.4 额度上限的单位后缀（2026-10-09 追加）

**动机**：额度动辄百万级（`5000000` 难读难打），而规则列表早就在用 K/M 格式化展示，输入却只认裸数字 —— 用户要么数零要么先心算。现场反馈"支持 M 为单位"即此。

**契约**：`PUT /admin/quota-rules` 的 `limitTokens` 接受

| 形态 | 例 | 换算 |
| ---- | -- | ---- |
| 裸数字 | `5000000` | 5000000（回归不变） |
| K | `500K` / `500k` | 500000 |
| M | `5M` / `5m` / `5 M` / `1.5M` | 5000000 / 1500000 |
| B | `2B` | 2000000000 |
| 万 | `500万` | 5000000 |

**拒绝**（400，不悄悄存成 0/NaN）：`abc`、`-5M`、`0M`、`5MB`（单位必须独立）、`M5`、`5 M M`、空串。

**两处实现必须同步**：服务端 `metering/quota-routes.ts` 的 `parseTokenLimit`（**权威**，冒烟以它为准）与管理台 `packages/admin/src/pages/Usage.tsx` 的同名解析（两包不共享代码）。管理台另有**实时换算预览**（`= 5,000,000 tokens`）与不可识别时的红字提示；保存后列表回显的是服务端换算值。

**验证**：`smoke:quota` ⑩-2 段 8 合法 + 8 非法断言全绿（合计 108 项）；真实环境 API 实测 `5M` / `500K` / `500万` 均换算正确。

2. 服务端配额只能逐条新建 ——「批量给每个用户每月 1 亿 token」要重复八百次，部门维度同理。

#### 服务端契约：`POST /admin/quota-rules/batch`

请求体：

```json
{
  "targets": [
    { "scopeType": "org" },
    { "scopeType": "dept", "scopeIds": ["3"], "expandUsers": true },
    { "scopeType": "user", "scopeIds": ["zhangsan", "lisi"] }
  ],
  "limitTokens": "100M",
  "limitCost": null,
  "alertThresholds": [80, 100],
  "action": "warn",
  "enabled": true,
  "dryRun": false
}
```

语义（逐条对应上面两个诉求的实现边界）：

| 项 | 规则 |
| -- | ---- |
| 目标解析 | `org` → 一条 org 规则；`dept` 不带 `expandUsers` → 部门本身一条规则（子树由 §2 Q7 既有解析语义自动覆盖）；`dept` 带 `expandUsers: true` → **该部门子树下每个在用用户各一条 user 规则**；`user` + `scopeIds` → 指定 uid 列表 |
| 同值下发 | 上限 / 阈值 / 动作对本次所有目标相同（"批量"即同值）；单条微调仍走 `PUT /admin/quota-rules` |
| `dryRun` | 只解析不写库，返回将写入的规则清单与分维度计数（管理台「预览」用；同一端点两种模式，避免再开一个 preview 面） |
| 去重 | 同一 `(scope_type, scope_id)` 在一次请求内只写一次（按 `targets` 顺序，先到先得），不互相覆盖 |
| 未知 uid | 不存在或已停用的用户**跳过**并计入 `skipped`，不静默建规则（否则删号的人仍被额度约束，且列表里查无此人） |
| 批量上限 | 单次最多 500 个目标（防误操作；超出 400） |
| 幂等 | 复用 `upsertQuotaRule` 的 `ON CONFLICT DO UPDATE`：重复 apply 是更新不是插重复行 |
| 鉴权 | 与 CRUD 一致：`platform_admin`，其余 403 |

回执：`{ dryRun, resolved: {org,dept,user}, rules: [{scopeType, scopeId, existed}], skipped: [{scopeType, scopeId, reason}], applied }`。

#### 端侧契约

`GET /desktop/quota/me` **不变**（items 已带每规则的 used/limit/阈值/动作，§11 P4c）。改动全在渲染：

| # | 改动 | 理由 |
| - | ---- | ---- |
| 1 | 每条适用规则渲染为**一行**（组织 / 本部门 / 本人），带 20 格分段进度条 + 百分比 + 已用/上限 | 参考图同款组件；多规则叠加时逐条可见，不再只有"一个数" |
| 2 | 行内显示**告警线**与**动作徽标**（仅告警 / 阻断） | 让用户知道超了是被拦还是只提醒 |
| 3 | 行尾显示**重置日期**（下一周期首日） | 参考图的关键信息；周期边界以服务端 `period` 为权威，端侧只格式化 |
