# 交付打包流程（标准流程）

适用版本：V1.1.1 起。本文覆盖**四类交付物的打包**（桌面安装包、Web 镜像、服务端镜像、门户镜像）
与**现场升级脚本的注意事项**。

> 交付物只支持 **Windows x64 桌面端**（macOS/Linux 不再出包），镜像部分与平台无关。

## 1. 一条命令

统一入口：`scripts/release/package-release.mjs`

```bash
# 单个目标
node scripts/release/package-release.mjs desktop            # 桌面安装包
node scripts/release/package-release.mjs web                 # Web 镜像
node scripts/release/package-release.mjs server              # 服务端镜像
node scripts/release/package-release.mjs portal              # 门户镜像

# 组合与选项
node scripts/release/package-release.mjs all --verify        # 全部 + 清单校验
node scripts/release/package-release.mjs web --reuse-assets  # 复用能力资产，不重新下载
node scripts/release/package-release.mjs portal --out "E:\工作\Reactor-版本更新\_test" --dry-run
```

| 选项 | 含义 |
| --- | --- |
| `--out <dir>` | 交付目录；默认 `E:\工作\Reactor-版本更新\V<version>`（可用 `REACTOR_DELIVERY_ROOT` 覆盖） |
| `--version <v>` | 覆盖版本号；默认取仓库根 `package.json` 的 `version` |
| `--reuse-assets` | 复用已有 Web 能力资产（`bundled-tools`，300MB，重新下载很慢） |
| `--skip-build` | 跳过构建，只重新导出（web / server / portal 有效） |
| `--verify` | 结束后校验交付包 `MANIFEST.sha256` 全量 |
| `--dry-run` | 只打印将要执行的步骤 |

版本号只有一个来源：仓库根 `package.json`。**打包前先 `grep '"version"' package.json`**——
桌面安装包文件名、镜像 tag、`server-info.version` 都取自它，版本漂移会让现场看到"旧版本"。

## 2. 交付目录结构

```
V<version>/
├── desktop/   Reactor-<version>-win-x64.exe + .blockmap + latest.yml
├── web/       images/reactor-web-v<version>.tar.gz + compose.yml + build/ + load-and-up.sh
├── server/    images/{reactor-desktop-server,reactor-portal,openldap,pgvector}.tar.gz
│              + compose.yml + .env + load-and-up.sh
├── docs/      更新说明-*.md
├── README.md
└── MANIFEST.sha256
```

打包脚本**只覆盖镜像与桌面安装包**，并自动更新 `MANIFEST.sha256`。
下列文件是人工维护的，打包后请自行确认是否需要同步：

- `server/compose.yml`、`server/.env`、`server/load-and-up.sh`、`server/部署说明.md`
- `web/compose.yml`、`web/.env`、`web/load-and-up.sh`、`web/部署说明.md`
- `docs/更新说明-*.md`、`README.md`

## 3. 各目标的流程与坑

### 3.1 桌面端（win x64）

流程：`core → CLI bundle → 同步内置 agent → build:no-runtime-assets → bundle → 交付`

- **必须先重建 core**：CLI 的 esbuild alias 指向 `@zcode/core` 的 `dist/index.js`，
  改过 core 源码只跑 CLI build 会打出旧提示词。
- **agent bundle 有两份来源，要一起换**：
  `packages/desktop/bundled-agents/win32-x64/glm/zcode.cjs`（桌面内置）与
  `packages/desktop/mock-cdn/releases/<版本>/glm/<平台>/zcode.cjs`（远端 agent 资产）。
  只换其一会导致桌面端仍用旧 bundle——脚本已自动同步两份。
- **CLI build 必须带** `ZCODE_BUILTIN_PROVIDER_CONFIG_FILE=config/provider/zcode-builtin.json`，
  否则报 `Invalid Built-in Provider config (production)`。
- **`--desktop-agent` 才是线上同款**：minify 后 17.4MB；不带该 flag 是 34MB 且带 sourcemap。
- **Vite 堆上限**：`NODE_OPTIONS=--max-old-space-size=6144`。8192 反而更容易 segfault。
- **打包必须带 `--skip-prepare --skip-build`**：
  `prepare` 会为 4 个平台构建 mock-cdn 组件，对 Windows 包无用且极慢。
- **图标**：改 `packages/desktop/build/icon.ico` 等资产后需重打；验证用
  `Icon.ExtractAssociatedIcon(exe)` 提取确认。**资源管理器仍显示旧图是 Windows 图标缓存**
  （`ie4uinit.exe -ClearIconCache`），不是打包失败。

### 3.2 Web 镜像

流程：`server-dist → web-dist → CLI bundle → 组装上下文 → docker build → save|gzip`

- **构建上下文必须在仓库内**（`.tmp-web-image-context`）：Windows Temp 下会掉
  `agent/zcode.cjs`、DWG sidecar、`bundled-tools`、`web-dist/assets`。
- **构建前自检关键资产**：`server-dist/entry-http.js`、`web-dist/index.html`、
  `agent/zcode.cjs`、`agent/dwg-tools/dwg-sidecar/linux-x64/dwg-sidecar`、
  `bundled-tools/linux-x64/file-tools`、`agent/packages`。脚本会检查并在缺失时直接失败。
- **官方插件 seed 必须带**：`agent/packages`（15 个）。缺了插件市场为空、
  `dwg_modify / parse_document / ocr_scan` 不可达。
- **server 构建必须带内置 provider 配置 env**，否则直连 Key 修复不会进镜像。
- **`ZCODE_AGENT_SERVER_ARGS_JSON` 必须单引号包住**（Docker ENV 会剥双引号，
  写成 `["a","b"]` 实际是 `[a,b]`，agent 启动即 JSON.parse 失败）。
- 基础镜像必须 **Debian（glibc）**，不能用 Alpine：`@lydell/node-pty` 是 glibc 链接。
- apt 源换国内镜像；`/root/.reactor` 软链到 `/data/.reactor`（会话持久化），
  **不要改 `HOME`**，否则凭据解密失败。

### 3.3 服务端镜像

流程：`server 工作区编译 → 基础镜像准备 → docker build → 导出 3 个镜像`

- **必须在 `server/` 工作区编译** `@reactor/shared` / `@reactor/server` / `@reactor/admin`，
  否则镜像是旧产物（直连 Key、管理台修复不会生效）。
- **`node:22-alpine` 直连 docker.io 会超时**：脚本自动从 `docker.1ms.run` 拉取并 retag。
- 镜像 tag 固定 `reactor-desktop-server:local`（identity 与 gateway 共用）。
- `openldap` / `pgvector` 是第三方镜像，不需要构建，本地有则直接导出。

### 3.4 门户镜像

流程：`portal/manual/build.mjs → check.mjs → docker build → save|gzip`

- **门户的"更新日志 / 下载页"内容来自 identity 数据库 + `updates` 卷，不在镜像里**，
  换镜像不会自动带出版本说明；要在管理台发布版本。
- 交付包里门户镜像归在 `server/images/reactor-portal.tar.gz`（历史命名）。

## 4. 速度：打包本身不慢，慢的是别的东西

实测基线（本机）：

| 环节 | 耗时 |
| --- | --- |
| 门户：说明书生成 + build + save|gzip | **约 6 秒** |
| Web：server-dist + web-dist + bundle + build + save|gzip | 约 5~7 分钟（导出 644MB 占大头） |
| 服务端：编译 + build + 导出 3 个镜像 | 约 5 分钟 |
| 桌面：build:no-runtime-assets + bundle + 导出 | 约 15 分钟 |

镜像类的完整循环（改内容 → 构建 → 导出 → 校验）通常 **半分钟到几分钟**，
桌面端因为要打 380MB 的 NSIS 安装包，是唯一天然慢的。

**三条不要做**（都是实际浪费过十几分钟的地方）：

1. **不要让交付物卡在模型调用上**。为截一张图去跑一次真实任务（10 秒~3 分钟，还可能卡在
   "等待确认"）——能静态截就静态截，截不到就改文案或留占位。
2. **不要改一次建一次**。内容批量改完再一次性 build/save/更新 MANIFEST。
3. **不要每次 save 后都 `docker load` 验证**。本地刚 save 的镜像再 load 一遍纯冗余，
   `MANIFEST` + `sha256sum -c` 才是门禁；`docker load` 只在"准备交付给别人"或"换机器"时做。

次要因素：Chromium 109（Chrome 109）每次加载 SPA 要 2~3 秒水合；
内存只剩 1GB 左右时页面加载和 Vite 都会明显变慢（也是之前 OOM 的来路）。

## 5. 现场升级脚本注意事项

交付包里有两个一键脚本，**分工不同，不要混用**：

| 脚本 | 管什么 | 关键行为 |
| --- | --- | --- |
| `server/load-and-up.sh` | identity / gateway / portal + pg / ldap | 沿用旧 compose 项目名；从运行中容器继承 `REACTOR_*` 环境变量；数据卷只创建不删除 |
| `web/load-and-up.sh` | reactor-web 容器 | 沿用旧项目名、旧令牌与网络；迁移旧 `/root/.reactor`；重建后接回 `reactor-web-backend` 网络 |
| 顶层 `load-and-up.sh` | 顺序调度 | 先 `server/` 再 `web/` |

### 5.1 现场只有 docker-compose v1 也没有关系

两个脚本都会自动识别：`docker compose`（v2）→ `docker-compose` → `compose`。
v1 下会生成一份 `.compose.v1.yml`（补 `version: "2.4"`、去掉顶层 `name:`），
**项目名始终用 `-p` 显式指定**，两种版本行为一致。

> 唯一依赖 v2 的是 HTTPS override（`compose.https.yml` 用了 `!reset` 语法）；
> 不用 HTTPS 就完全不受影响。

### 5.2 原位升级必须"沿用"的东西

1. **compose 项目名**：旧部署的 `kb-files / updates / feedback-files` 卷名带项目前缀
   （如 `docker_kb-files`）。项目名漂移会创建一套空卷，现场表现是
   "知识库文件、已发布安装包全没了"。脚本读 `reactor-desktop-identity` 的
   `com.docker.compose.project` 标签并沿用。
2. **容器里的环境变量**：JWT 主密钥、加密主密钥、上游 Key 只存在于运行中的容器里。
   升级时脚本从容器 dump 出 `REACTOR_*` 写成临时 env_file 再交给 compose——
   直接依赖包里的 `.env` 会把鉴权配置**悄悄清空**。
3. **数据卷**：`docker_pg-data / docker_ldap-data / docker_ldap-config` 是 external 卷，
   全新机器要先 `docker volume create`。
4. **Web 的网络接线**：compose 重建容器会丢掉手工接入的 `reactor-web-backend`，
   容器内 `identity:8791` 会 DNS 失败（登录页 fetch failed）。
   所以 Web 脚本是 `create → 接网络 → start`，**不能先 `up -d` 再接线**。

### 5.3 绝对不要做的事

- 不要 `docker compose down -v`（`-v` 会删数据卷：会话库、我的空间、凭据全丢）；
- 不要手删 `reactor-web` 容器再让脚本接管（脚本要读它的项目名/令牌/网络来继承）；
- 不要改容器里的 `HOME`（凭据密文密钥由 `platform + homedir + user` 推导，改了必然解密失败）；
- 不要在升级包里改 `.env` 里的密钥值（升级脚本以容器里的真实值为准）。

### 5.4 升级后"页面没变"怎么排查

1. 门户：比对镜像 ID——`docker inspect reactor-desktop-portal --format '{{.Image}}'` 与
   `docker image inspect reactor-portal:v<版本> --format '{{.Id}}'`。相同就说明镜像没更新，
   页面内容来自数据库，不是镜像问题。改完记得 Ctrl+F5 强刷。
2. Web：确认容器健康与版本，`curl http://<IP>:3030/api/server-info` 看 `version`；
   登录页出现说明会话模式已生效。

### 5.5 Web 两种登录模式

- **默认企业账号登录**（`REACTOR_WEB_SESSION_AUTH=1`）：每个浏览器一条会话，
  每个账号一个降权 worker，工作区 `/data/users/<uid>` 隔离。
- **回退共享令牌**（`REACTOR_WEB_SESSION_AUTH=0`）：`http://<IP>:3030/?token=<令牌>`。
  旧令牌在升级时会被脚本沿用并回写到 `web/.env`（终端不回显令牌）。

## 6. 交付前检查清单

```bash
# 1. 版本一致
grep '"version"' package.json

# 2. 打包（按需选目标）
node scripts/release/package-release.mjs all --verify

# 3. 清单全量校验（独立再跑一次，跨机器交付时更有意义）
cd "E:\工作\Reactor-版本更新\V<version>" && sha256sum -c MANIFEST.sha256

# 4. 镜像可加载（只在"换机器/交付给别人"时做）
docker load -i web/images/reactor-web-v<version>.tar.gz
```

- [ ] 版本号与文件名、镜像 tag 一致
- [ ] 四个目标的产物都在交付目录里
- [ ] `MANIFEST.sha256` 全量 `OK`
- [ ] `docs/更新说明-V<version>.md` 写清了本次改动
- [ ] 桌面安装包图标为最新样式（用 `Icon.ExtractAssociatedIcon` 提取确认）
- [ ] 包内 agent bundle 不含旧品牌提示词（`grep -c "You are an interactive ZCode agent"` 应为 0）
